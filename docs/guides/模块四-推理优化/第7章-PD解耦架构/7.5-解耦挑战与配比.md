## 1. 解耦后多出来的复杂度

相对单引擎混合服务，解耦至少新增：

| 挑战 | 具体表现 |
|---|---|
| **双池调度** | 既管 P 队列也管 D 队列，还要管两者之间的交接 |
| **状态迁移** | KV 传输、失败重试、超时与幂等（[7.2](./7.2-解耦架构设计.md) 状态机） |
| **一致性运维** | 两池模型版本、量化配置必须匹配 |
| **故障域扩大** | P 正常 D 挂、或传输挂，都要有降级路径 |
| **可观测性** | 需打通 TTFT 分段（排队/算/传/再排队） |
| **配比与弹性** | $N_p:N_d$ 随负载结构漂移，静态度假日夜翻车 |

🔑 **核心概念**：解耦把「一个难调度」变成「两个阶段 + 一条传输链」——阶段互扰下降，**系统熵上升**。只有当 Goodput 收益（在目标负载与总成本下）盖过熵增时才值得。

## 2. 配比问题为什么致命

设集群共有 $N$ 张 GPU，分给 Prefill 池 $N_p$、Decode 池 $N_d$，$N_p + N_d = N$（可再留管理节点；若每池内部还有 TP，则「池容量」按 TP 组数理解，见 [6.2](../第6章-分布式推理/6.2-张量并行推理.md)）。

- $N_p$ 太大：Decode 槽位不够，KV 传入后排队，TPOT/可用性变差，P 侧也会因背压空转。
- $N_d$ 太大：Prefill 能力不足，TTFT 排队，D 侧饥饿。

聚合服务里这种错配被「同一池混跑」掩盖成利用率数字；解耦后错配会**直接打在双 SLO 上**。

⚠️ **注意**：配比不是静态勋章。白天聊天 Decode 重、夜间批处理 Prefill 重，同一配比可能昼夜交替翻车。

## 3. 手算：P:D 配比直觉

### 3.1 工作量粗口径

从日志估计单位时间：

- 到达率 $\lambda$（请求/s）；
- 平均输入长度 $\bar{S}_{in}$、输出长度 $\bar{S}_{out}$；
- 目标 TTFT/TPOT SLO。

粗口径（可替换为实测 profile）：

- Prefill 工作量 $\propto \lambda \times \bar{S}_{in}$
- Decode 工作量 $\propto \lambda \times \bar{S}_{out}$（每输出 Token 一步）

再除以单 GPU（或单 TP 组）在该阶段的可持续处理速率，得到所需并行度，并加突发/KV 余量：

\[
N_p \propto \frac{\lambda \bar{S}_{in}}{r_P} \times (1 + \alpha_{\mathrm{burst}}),\quad
N_d \propto \frac{\lambda \bar{S}_{out}}{r_D} \times (1 + \alpha_{\mathrm{KV}})
\]

其中 $r_P$、$r_D$ 为单卡（组）在该阶段的可持续 Token/s，**必须来自同模型同量化的 profile**，不能从宣传材料抄。

### 3.2 示意手算

教学示意（**非某集群实测**）。前提：

- $\lambda = 4\,\mathrm{req/s}$，$\bar{S}_{in}=2048$，$\bar{S}_{out}=256$；
- profile 得单卡可持续 $r_P \approx 8\times 10^4$ prefill tok/s，$r_D \approx 2\times 10^3$ decode tok/s（Decode 显著更「慢」是 Memory Bound 的常见画像，数字仅示意）；
- 余量先取 $\alpha_{\mathrm{burst}}=\alpha_{\mathrm{KV}}=0.25$。

则工作量速率：

\[
\lambda \bar{S}_{in} = 8192\,\mathrm{tok/s},\quad
\lambda \bar{S}_{out} = 1024\,\mathrm{tok/s}
\]

粗算卡数：

\[
N_p \approx \frac{8192}{8\times 10^4}\times 1.25 \approx 0.13,\quad
N_d \approx \frac{1024}{2\times 10^3}\times 1.25 \approx 0.64
\]

取整并保证每池至少能跑完整并行度后，**起点比例**常落在「D 多于 P」——例如总预算 $N=8$ 时先试 $(N_p,N_d)=(2,6)$ 或 $(3,5)$。若换成 RAG 画像 $\bar{S}_{in}=8192$、$\bar{S}_{out}=128$，则 $N_p$ 相对上升，起点改为更靠近 $1:1$ 或 $N_p$ 略多。

取舍句：**公式给的是搜索起点；在候选比例上跑混合压测，选 Goodput 最高且双 SLO 达标的点，才是答案**（门禁模板见 [7.4](./7.4-Goodput与SLO感知调度.md)）。不要把「经验 1:2」写成真理。

```text
扫描例（N=8）：
  (Np,Nd) = (2,6), (3,5), (4,4), (5,3)
  主看：Goodput、TTFT P95、TPOT P95、transfer P95、两池队列
```

症状对照（压测时用来解释「为什么这档输了」）：

| 现象 | 更可能缺什么 |
|---|---|
| TTFT P95 破线、P 队列很长 | $N_p$ 不足，或 Prefill 批策略过保守 |
| TPOT P95 破线、D 侧 KV/并发打满 | $N_d$ 不足 |
| 两池队列都短，但 TTFT 仍差 | 传输税（先看 [7.3](./7.3-KV-Cache传输与Connector.md)，别拧配比） |
| Raw QPS 高、Goodput 低 | 接纳过猛或 SLO 定义未进调度（[7.4](./7.4-Goodput与SLO感知调度.md)） |

📌 **关键点**：$r_P/r_D$ 随模型、量化、批大小剧烈变化；换模型或换 INT4/FP8 后，配比要重做手算 + 重扫，不能继承旧比例。

## 4. 动态负荷与再平衡

生产中更稳妥的做法是「慢变化再平衡」：

1. 监控 P 队列等待、D 队列等待、KV 传输耗时、双 SLO 违约率；
2. 若 TTFT 违约主导 → 扩 P 或缩 D（在总预算内迁移）；
3. 若 TPOT/D 排队主导 → 扩 D；
4. 若传输主导 → 先优化拓扑/后端（[7.3](./7.3-KV-Cache传输与Connector.md)），而不是盲目加 GPU。

自动迁移 GPU 池属于高阶能力（涉及模型重载或弹性实例）。团队初期可按高峰档位做**分时静态配比**（业务高峰一套、夜间一套）。

💡 **提示**：先做「告警 + 人工改副本数」，再做自动弹性。自动配比在错误指标（只看利用率）下会放得很大。

## 5. 何时用、何时不用

**更适合评估解耦**

- TTFT 与 TPOT 双 SLO 同时紧；
- 负载强混合（长 Prefill + 大量流式 Decode），且 [7.1](./7.1-混合Batching的问题.md) 的 IF 在同引擎优化后仍高；
- 集群有足够高速互联，代表 Prompt 的传输税可控（[7.3](./7.3-KV-Cache传输与Connector.md)）；
- 团队具备双池运维与分段观测能力。

**更适合继续聚合**

- 离线批处理、单 SLO 或 SLO 很松；
- 请求同质、几乎无长尾 Prefill；
- 网络一般，长 Prompt KV 传输昂贵；
- 集群规模小，拆池后每池并行度不够（例如总共 2～4 卡）；
- 控制面人力不足，稳定性优先。

| 条件 | 倾向 |
|---|---|
| 双紧 SLO + 混合负载 + 好网络 + 运维就绪 | 评估解耦 |
| 松 SLO / 同质负载 / 差网络 / 小集群 | 聚合 |
| 昼夜负载结构剧变 | 聚合、分时静态配比，或自适应统一框架（[7.2](./7.2-解耦架构设计.md)） |

## 6. 挑战与决策清单

上线前把挑战逐项打勾；缺一项就先补课，而不是先改生产流量：

```text
挑战清单（运维 / 系统）
[ ] 双池调度与交接超时/重试协议已定义
[ ] P/D 模型版本与量化配置一致性有门禁
[ ] 传输失败、D 池满、P 池 OOM 的降级路径已演练
[ ] TTFT 分段追踪（排队/算/传/再排队）已打通
[ ] 代表 Prompt 的 KV 体积与 transfer P95 已测

决策清单（是否上解耦 / 如何配比）
[ ] 同引擎手段（Chunked Prefill 等）已挖过浅层收益
[ ] 已定义 TTFT/TPOT 分位 SLO 与 Goodput
[ ] 至少 3 组 Np:Nd 的对比压测（同总 GPU、同负载）
[ ] 手算起点与压测结论一致或已解释偏差
[ ] 发布对比表主看 Goodput，而非只看 Raw QPS
```

## 7. 代价与权衡

| 选择 | 收益 | 代价 / 不适用 |
|---|---|---|
| 固定解耦 + 静态配比 | 运维简单、行为可预期 | 昼夜负载结构剧变时双杀 SLO |
| 分时两套配比 | 跟高峰走 | 切换窗口的抖动与变更成本 |
| 自动弹性迁移 GPU | 跟指标走 | 重载/放置复杂；指标错则放大错误 |
| 小集群强行拆池 | 「架构正确」叙事 | 每池并行度不够，两端都变慢 |

适用：总 GPU 预算足够两池各自形成可用并行度，且传输预算已过门槛。  
若 $N$ 很小或 $r_P/r_D$ 尚未 profile，先聚合把 IF 与 Goodput 基线测准（实战见 [7.6](./7.6-vLLM-Disaggregated-Prefill实战.md)）。

## 📝 总结

- 解耦用阶段隔离换来调度、传输、运维上的熵增；要用 Goodput 证明值得。
- **P/D 配比错了会直接双杀 SLO**；用手算（$\lambda,\bar{S},r_P,r_D$）给起点，用压测定案。
- 配比应随负载与量化配置演进；传输瓶颈优先于盲目加卡。
- 双紧 SLO、强混合、好网络、运维就绪时评估解耦；小集群、差网络、松 SLO 时聚合往往更优。

## 🎯 自我检验清单

- 能列举解耦相对聚合新增的三类以上复杂度
- 能解释 $N_p$ 过大或 $N_d$ 过大各自的症状
- 能按输入/输出长度与 $r_P/r_D$ 给出配比搜索的起点直觉
- 能说明为何最终必须以 Goodput 压测定案
- 能判断一组给定约束下该不该上解耦
- 能走完挑战清单与决策清单并指出缺口
