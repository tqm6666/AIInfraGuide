## 本节目标
7.2 已经定义 producer、consumer 与所有权。
本节把“交接 KV”展开成一条完整数据协议，不罗列传输产品。
学完后，你应能：
- 从模型结构推导 KV 主体字节数；
- 解释逻辑 token、物理 page、layout 与 TP shard；
- 区分 pack、register、transfer、visibility 与 ack；
- 用 effective bandwidth 而不是链路线速估算延迟；
- 识别传输成功但语义失败的情况；
- 把 Connector 理解为协议抽象。

## 1. 固定算例与 KV 字节公式
固定工作负载仍为：
- 输入 $4096$ token；
- 输出 $256$ token；
- $s_P=80$ GPU-ms/request；
- $T_{prefill,wall}=80$ ms/request，由目标 batch 下独立测得，不由 $s_P$ 换算；
- $s_D=320$ GPU-ms/request；
- Prompt KV 为 $512$ MiB/request；
- $BW_{transfer}=25$ GiB/s，计时边界为数据阶段 `post→complete`；
- $\lambda=6$ requests/s；
- TTFT $\le250$ ms；
- P99 TPOT $\le35$ ms；
- E2E $\le6.5$ s。
### 1.1 通用公式
对常见自注意力模型，记：
- $L$：Transformer 层数；
- $H_{kv}$：KV head 数；
- $D_h$：每个 head 的维度；
- $S$：每个元素字节数；
- $T$：需要保存的 token 数；
- 因子 $2$：Key 与 Value。
每 token 的 KV 主体为：
$$
Bytes_{KV/token}=2LH_{kv}D_hS
$$
$T$ 个 token 的主体为：
$$
Bytes_{KV}=2LH_{kv}D_hST
$$
该式不包含：
- page 尾部对齐；
- block table 与描述符；
- 量化 scale；
- layout 转换 buffer；
- 协议元数据；
- 源、目标短时双份占用。
### 1.2 为什么使用 KV head
MHA 中 $H_{kv}$ 通常等于 query head 数。
GQA 中多个 query head 共享较少 KV head。
MQA 会进一步减少 KV head。
因此不能机械地用 attention head 数计算所有模型。
## 2. 512 MiB 怎样推导
取一组与固定算例一致的教学形状：
$$
L=32,\quad H_{kv}=8,\quad D_h=128,\quad S=2
$$
每 token KV 为：
$$
2\times32\times8\times128\times2
=131072\text{ bytes}
=128\text{ KiB}
$$
4096-token Prompt 为：
$$
4096\times128\text{ KiB}=512\text{ MiB}
$$
### 2.1 Decode 还会继续增长
每生成一个 token，D 追加约 $128$ KiB。
256 个输出 token 最多新增：
$$
256\times128\text{ KiB}=32\text{ MiB}
$$
请求结束附近的 KV 主体约为：
$$
512+32=544\text{ MiB}
$$
P→D 初始交接仍是 Prompt 的 $512$ MiB。
### 2.2 dtype 变化
若元素从 2 bytes 降到 1 byte，主体理论上减半。
但协议仍要约定：
- KV dtype；
- scale 的组织；
- 每层或每 block 的量化元数据；
- P/D 对字节的解释。
减少 payload 不会自动解决兼容性和精度问题。
## 3. 从 token 到 page
引擎通常按固定 token 数分配 page 或 block。
记一个 block 容纳 $B$ token。
跨所有层的 block 主体为：
$$
Bytes_{block}=B\times Bytes_{KV/token}
$$
若 $B=16$：
$$
Bytes_{block}=16\times128\text{ KiB}=2\text{ MiB}
$$
4096 token 需要：
$$
N_{block}=\left\lceil\frac{4096}{16}\right\rceil=256
$$
总主体为：
$$
256\times2\text{ MiB}=512\text{ MiB}
$$
逐 token 与逐 block 推导闭合。
### 3.1 非整块对齐
一般情况：
$$
N_{block}=\left\lceil\frac{T}{B}\right\rceil
$$
物理分配量为：
$$
Bytes_{allocated}=N_{block}\times Bytes_{block}
$$
最后一个 block 即使只使用一个 token，也可能占完整空间。
固定算例恰好整除，不代表真实流量没有碎片。
### 3.2 block table 是语义
consumer 不只需要字节，还需要知道：
- token 对应哪个目标 block；
- block 内 token offset；
- layer 与 K/V 顺序；
- 哪些 block 已完整；
- 映射属于哪个 generation。
字节正确而 block table 错误，仍会生成错误结果。
### 3.3 描述符数量
若每层、K/V、block 都单独描述，朴素数量近似：
$$
N_{desc}=L\times2\times N_{block}
$$
固定算例为：
$$
32\times2\times256=16384
$$
真实实现通常聚合连续区间。
否则 pack、注册查询和 post 会被大量小描述符放大。
## 4. Layout 与 TP 分片
### 4.1 逻辑维度
KV 常包含：
```text
layer
K or V
block
token within block
kv head
head dimension
```
物理内存可以按不同顺序排列这些维度。
总字节相同，不代表同一 offset 表示同一元素。
### 4.2 Layout 转换
P/D layout 不同时，handoff 可能需要 permute 或 pack。
一次完整转换至少读源、写目标：
$$
Traffic_{permute}\gtrsim2\times Bytes_{KV}
$$
对 $512$ MiB KV，最低 HBM 流量约为：
$$
2\times512\text{ MiB}=1\text{ GiB}
$$
它不增加 wire payload，却增加 HBM 争用、临时区与延迟。
### 4.3 TP 分片
设 TP 度为 $p$，KV head 可均匀切分。
每个 rank 近似持有：
$$
\frac{Bytes_{KV}}{p}
$$
所有 rank 的聚合字节仍为：
$$
\sum_{r=1}^{p}Bytes_r\approx Bytes_{KV}
$$
若 $TP=4$：
```text
4 ranks × 128 MiB/rank = 512 MiB
```
单 rank 变小，没有让网络总量消失。
### 4.4 P/D TP 不同
若 $TP_P=4$、$TP_D=2$：
```text
P: 4 个源 shard，每个约 128 MiB
D: 2 个目标 shard，每个约 256 MiB
```
协议必须定义：
- KV head 怎样合并；
- rank-local block ID 怎样映射；
- 是否需要重分片；
- shard 到达顺序；
- 何时所有目标 rank 同时 READY。
异构 TP 是数据重排问题，不只是连接数问题。
## 5. 完整 handoff 链
把交接只写成 $KV/BW$ 会漏掉关键步骤。
```text
pack
  -> register
  -> metadata exchange
  -> transfer
  -> completion
  -> visibility
  -> commit
  -> ack
  -> source release
```
### 5.1 Pack
pack 把逻辑 block 变成可传输区间。
它可能：
- 收集源 block；
- 聚合连续地址；
- 生成 scatter/gather 描述；
- 转换 layout；
- 附加 token、dtype 与 shard 信息。
page 越分散，pack 的 HBM 与 CPU 成本越高。
### 5.2 Register
数据移动层要知道哪些内存可被设备访问。
register 阶段建立或查找：
- 源、目标 region；
- 设备可访问句柄；
- 地址到描述符的映射；
- region 生命周期。
冷路径创建注册，热路径复用已有 region。
扩容和 worker 重启仍可能回到冷路径。
### 5.3 Metadata exchange
双方交换描述，而不是 KV 主体：
```text
request_id + generation
model / layout / dtype identity
token / layer / shard range
source descriptors
target block mapping
expected bytes and completions
```
元数据到达只允许 consumer 准备接收。
### 5.4 Transfer
transfer 才是字节实际移动。
异步 post 只表示工作进入设备队列。
调用返回不等于目标数据可见。
### 5.5 Completion
多描述符、多 shard 请求必须满足：
$$
CompletedCount=ExpectedCount
$$
以及：
$$
CompletedBytes=ExpectedBytes
$$
任何 shard 缺失都不能把请求标为完整。
### 5.6 Visibility
若传输与 Attention 位于不同 stream，必须建立 event 或 fence 依赖。
正确顺序是：
$$
KVWrite\prec DecodeRead
$$
设备完成不自动等于所有消费者可读。
### 5.7 Commit
consumer 将目标 KV 从 NOT_READY 原子发布为 READY。
多 rank 必须形成请求级屏障。
不能让一部分 rank 开始 Decode，而另一部分仍在接收。
### 5.8 Ack 与释放
D 确认正确 generation 已提交，P 才能释放源 KV。
ack 丢失时依靠幂等重试或安全 lease 回收。
迟到 ack 必须校验 generation 与 worker epoch。
## 6. Effective bandwidth
本章的 $25$ GiB/s 是数据传输阶段按 `post→complete` 实测的 $BW_{transfer}$，不是标称线速，也不是从 Prefill 结束到 READY 的完整 handoff 带宽。
### 6.1 数据阶段时间
$$
T_{transfer,data}
=\frac{0.5\text{ GiB}}{25\text{ GiB/s}}
=20\text{ ms}
$$
它只覆盖已 post 的 KV 主体直到全部 transfer completion。
### 6.2 READY 与源释放时间
$$
\begin{aligned}
T_{handoff\to READY}={}&T_{pack}+T_{register}+T_{meta}\\
&+T_{queue,xfer}+T_{transfer}\\
&+T_{visibility}+T_{commit}
\end{aligned}
$$
$T_{handoff\to READY}$ 是 TTFT 的交接临界路径。READY 后的 ownership ack 决定 producer 何时释放源 KV；它应另记为 $T_{ack,after\ READY}$，不能塞进首 Token handoff 后再重复等待。
若目标分配和 READY 后等待单列，还要加入 $T_{alloc,D}$ 与 $queue_D$。
### 6.3 两种带宽口径
纯数据阶段：
$$
BW_{transfer}=\frac{Bytes_{KV}}{T_{complete}-T_{post}}
$$
整个交接：
$$
BW_{handoff}=\frac{Bytes_{KV}}{T_{ready}-T_{prefill\_end}}
$$
前者诊断数据通道，本章固定的 $25$ GiB/s 只对应此前者；后者接近 TTFT handoff 成本。
报告必须注明时间边界。
### 6.4 平均值不能保护 P99
平均数据率：
$$
6\times0.5=3\text{ GiB/s}
$$
平均链路占用：
$$
\frac{3}{25}=12\%
$$
多个 Prefill 同时完成时，仍会瞬间提交多个 $512$ MiB。
排队、注册锁和目标分配会放大 P99。
## 7. 并发、流水与背压
### 7.1 并发不复制容量
共享瓶颈满足：
$$
\sum_{i=1}^{n}BW_{transfer,i}\le25\text{ GiB/s}
$$
四个 $512$ MiB 请求公平共享时，每个约得 $6.25$ GiB/s：
$$
T_i\approx\frac{0.5}{6.25}=80\text{ ms}
$$
聚合吞吐仍高，单请求数据阶段却比 $20$ ms 教学值高四倍，随后仍需 visibility 与 commit 才能进入 READY。
### 7.2 流水隐藏部分成本
若已生成 block 可先传，移动可与剩余 Prefill 重叠：
$$
T_{wall}\approx\max(T_{prefill},T_{transfer})+T_{tail}
$$
$T_{tail}$ 包含首 Token 临界路径上最后的 visibility 与 commit；READY 后的 ack 只延长 producer 的源 KV 保留时间。
流水减少临界路径，不减少总字节。
### 7.3 背压
consumer 没有目标 block 时，producer 不应无限 post。
至少限制：
- in-flight bytes；
- in-flight requests；
- NOT_READY 目标页；
- producer retained KV；
- 每条共享路径并发数。
限并发可能降低瞬时吞吐，却能保护 TTFT 和显存上限。
## 8. 一致性与原子可见
### 8.1 身份一致
最小身份为：
$$
(request\_id,generation,model\_revision)
$$
旧请求的迟到数据不能写入新请求复用的 block。
### 8.2 范围一致
必须约定：
- Prompt token 起止；
- layer 与 K/V；
- shard 范围；
- 已命中与未命中范围。
少一个或多一个 block 都会破坏 position 语义。
### 8.3 格式一致
双方必须匹配：
- dtype 与 scale；
- block size；
- layout；
- TP/PP shard map；
- Attention 对 KV 的解释。
字节校验通过不等于 Tensor 解释相同。
### 8.4 原子提交
请求级 READY 条件为：
$$
READY_g\iff CommitPublished_g\land\bigwedge_{r=1}^{N_{shard}}Visible_{r,g}
$$
其中 $g$ 是 request generation。$Complete_{r,g}$ 只是 $Visible_{r,g}$ 的必要前置；设备 completion 尚未建立 Decode stream 的可读依赖，因此不能单独触发 READY。
任何 shard 尚不可见或 generation commit 尚未发布，整个请求都保持 NOT_READY。
这相当于先写不可见目标，再统一提交可见。
### 8.5 回收一致
源释放过早会 use-after-free。
释放过晚会显存泄漏。
lease、ack、取消和失败必须指向同一幂等终态。
## 9. 软失败
软失败不一定返回错误码，却会让延迟或容量悄悄恶化。
### 9.1 注册缓存失效
数据仍能传，但每次重复冷注册。
wire 带宽正常，固定开销升高。
### 9.2 描述符碎片
主体仍是 $512$ MiB，小段数量却大增。
pack、post 与设备队列压力上升。
### 9.3 路径回退
连接可用且最终到达，但实际走较慢路径。
只检查“成功”看不见 effective bandwidth 下降。
### 9.4 完成通知丢失
D 已 READY 并正确 Decode，P 却没有收到 ack。
结果正确，但源 KV 长期滞留。
### 9.5 lease 过期过早
D 仍在排队或传输，P 已回收源 block。
请求随后失败，甚至读取复用后的数据。
### 9.6 layout 或 shard 错误
字节数和传输校验都可能正确，输出却错误。
必须结合 request、token、layout 与结果检测。
### 9.7 READY 发布遗漏
数据完整到达，请求却永远等待。
表现为 D 空闲而 TTFT 持续增长。
## 10. Connector 的正确抽象
Connector 位于推理引擎与外部 KV 能力之间。
它不是网卡，也不是完整集群调度器。
合理抽象至少参与：
1. 声明可由外部获得的 KV token；
2. 在调度时映射目标 block；
3. 生成 pack 与传输描述；
4. 启动异步 save/load；
5. 汇总完成事件；
6. 向调度器发布 READY；
7. 返回 ack 或释放通知；
8. 在取消、超时和失败时清理。
它对上提供 request/block 语义，对下使用数据移动或存储能力。
不同实现可以选择不同路径，但必须兑现相同正确性合同。
正确问题不是“哪个名字最快”，而是：
> 它在目标 layout、TP、故障与 SLO 下，能否完整实现这条协议？
## 11. 交接验收问题
1. 字节公式使用 KV head 还是 query head，$512$ MiB 是否含 page 对齐与 scale？
2. block table 怎样绑定 generation，P/D layout 不同时在哪里转换？
3. TP 不同时如何重分片，注册是冷路径还是热路径？
4. $25$ GiB/s 的计时边界是什么，并发传输时每请求 P99 是多少？
5. completion 与 visibility 如何区分，多 rank 怎样原子 READY？
6. ack 丢失后谁回收源 KV，迟到写如何隔离复用 block？
7. consumer 变慢时谁限制 producer？
## 总结
1. KV 主体由层数、KV head、head dimension、dtype 与 token 数共同决定。
2. 固定形状下每 token 为 128 KiB，4096-token Prompt 恰好产生 512 MiB。
3. page、block table、layout 与 TP shard 都是交接语义。
4. TTFT handoff 到 READY 包含 pack、register、metadata、transfer、visibility 与 commit；其后的 ownership ack 控制源 KV 释放。
5. $512$ MiB 在 $25$ GiB/s 下的 $20$ ms 只对应 `post→complete` 数据阶段。
6. 平均链路占用 12% 仍可能在并发完成时产生长尾。
7. Connector 是引擎侧协议抽象，而不是产品列表。
