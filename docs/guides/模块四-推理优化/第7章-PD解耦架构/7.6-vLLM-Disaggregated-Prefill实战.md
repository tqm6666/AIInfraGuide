这里的“实战”不是命令、部署步骤、benchmark 或源码文件清单。

- 把 P/D 映射为 producer 与 consumer；

- 说明 fail 与 recompute 两类回退；

- 区分“有输出”和“运行时正确”。

## 1. 版本坐标与固定算例
vLLM v0.27.1 将 Disaggregated Prefilling 标为实验能力。
该版本的官方定位强调：
- 分别优化 TTFT 与流式节拍；
- 物理隔离 mixed Prefill 对 tail ITL 的影响；
- 该机制本身不承诺提高 throughput；
- 生产能力依赖基础设施和外部控制面。
这与本章成本式一致：
$$
T_{PD}=queue_P+T_{prefill,wall}+T_{handoff\to READY}+queue_D+T_{decode,wall}
$$
解耦用到 READY 的 handoff、双队列和状态换取更小的统一实例互扰；READY 后 ownership ack 另行控制源 KV 回收。
验证重点应是联合 Goodput 和状态收敛。
### 1.1 固定工作负载
- 4096 Prompt token；
- 256 输出 token；
- $s_P=80$ GPU-ms/request；
- $T_{prefill,wall}=80$ ms/request，由目标 batch 下独立测得，不由 $s_P$ 换算；
- $s_D=320$ GPU-ms/request；
- 512 MiB Prompt KV；
- $BW_{transfer}=25$ GiB/s，计时边界为数据阶段 `post→complete`；
- $\lambda=6$ requests/s；
- TTFT $\le250$ ms；
- P99 TPOT $\le35$ ms；
- E2E $\le6.5$ s。
本节不换算例来美化实现结论。
## 2. 理论角色映射
### 2.1 Producer
Producer 是承担 Prefill 的 vLLM 引擎角色。
它负责：
- 接收 Prompt 请求腿，由 Scheduler 分配 KV block；
- 由 model runner 执行 4096-token Prefill；
- 让 Connector 导出 KV，并产出 consumer 所需元数据；
- 在确认前保持源 block 生命周期。
Producer 是所有权与数据方向概念，不表示可以忽略 deadline。
### 2.2 Consumer
Consumer 是承担 Decode 的 vLLM 引擎角色。
它负责：
- 接收原请求与远端 KV 描述，并分配目标 block；
- 让 Connector 加载 512 MiB KV，未就绪时阻止执行；
- READY 后生成 256 token，并管理 KV 增长；
- 结束或取消时释放目标 block。
### 2.3 Connector
Connector 是 vLLM 引擎内的 KV 协议边界。
它把 Scheduler 的 request/block 语义与 worker 数据移动连接起来。
它不是端到端 Router、全局负载均衡器、租户 admission controller、P:D 容量规划器或完整故障恢复平台。
它的核心职责是让外部 KV 可正确等待、消费和释放。
## 3. 外部协调者的边界
P 与 D 引擎不会仅凭同时存在就自动组成服务。
两条请求腿之间仍需要外部协调者。
它至少负责：
- 生成 request identity，并选择兼容 producer/consumer；
- 编排 P leg、接收交接元数据并启动 D leg；
- 转发 consumer 流式输出；
- 维护 pairing，并传播取消、deadline 与错误。
在 vLLM 语境中，交接元数据可由 `kv_transfer_params` 一类不透明结构承载。
协调者负责关联和转发，不负责搬运 512 MiB KV 主体。
### 3.1 P leg 成功不是请求成功
Producer 返回只说明 P leg 到达一个协议点。
它不保证：
- 数据已到 D；
- D 已分配 block；
- D 已发布 READY；
- P 已收到 ack；
- 客户端已看到首 token。
客户端 TTFT 结束点仍在 consumer 输出经过协调者后到达客户端。
### 3.2 pairing 绑定 epoch
最小身份为：
$$
(request\_id,generation,P\_epoch,D\_epoch)
$$
worker 重启后，旧远端描述必须失效。
地址或 block ID 数值相同，不代表生命周期相同。
## 4. Scheduler 侧与 Worker 侧
vLLM 的 Connector 集成可分成逻辑侧和数据侧。
### 4.1 Scheduler 侧
Scheduler 关心：
- 外部 KV 覆盖哪些 Prompt token、应分配哪些目标 block；
- 请求是否等待或已完成远端 KV；
- 何时恢复调度，以及失败/取消时释放什么。
Scheduler 不能把异步 post 返回当成 KV 可用。
### 4.2 Worker / model runner 侧
worker 关心：
- 根据 metadata 定位源/目标并启动 save/load；
- 查询设备完成并建立 stream 可见性；
- 汇总请求级完成，通过 `KVConnectorOutput` 一类结果通知 Scheduler。
它对应 7.3 的：
```text
register -> transfer -> completion -> visibility
```
### 4.3 调度循环
```text
Scheduler 生成 Connector metadata
  -> model runner 执行数据操作
  -> worker 返回完成集合
  -> Scheduler 推进 request state
```
Connector 因此是调度协议的一部分，而不是独立后台复制工具。
## 5. Producer 请求路径
### 5.1 入队
请求进入 producer 的 P 队列。
理论状态是 `P_QUEUED`。
TTFT deadline 已经开始消耗。
### 5.2 分配与 Prefill
KV cache manager 分配 block。
model runner 执行 4096-token Prefill。
目标 batch 下服务需求为 $80$ GPU-ms/request。
固定 TTFT 时间线另使用独立测得的 $T_{prefill,wall}=80$ ms；两者数值相同不表示 GPU 服务需求等于单请求墙钟时间。
完成后，512 MiB KV 已写入 producer 本地 cache。
### 5.3 导出元数据
Scheduler 与 Connector 形成：
- request identity 与可交接 token 范围；
- 源 block/shard 描述与 layout/dtype 契约；
- consumer 找到 producer 所需信息。
这些是控制数据，不是 KV 主体。
### 5.4 源 KV 保留
P leg 完成后，源 block 不能立即回到空闲池。
```text
request = KV_PRODUCED
source_owner = producer
consumer_ready = false
```
源 KV 保留到以下事件之一：
- consumer 确认；
- 取消且数据操作安全终止；
- lease 到期且无迟到访问；
- 请求失败并完成清理。
### 5.5 Producer 的终点
对协调者而言，P leg 成功只允许进入 `HANDOFF_PENDING`。
把它计为 completed request 会重复计数并美化吞吐。
## 6. Consumer 请求路径
### 6.1 接收和验证
Consumer 收到原请求与远端 KV 元数据。
它先验证：
- request identity、model revision 与 Prompt token 前缀；
- KV dtype、block/layout 与并行分片兼容性。
metadata 正确后，数据仍未 ready。
### 6.2 识别远端 Prefill
Scheduler 识别 Prompt KV 将从外部加载。
除非进入明确故障回退，consumer 不应再次正常 Prefill。
### 6.3 分配目标 block
KV cache manager 为 4096 个逻辑已计算 token 分配本地 block。
此时目标是：
```text
allocated
uncommitted
not consumable
```
它已经占容量，却不能被 Attention 或其他请求复用。
### 6.4 异步加载
worker Connector 发起 load。
按 `post→complete` 计时边界，数据阶段教学值为：
$$
\frac{512\text{ MiB}}{25\text{ GiB/s}}=20\text{ ms}
$$
到 READY 的 handoff 还包含目标分配、pack、注册、metadata、传输排队、可见性、commit 和完成传播；READY 后 ack 不阻塞首个 Decode step。
### 6.5 完成与恢复
worker 确认所有 shard 可见，并把完成集合交回 Scheduler。
Scheduler 才把请求恢复为可运行。
随后 consumer 执行首个 Decode step。
### 6.6 Decode
请求进入 continuous batching。
平均 TPOT 基线为 20 ms。
256-token Decode 约 5.12 s。
D 侧继续追加最多约 32 MiB KV。
## 7. WAITING_FOR_REMOTE_KVS
vLLM v0.27.1 的 `WAITING_FOR_REMOTE_KVS` 直接映射：
> Prompt 在逻辑上已计算，但物理 KV 尚不可消费。
### 7.1 为什么不能是普通 waiting
远端等待请求通常已经：
- 通过身份检查、分配目标 block并记录外部已计算 token；
- 启动 load，并占用 deadline 与 Connector 状态。
它与尚未获得任何资源的普通 waiting 不同。
### 7.2 为什么不能是 running
数据尚未可见。
若进入 running，Attention 可能读取未完成或旧 block。
显式 waiting 状态就是正确性屏障。
### 7.3 `num_computed_tokens` 的双重语义
Prompt token 可记录为逻辑已计算，因为 D 无需重做 Prefill。
但在 transfer complete 前，该计数不能让模型执行。
逻辑进度必须与物理可见性共同约束调度。
### 7.4 Waiting 也占容量
该状态可能占用：
- request slot、目标 KV block 与 in-flight operation；
- pairing 与 deadline 预算。
容量统计不能只数 running 请求。
### 7.5 完成事件
worker 完成集合到达后，Scheduler 才能：
- 从远端等待集合移除请求；
- 保留其已加载 block；
- 允许 Decode；
- 推进 ack 流程。
完成事件应按 generation 幂等处理。
## 8. KV 完成语义与状态映射
### 8.1 三层完成
第一层是 transfer complete：设备操作结束。
第二层是 Scheduler data ready：worker 确认可见，Scheduler 收到完成。
第三层是 ownership ack：consumer 接管，producer 可释放。
正确顺序是：
```text
transfer complete
  -> data visible
  -> Scheduler READY
  -> consumer ownership
  -> producer release
```
遗漏可见性会导致错误读取。
遗漏 ack 会导致 producer 显存泄漏。
### 8.2 理论状态映射
```text
ARRIVED / ADMITTED
  -> 外部协调者
P_QUEUED / PREFILLING
  -> producer Scheduler + model runner
KV_PRODUCED
  -> producer block 被 Connector 生命周期保留
HANDOFF_PENDING
  -> 协调者携带远端 KV metadata
DATA_IN_FLIGHT
  -> consumer 分配 block，worker 正在 load
DATA_VISIBLE
  -> completion 已返回 Scheduler
D_QUEUED
  -> 离开 WAITING_FOR_REMOTE_KVS
DECODING
  -> consumer 逐 token 执行
DONE
  -> 两侧 block、operation 与 pairing 收敛
```
### 8.3 两层 owner
引擎 owner 管本地 Scheduler 与 KV。
协调者 owner 管端到端 deadline、客户端流与 pairing。
不能让两边都假设“对方会清理”。
### 8.4 两层业务完成
P leg 完成不是业务完成。
D 输出结束也不一定代表 P lease 已释放。
完整终态要求：
$$
ClientTerminal\land ProducerReleased\land ConsumerReleased\land NoInflight
$$
## 9. 固定算例时间线
沿 7.4 的 250 ms TTFT 预算：
```text
P queue                 45 ms
producer Prefill wall   80 ms
handoff to READY        35 ms
D queue                 55 ms
first Decode step       35 ms
-----------------------------
client TTFT            250 ms
```
### 9.1 Producer 区间
前 125 ms 用于 P queue 与 Prefill。
此时源 KV 为 512 MiB，owner 是 producer。
### 9.2 Handoff 区间
35 ms 中的 20 ms 是按 $BW_{transfer}=25$ GiB/s 得到的 `post→complete` 数据阶段教学值。
其余 15 ms 是目标分配、pack、register、metadata、传输排队、visibility 与 commit 的规划余量。
ownership ack 发生在 READY 后，只延长 producer retained-KV 时长，不计入这段 TTFT handoff。
计时边界必须明确，不能与 $queue_D$ 重复。
### 9.3 Consumer 区间
READY 后仍可能等待 55 ms 才进入首个 D step。
所以 Connector transfer 达标不等于 TTFT 达标。
### 9.4 完整 E2E
$$
E2E_{baseline}\approx0.25+5.12=5.37\text{ s}
$$
距离 6.5 s 有 1.13 s。
故障回退若在 D 重做 Prefill，会同时消耗 TTFT 和其他流的 TPOT。
### 9.5 $\lambda=6$ 的状态规模
平均 KV 数据率为 3 GiB/s。
平均 Decode 活跃请求为 $6\times5.12=30.72$。
容量统计要同时看：
- running Decode；
- `WAITING_FOR_REMOTE_KVS`；
- NOT_READY block；
- producer retained KV。
## 10. 取消、失败与回退
### 10.1 等待远端 KV 时取消
需要：
- 从等待集合移除，并停止或隔离 in-flight load；
- 拒绝迟到 completion，安全释放目标 block；
- 通知 producer 回收。
只删除 request 对象会留下数据操作和 KV。
### 10.2 Producer 失败
Prefill 前失败，可由协调者选择新 producer。
Prefill 后、load 前失败时，源 KV 若丢失，只能重做 Prefill或失败。
旧 worker epoch 的 metadata 必须失效。
### 10.3 Consumer load 失败：Fail
请求显式失败。
优点：
- 不在 D 混入 Prefill；
- 故障边界清晰；
- Connector 问题不会被掩盖。
代价是客户端失败或上游重试。
### 10.4 Consumer load 失败：Recompute
Consumer 本地重做缺失 Prefill。
单请求可能完成，但代价是：
- D 调度域重新出现 Prefill；
- 增加 $80$ GPU-ms；
- 其他请求 ITL 可能抖动；
- TTFT slack 减少；
- 故障期容量模型改变。
Recompute 是降级语义，不是免费容错。
### 10.5 部分 shard 完成
任何 shard 失败，请求都不得离开 `WAITING_FOR_REMOTE_KVS`。
应整体失败或整体重试，不能消费部分 KV。
### 10.6 Consumer 在 READY 后失败
若 producer 已释放源 KV，新 consumer 通常不能继续使用旧描述。
最保守路径是重新 Prefill或失败。
### 10.7 Ack 丢失
D 可能正确输出，P 却保留源 block。
需要幂等确认、有界重试、generation 与安全 lease。
这是资源层失败，不一定是结果失败。
### 10.8 协调者失败
pairing 与客户端流可能丢失。
worker lease 必须最终回收孤儿 KV。
可恢复控制面还需保存 request generation、P/D、handoff、deadline 与 cancel state。
## 11. 运行时正确性验收
“有文本输出”只覆盖最外层结果。
### 11.1 模型语义一致
P/D 必须匹配：
- model revision、tokenizer、Prompt token IDs 与 position；
- KV dtype/scale、block size 与 layout；
- TP/PP shard mapping。
文本看似合理不能证明 KV 没有错位。
### 11.2 状态单调
```text
PREFILLING
 -> WAITING_REMOTE
 -> DATA_READY
 -> DECODING
 -> DONE
```
迟到事件不能把 CANCELLED 恢复成 DECODING。
旧 generation 不能推进新 generation。
### 11.3 可见性
只有全部 shard 完成并建立同步屏障后，Scheduler 才能运行请求：
$$
Runnable\Rightarrow AllRemoteKVVisible
$$
### 11.4 资源守恒
终态请求必须满足：
$$
RetainedBlocks_P=0
$$
$$
AllocatedBlocks_D=0
$$
$$
InflightConnectorOps=0
$$
客户端成功但资源不归零，运行时仍不正确。
### 11.5 SLO 记账
请求 trace 应还原：
$$
TTFT=queue_P+T_{prefill,wall}+T_{handoff\to READY}+queue_D+T_{firstD}
$$
以及 $E2E\approx TTFT+T_{decode,wall}$；ownership ack 应另记为 producer 资源回收事件。
重试与 recompute 不能从统计中隐藏。
### 11.6 最小事件链
```text
request_arrived
 -> p_queue / prefill / source_retained
 -> metadata_ready
 -> target_allocated / remote_wait
 -> transfer_complete / data_visible
 -> first_decode / client_first_token
 -> decode_finished
 -> source_released / target_released
```
所有事件使用 `(request_id,generation,P_epoch,D_epoch)` 关联。
## 12. v0.27.1 的能力边界
### 12.1 可以验证
- producer/consumer 可独立执行，Scheduler 能识别远端 Prompt KV；
- consumer 能分配目标 block，请求能进入 `WAITING_FOR_REMOTE_KVS`；
- worker 完成事件能恢复调度，Connector 能反馈 data ready；
- load 失败能进入 fail 或 recompute 语义。
### 12.2 单请求成功不能证明
- $\lambda=6$ 下 P/D 配比稳定，或并发 512 MiB transfer P99 为 20 ms；
- 协调者做了 SLO-aware admission，或 worker 重启后 pairing 可恢复；
- 取消没有 orphan block，或 recompute 不破坏 P99 TPOT；
- 多租户 KV 不串用，或每 GPU Goodput 优于统一实例。
### 12.3 与前五节闭合
```text
7.1 -> 比较 mixed-batch 尾部与统一实例
7.2 -> 检查 owner、READY、ack、cancel、terminal
7.3 -> 检查 512 MiB、25 GiB/s、layout 与 shard
7.4 -> 检查 TTFT、TPOT、E2E 联合 Goodput
7.5 -> 检查 λ=6 下 queue、KV、带宽、背压与冗余
```
五条都闭合，vLLM 层面的“可运行”才成为系统层面的“正确且有价值”。
## 总结
1. vLLM v0.27.1 是实现坐标；该能力目标是阶段隔离与尾延迟控制，不承诺吞吐提升。
2. Producer 生成并保留源 KV，consumer 分配目标 KV、等待加载并执行 Decode。
3. Connector 参与 Scheduler 逻辑和 worker 数据执行，但不替代外部协调者。
4. `WAITING_FOR_REMOTE_KVS` 显式编码“逻辑已计算、物理尚不可见”。
5. transfer complete、Scheduler READY 与 ownership ack 是不同完成层次。
6. fail 保持隔离，recompute 可挽救请求却把 Prefill 带回 D。
7. 正确性要求结果、状态、可见性、资源守恒与 SLO 记账同时成立。
