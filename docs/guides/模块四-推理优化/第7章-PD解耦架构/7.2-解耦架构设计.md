## 1. 解耦的共同骨架

把各系统的差异剥掉，P/D 解耦通常长这样：

```mermaid
graph LR
    Q["请求进入"] --> P["Prefill 池<br/>算力型配置"]
    P -->|传输 KV Cache| D["Decode 池<br/>带宽/容量型配置"]
    D --> O["流式输出 Token"]
```

共通组件：

1. **阶段分离**：Prefill 与 Decode 不再争夺同一步；
2. **KV 交接**：Prefill 产物（KV Cache）必须送到 Decode 侧；
3. **独立扩缩**：两池可按各自瓶颈配不同 GPU 数甚至不同型号；
4. **SLO 导向调度**：按 TTFT/TPOT 约束分配到哪一池、是否接纳。

🔑 **核心概念**：**解耦的本质不是"多开几个服务"，而是"用 KV 传输换取阶段隔离与资源异构优化"。**

## 2. DistServe：为 Goodput 论证解耦

**DistServe（OSDI'24）** 是理解解耦动机的关键论文之一。它系统化论证：

- 混合服务下，满足双 SLO（TTFT + TPOT）的**有效吞吐（Goodput）**会被互扰严重伤害；
- 将 Prefill/Decode 拆开后，可以为两阶段选择不同并行策略与批次，提高 Goodput；
- 调度与放置需要显式面向 SLO，而不是只盯 GPU 利用率。

对工程读者，DistServe 留下的不是某一固定开源二进制，而是三句可迁移结论：

1. 优化目标应切到 Goodput；
2. P/D 需要不同资源与并行度；
3. 解耦后调度复杂度上升，但换来双 SLO 可达区扩大。

📌 **关键点**：读 DistServe 时抓住 **Goodput 与解耦的因果关系**，它直接决定你后面怎么做容量规划。

## 3. Splitwise：池化与阶段放置

**Splitwise（ISCA'24）** 强调在集群层面把机器组织成不同阶段池：

- Prefill 池偏向高算力；
- Decode 池偏向能撑住大量 KV 与稳定带宽的配置；
- 请求在 Prefill 完成后迁移到 Decode 池继续生成。

它把"异构硬件 / 异构配置"推到前台：既然两阶段瓶颈不同，就不必用同一型号 GPU、同一 TP 度去伺候两者。这对云上混部、老新GPU 混用很有启发。

💡 **提示**：即便两池都用同型号卡，**池大小比例、并发上限、并行度**仍应按阶段分开调——异构是可选项，分池是必选项。

## 4. TaiChi：聚合与解耦的统一

完全解耦不是免费的：KV 传输、调度状态机、池配比都会带来成本。**TaiChi** 一类工作探索的是：

- 何时应聚合（同实例混合，省传输）；
- 何时应解耦（隔离互扰，保 SLO）；
- 能否在统一框架下随负载切换或并存。

这对生产很重要：流量日夜变化，白天交互式 Decode 多、夜间长文档 Prefill 多，**静态二选一**往往不是最优。统一框架的价值在于提供策略空间，而不是宣称"永远解耦"。

⚠️ **注意**：统一框架通常更复杂。若团队还没有稳定的观测与 SLO 体系，先把"固定解耦 / 固定聚合"之一做对，再考虑自适应。

## 5. Microserving：跨引擎编排

**MLC Microserving** 等路线从"服务组合"角度看问题：Prefill、Decode 乃至其它组件可以是不同引擎实例，通过标准化接口编排。

启示：

- 解耦不必绑定单一代码树内部调度；
- 可以用网关/控制器把请求阶段化；
- 更适合多团队、多后端（不同推理引擎）共存的平台层。

代价是控制面更重：超时、重试、KV 传输失败、部分阶段降级都要有协议。

## 6. 对照与选型启示

| 系统/路线 | 强调重点 | 你可带走的实践 |
|---|---|---|
| **DistServe** | Goodput、双 SLO、阶段并行差异 | 改指标；分阶段调并行 |
| **Splitwise** | 池化放置、资源异构 | P 池/D 池分容量与机型 |
| **TaiChi** | 聚合↔解耦统一/自适应 | 按负载选择是否解耦 |
| **Microserving** | 跨引擎编排 | 平台层阶段化接口 |

落到当前开源生态（如 vLLM Disaggregated Prefill）：你通常会看到 DistServe/Splitwise 的骨架——P 实例、D 实例、KV Connector——再叠加工程化的传输后端与调度。细节见 7.3 与 7.6。

```text
选型问句：
1) 双 SLO 是否同时很紧？ → 是则倾向解耦
2) KV 传输带宽是否够？ → 不够则先优化同引擎调度
3) 负载是否长期稳定可分池？ → 稳定则固定解耦，波动大则考虑统一/自适应
```

## 7. 从论文到工程的最小落地地图

读完四条路线，落地时不要同时开四条线。推荐一条收敛路径：

1. **对齐目标**：先把 Goodput 与双 SLO 写成可测门禁（DistServe 的遗产）。
2. **固定拓扑**：P 池 + D 池 + KV 通道（Splitwise 的骨架），先同型号 GPU 也没关系。
3. **打通传输**：选一个 Connector 后端，用真实 Prompt 长度测传输 P95（见 7.3）。
4. **再谈自适应**：聚合/解耦切换或跨引擎编排，等前三步稳定后再做（TaiChi / Microserving）。

一张对照表帮助你避免"名词驱动架构"：

| 你真正缺的能力 | 优先借鉴 |
|---|---|
| 指标与调度目标错了 | DistServe |
| 不会分池、不会按阶段配资源 | Splitwise |
| 日夜负载结构差很大 | TaiChi 类统一/自适应 |
| 多引擎/多团队平台化 | Microserving |

📌 **关键点**：开源引擎里的 Disaggregated Prefill，本质上是把上述骨架产品化。先会画骨架、会测 Goodput，再去对齐具体旗标，学习曲线会短很多。

下一节开始钻工程硬骨头：KV 怎么传、带宽账怎么算；再往后才是 Goodput 调度、配比与 vLLM 实战。

## 📝 总结

- P/D 解耦的共通骨架是：**分池计算 + KV 交接 + 独立扩缩 + SLO 调度**。
- DistServe 把目标推到 Goodput；Splitwise 强调池化与异构放置；TaiChi 关注聚合/解耦统一；Microserving 走向跨引擎编排。
- 解耦用传输与控制面复杂度，换取互扰隔离和资源匹配。
- 工程上先判断双 SLO、带宽与负载稳定性，再决定固定解耦还是保留聚合路径。
