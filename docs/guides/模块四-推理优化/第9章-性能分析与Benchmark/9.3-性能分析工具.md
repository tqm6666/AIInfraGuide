## 1. 问题：相关轨迹为什么不是根因
观察到“TTFT 变差时 GPU 利用率升高”，最多说明二者同时发生。更高 offered load、长输入比例、Cache 命中下降、CPU 调度、失败重试或 Profiler 扰动都可能同时推高两者。

根因结论需要回答反事实：

> 如果只改变被怀疑的机制，其他合同不变，用户指标是否按预测方向变化？

性能分析的目标不是收集更多指标，而是逐步排除竞争解释。

---

## 2. 统一基准合同
诊断必须从有效 Benchmark 出发。本节沿用[第 9 章总览](/AIInfraGuide/inference/模块四-推理优化/第9章-性能分析与benchmark/第9章-性能分析与benchmark/)的 \(C=(W,S,Q,M)\)。

### 2.1 Workload \(W\)
- 60% \((512,128)\)、30% \((2048,256)\)、10% \((8192,512)\)；
- 开环 Poisson 和 \(0.25,0.5,0.75,1.0,1.25\times\lambda_{ref}\) 五个名义强度，配对重放计划 Manifest；
- 服务端在途上限 256；
- 冷 Prefix Cache 主实验，80% 命中率热缓存独立分析。

### 2.2 System \(S\)
- 同一约 8B 模型、权重、Tokenizer、Chat Template 与解码配置；
- BF16、TP=1；
- 同一专用单机与同一张 80 GiB GPU；
- CPU、内存、驱动、运行时、功耗及时钟策略冻结。

### 2.3 Quality / SLO \(Q\)
$$
TTFT\le500\,ms,\quad TPOT\le40\,ms,\quad E2E\le25\,s
$$

硬超时 30 s，协议有效率至少 99.9%，candidate 任务分数下降不超过 0.5 个百分点；两项构成数据集级质量门。
质量门通过后，Goodput 只计成功且满足所有适用请求级 SLO 的请求，每点聚合目标为 \(A_{joint}\ge95\%\)。

### 2.4 Measurement \(M\)
- 客户端事件定义用户结果；
- 每点至少五次独立重复，baseline/candidate 运行级配对；
- 预声明停止规则，报告 95% 置信区间并保留原始事件；
- 有 Profiler 运行与无 Profiler 性能运行严格分开。

诊断可缩短采集窗口，但必须从统一负载选择预声明的代表片段，不能另造一个更容易支持假设的工作负载。

## 3. 现象—假设—干预—证据
### 3.1 现象
现象是最小测量描述。合格写法：

> 在冷 Prefix Cache、L5、相同配对到达序列下，candidate 的 TTFT P95 和联合 Goodput 相对 baseline 恶化。

“candidate 的 Scheduler 太慢”不是现象，它已把原因塞进描述。现象应绑定合同版本、负载与缓存组、指标总体、差异方向、不确定性，以及失败和质量有效性。

### 3.2 假设
可证伪假设至少包含：

```text
候选原因：哪个机制变化
作用路径：它如何进入关键路径
可观察预测：成立时还应看到什么
反证条件：看到什么就降低置信度
```

例如：

> candidate 在 L5 把长 Prefill 组织成更大的连续工作块，令后到 Decode 请求等待；若成立，TTFT 尖刺应与 Queue Span 和长 Prefill 区间对齐，而同 Shape 的核心 Kernel 不应普遍变慢。

### 3.3 干预
干预是主动改变被怀疑机制，不是继续观察相关指标。理想干预只改一个变量，保持 Manifest、到达序列、环境、模型和质量路径不变，提前声明预期方向，同时观察目标与护栏，最终在关闭 Profiler 后重复。

干预可以是恢复一个调度策略、固定一个动态 Shape、禁用一个新融合路径、改变一个队列优先级，或对同一 Kernel 固定相同输入做微观对照。

### 3.4 证据强度
证据可由弱到强排列：
1. 指标同时变化；
2. 时间上对齐；
3. 有机制解释；
4. 排除主要混杂；
5. 受控干预产生预测结果；
6. 恢复干预使现象再次出现；
7. 无 Profiler 的端到端结果复现。

单次相关 Trace 通常只到第 2 或第 3 级，不能使用第 7 级的结论语言。

## 4. 从客户端到 Kernel 的四层时间线
### 4.1 客户端层
```text
计划到达 → 实际发送 → 首Token → 中间Token事件 → 末Token → 协议完成
```

它提供 TTFT、ITL/Chunk gap、TPOT、E2E、失败、实际长度和联合 SLO，决定“用户是否真的变慢”。

### 4.2 服务层
```text
入口接收 → 解析/Tokenize → 等待队列 → 被调度
         → Prefill/Decode → Detokenize → 流式发送 → 完成
```

它提供阶段 Span、队列深度、运行请求数、KV Cache 状态和调度决策，把客户端现象缩小到候选阶段。

### 4.3 CPU/GPU 系统层
```text
CPU：调度、锁、序列化、CUDA调用、线程运行/等待
GPU：Kernel、Memcpy、Stream、同步、通信、空洞
```

这一层回答“谁在等待谁”，强调重叠与关键路径，而不是事件排行榜。

### 4.4 Kernel 层
```text
Shape、dtype、调用次数、时长、FLOP、字节流量、占用与停顿
```

它回答某个已被证明重要的 Kernel 为什么受限；没有上层证据时，精细 Kernel 分析容易回答错问题。

### 4.5 时间对齐
跨层至少需要 run ID、请求/采样请求 ID、step ID、rank/device、同机单调时间、共同标记和映射误差。多进程单调时钟不一定共享零点，不同主机墙钟也有同步误差，不能制造纳秒级假精确。

## 5. 服务时间线与 Queue
设到时刻 \(t\) 为止，\(A(t)\) 是到达数，\(D(t)\) 是完成数，\(R(t)\) 是拒绝或终止数，\(Q(t)\) 是系统内请求数：

$$
Q(t)=Q(0)+A(t)-D(t)-R(t)
$$

若 \(A\) 长期快于 \(D+R\)，积压必然增加；吞吐仍可保持平台，TTFT 却继续恶化。

对请求 \(r\)，Queue Span 和调度后服务时间可写为：

$$
W^{queue}_r=t^{scheduled}_r-t^{enqueued}_r
$$

$$
S_r=t^{done}_r-t^{scheduled}_r
$$

客户端 E2E 还含入口前和完成后的链路。若 TTFT 上升主要来自 \(W^{queue}\)，直接优化 Kernel 不一定改变用户结果。

三组组合用于选路：
- Queue 非空 + GPU 连续忙：可能是容量不足或工作量增加；
- Queue 非空 + GPU 长空洞：更支持 CPU、同步、数据准备或通信依赖；
- Queue 为空 + GPU 空洞：可能只是负载不足。

这些不是根因证明。统一负载还应研究条件分布：

$$
F_{W^{queue}\mid L,\lambda,cache}(w)
$$

否则长输入对后到短请求的阻塞会被混合总体掩盖。

## 6. CPU 时间线
CPU 常承担请求解析、Tokenize/Detokenize、调度、KV Block 管理、Batch 构造、Kernel 发射、序列化、网络和后台维护。

线程状态需要区分：
- Running：正在 CPU 上执行；
- Runnable：可运行但等 CPU；
- Sleeping/Blocked：等锁、I/O、条件变量或同步。

GPU 空洞期间，三种状态支持不同假设。

典型 CPU launch-bound 形态：

```text
CPU: [prepare][launch k1]---gap---[launch k2]---gap---[launch k3]
GPU:              [k1]__idle__[k2]__idle__[k3]
```

支持该假设还需要 Queue 非空、空洞与发射间隔对齐、Kernel 本身未普遍变慢、主线程状态可解释，并且减少 CPU 路径后空洞按预测缩小。仅看到“很多短 Kernel”不够。

总 CPU 利用率也会误导：64 核主机上一个关键线程满核，总利用率仍很低；高总利用率也可能来自非关键后台工作。必须回到线程和时间对齐。

---

## 7. GPU 时间线
GPU 时间线先看工作与空洞关系，再看 Kernel 名称。

### 7.1 连续忙
```text
[prefill][decode][decode][prefill][decode][decode]...
```

Queue 非空且 GPU 无空洞时，可能是工作量增加、Batch/Shape 变大、重算、单 Kernel 变慢、通信进入关键路径或时钟下降。“GPU 100%”不能区分这些解释。

### 7.2 空洞
```text
[kernel]____idle____[kernel]________idle________[kernel]
```

可能来自 CPU 未发射、同步、数据未就绪、跨进程通信、输入不足或观测扰动；只有 Queue 非空时，空洞才更像供给链问题。

### 7.3 重叠
多 Stream、Memcpy、计算和通信可能并行，所以：

$$
\sum_j duration(kernel_j)\neq wall\ clock
$$

总 Kernel 时间描述工作量，墙钟时间由依赖图关键路径决定。

统一基准默认 TP=1，主例不引入 NCCL。若做分布式敏感性实验，必须建立新合同，不能把多卡 Trace 混入单卡结论。

## 8. Kernel 与 Roofline
只有系统时间线证明某个 Kernel 位于关键路径，才需要微架构模型。

设 Kernel 完成 \(F\) 次浮点运算，从目标内存层级搬运 \(B\) 字节，算术强度：

$$
I=\frac{F}{B}\quad [FLOP/Byte]
$$

硬件峰值计算吞吐为 \(P_{peak}\)，目标内存带宽为 \(BW\)，Roofline 上界：

$$
P\le\min(P_{peak},I\cdot BW)
$$

转折算术强度：

$$
I^*=\frac{P_{peak}}{BW}
$$

\(I<I^*\) 时带宽屋顶更低，\(I>I^*\) 时计算屋顶更低。但 Roofline 是上界，不是自动诊断；点远低于屋顶还可能来自访存不合并、复用不足、Occupancy、指令依赖、分支、小 Shape 或同步空泡。

baseline/candidate 比较前必须对齐语义工作、Shape、dtype、布局、融合边界、调用阶段、次数、GPU 时钟和采集集合。若三个 Kernel 融成一个，应比较同一语义区域及其关键路径，而非名称。

## 9. Memory-bound 与 compute-bound
memory-bound 必须指明 HBM、L2、Shared Memory、地址转换或 Host-device 等层级。高 HBM 吞吐接近可持续上限且计算单元仍有余量，才支持 HBM-bound。

compute-bound 也不是“GPU 很忙”，而是关键工作接近相关计算管线的可持续能力；Tensor Core、标量、特殊函数、转换和控制流有不同屋顶。

长 Prefill 的大矩阵运算常有较高算术强度，小 Batch Decode 常反复读取权重和 KV Cache，所以常见起始假设是：

```text
Prefill 更可能偏计算受限
Decode 更可能偏内存带宽受限
```

Batch、量化、融合、上下文和硬件都会改变结论，经验不能替代实测。瓶颈还可随负载切换：L1 可能受 CPU 固定开销，L3 通过 Batch 提高 GPU 效率，L5 由 Queue/KV 压力主导。

## 10. 关键路径与反事实
执行可看作依赖图 \(G=(V,E)\)，墙钟下界由最长依赖路径决定：

$$
T_{critical}=\max_{p\in Paths(G)}\sum_{v\in p}duration(v)
$$

优化完全重叠的非关键事件可能不改变 E2E。调度器也可让 GPU 始终有工作，却使部分请求长期等待，所以“消除 GPU 空洞”必须配合请求级 SLO。

若假设是“长 Prefill 阻塞 Decode”，应提前写出预测：
- 尖刺与长 Prefill 重合；
- Queue 非空；
- 同 Shape Decode Kernel 时长近似不变；
- 只切分 Prefill 后尖刺缩小；
- 若尖刺时没有 Prefill或 Kernel 同步变慢，则原假设受反证。

先写预测再看时间线，能减少事后讲故事。

## 11. Profiler 的 observer effect
Profiler 会记录事件、调用栈、Shape 和计数器，也可能写缓冲、重放 Kernel、强制同步或改变热路径。概念上：

$$
T_{observed}=T_{native}+\Delta_{direct}+\Delta_{behavior}
$$

\(\Delta_{behavior}\) 会改变 Batch、Queue 和重叠，不是能从总时间简单扣除的常数。

无 Profiler 性能运行用于五点 TTFT、TPOT、E2E、吞吐与 Goodput 正式比较；有 Profiler 诊断运行只采足以验证假设的短窗口，baseline/candidate 使用相同条件，并单独量化扰动。

可定义总时长扰动比：

$$
\eta_{obs}=\frac{T_{profiled}-T_{native}}{T_{native}}
$$

但还要检查 Shape、Batch、Queue 和失败是否改变；总时长只变 2%，尾部结构也可能已被改变。

侵入性应逐级增加：无侵入客户端/服务事件 → 轻量阶段与资源序列 → 短系统时间线 → 框架算子/Shape → 少数关键 Kernel 计数器。每一级都由上一层假设驱动。

## 12. 统一算例
沿用 9.1、9.2 的教学数据。到达窗口 100 s、观测窗口 130 s，\(\lambda_{ref}=4\) req/s。
五个 Manifest 全部按计划送达，两套系统均通过数据集级质量门；表中“合格”为请求级联合 SLO 合格。

| 点 | baseline 成功/合格 | candidate 成功/合格 |
|---|---:|---:|
| L1 | 102 / 100 | 102 / 100 |
| L2 | 197 / 192 | 197 / 193 |
| L3 | 301 / 280 | 302 / 288 |
| L4 | 382 / 309 | 387 / 322 |
| L5 | 401 / 212 | 396 / 198 |

| 点 | baseline TTFT P95 / TPOT P95 | candidate TTFT P95 / TPOT P95 |
|---|---:|---:|
| L1 | 220 ms / 31 ms | 210 ms / 30 ms |
| L2 | 260 ms / 33 ms | 245 ms / 31 ms |
| L3 | 340 ms / 36 ms | 315 ms / 34 ms |
| L4 | 520 ms / 42 ms | 470 ms / 38 ms |
| L5 | 1100 ms / 58 ms | 1250 ms / 60 ms |

### 12.1 现象
candidate 在 L3、L4 的合格数更高：

$$
288>280,\qquad322>309
$$

但 L5：

$$
198<212
$$

且 candidate TTFT P95 从 L4 的 470 ms 增至 L5 的 1250 ms。诊断问题应限定为高负载退化，而非“candidate 全面变慢”。

### 12.2 先排除合同差异
配对运行必须使用相同 Poisson 序列、三类长度 Manifest、冷 Prefix Cache、模型与实际输出记录、100/130 s 窗口、256 在途上限、质量和失败语义；任何一项不一致，都应先修复实验而不是解释 Trace。

### 12.3 异常请求切片
在同一 \((8192,512)\) 桶中取一个 P95 附近的教学请求：

```text
                    baseline    candidate
入口与解析             30 ms        30 ms
Queue                 620 ms       870 ms
Tokenize               20 ms        20 ms
调度后至首Token         410 ms       500 ms
客户端TTFT            1080 ms      1420 ms
```

这是教学切片，不替代运行级分布；新增 340 ms 中 Queue 增量为 250 ms，只提示首要假设。

### 12.4 竞争假设
- H1：candidate 的长 Prefill 调度块在 L5 增大，阻塞后到请求；
- H2：核心 Prefill Kernel 在相同 Shape 下变慢；
- H3：CPU 调度线程在高负载出现发射空洞；
- H4：客户端流式消费变慢，放大 TTFT。

先看服务层 Queue 与长 Prefill 是否对齐，再看 Queue 非空时 GPU 是否连续忙、空洞是否对齐 CPU 发射，最后才在工作和 Shape 相同后看 Roofline 与 Kernel。

### 12.5 干预判定
若只恢复被怀疑的 Prefill 切分策略，并重放同一 L5 序列，H1 预测 Queue 和 TTFT 尖刺缩小，同 Shape Kernel 时长不必改变，无 Profiler 的 L5 Goodput应恢复，而 L1—L4 的吞吐、TPOT、质量与错误率不能退化。

若 Queue 不变或无 Profiler 结果不恢复，H1 应被削弱。证据完成前只能写：

> canonical L5 中 candidate 的退化主要出现在 TTFT 与联合 Goodput；单请求切片显示 Queue 增量，是待干预验证的首要假设。

不能写“Prefill Scheduler 已被证明是根因”。

## 13. 常见陷阱
- **资源利用率直接命名瓶颈**：GPU 活跃不等于 compute-bound，高显存占用不等于 memory-bound。
- **最长事件等于关键路径**：长 Kernel 若完全重叠，缩短它未必改变用户延迟。
- **先抓最重采集**：高侵入采集可能改变原始现象，应由假设选择最小证据。
- **不同 Shape 比 Kernel**：单次变长可能只是输入更大，调用次数和工作量都要对齐。
- **Queue 上升归因 Scheduler**：offered load 超过能力也会增队列。
- **用 Profiler TTFT 更新基准**：正式结果必须来自关闭 Profiler 的独立运行。
- **把经验当事实**：“Prefill compute-bound、Decode memory-bound”只是常见起点。
- **相关后停止干预**：时间对齐不能排除共同原因，可逆干预才更接近因果。

---

## 14. 结论边界
性能分析可把“L5 更差”缩小为排队、CPU 供给、GPU 工作量/时钟、同步或特定 Kernel 问题，却不能凭一次 Trace 证明普遍因果。结论须限定模型、长度、负载、缓存、系统和采集条件；优化是否兑现，最终由无 Profiler 的客户端 Goodput—offered-load 曲线决定。

---

## 总结
- 因果分析以“现象—假设—干预—证据”为主线，时间相关只是中间证据。
- 客户端、服务、CPU/GPU 和 Kernel 四层要通过共同事件对齐并围绕关键路径解释。
- Queue 守恒和时间线判断积压位置，Roofline 约束已确认关键 Kernel 的瓶颈模型。
- Profiler 会改变 Batch、Queue 和重叠，诊断运行不能替代无 Profiler 的正式结果。
