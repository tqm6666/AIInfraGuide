## 1. 压测前要钉死的变量

每次对比实验至少固定：

| 变量 | 示例 |
|---|---|
| 模型与精度 | 权重路径、量化方式、Tokenizer |
| 硬件与拓扑 | GPU 型号、数量、TP/PP、驱动/CUDA |
| 引擎版本与关键 flag | vLLM 版本、chunked prefill、前缀缓存开关 |
| 负载形状 | 输入/输出长度分布、到达过程、是否流式 |
| 采样参数 | Temperature、max tokens、stop |
| 预热与正式窗 | warmup 请求数、测量时长、种子 |

📌 **关键点**：改了一个 flag 却同时换了数据集，结论作废。一次只动一个自变量；报告里写清「动了什么」。

## 2. 负载画像、预热与并发阶梯

### 2.1 负载画像（Workload Profile）

没有画像，数字不可比。最少声明：

- **长度分布**：固定 `(L_in, L_out)` 或分位数（P50/P95 Prompt 长度）；
- **到达过程**：泊松到达 / 固定 QPS / 闭循环并发（闭环会隐藏排队）；
- **前缀复用率**：系统提示是否重复（决定 Prefix Cache 是否「白送」）；
- **流式 vs 非流式**：TTFT/ITL 定义依赖流式。

推荐三层场景：

1. **微观基线**：固定长度，并发=1，测延迟底座；
2. **饱和曲线**：阶梯抬高到达率/并发，找 SLO 拐点；
3. **业务混合**：按线上长度与复用率回放（脱敏 trace）。

### 2.2 预热（Warmup）

正式窗口前必须消化：

- CUDA/引擎编译与图捕获；
- 权重与缓存页分配；
- Prefix / 编译缓存填充（若测稳态命中，预热要包含同类前缀）。

预热不足的典型假象：第一次跑「很慢」，第二次「优化了 30%」——其实只是冷启动结束。

### 2.3 并发阶梯

不要只报一个「最大吞吐点」。建议：

```text
request_rate 或 concurrency = [1, 2, 4, 8, 12, 16, ...]
每个点：warmup → 稳态测量 ≥ N 请求或 T 秒 → 记录 TTFT/TPOT P95、吞吐、错误率
```

```mermaid
flowchart LR
    A["低负载基线"] --> B["阶梯抬高到达率"]
    B --> C["记录 P95 与吞吐"]
    C --> D["SLO 拐点 = 有效容量"]
    D --> E["拐点以上只作压力观察"]
```

💡 **提示**：`request-rate`（开环到达）与「飞行中并发」（闭环）不是同一模型。要画饱和曲线，优先开环扫多个负载点；闭环适合摸客户端并发上限，但会掩盖服务端排队真相。

## 3. vllm bench 三件套

vLLM 提供面向不同问题的子命令（参数以当前版本 `--help` 为准）：

### 3.1 `vllm bench latency`

偏**单请求/低并发延迟**画像，适合看 TTFT/TPOT 基线、回归引擎改动对延迟的影响。

### 3.2 `vllm bench throughput`

偏**极限吞吐**，尽快打满引擎，回答「这张卡最高能吐多少 Token/s」。适合容量上界与 kernel/图优化对比——**不能单独当产品验收**。

### 3.3 `vllm bench serve`

对已拉起的 OpenAI 兼容服务做在线压测，输出更贴近生产的 QPS、TTFT、TPOT、吞吐等。适合发布前验收、配置调优、单副本摸高。

```bash
# 概念示例：对本地服务做 serve 压测（参数随版本调整）
vllm bench serve \
  --backend vllm \
  --model <model-name> \
  --host 127.0.0.1 \
  --port 8000 \
  --dataset-name sharegpt \
  --num-prompts 1000 \
  --request-rate 8
```

对同一配置扫多个 `--request-rate`，才能得到 [9.1](./9.1-推理指标体系.md) 所需的负载前提曲线，而不是一张「峰值海报」。

## 4. GenAI-Perf 与其它工具

| 工具 | 特点 | 适用 |
|---|---|---|
| **GenAI-Perf** | NVIDIA 生态，TTFT/ITL/吞吐一站式 | Triton / NIM / 兼容端点对比 |
| Triton Perf Analyzer | 传统 Triton 模型分析 | 非 LLM 或 Triton 管道 |
| 自定义脚本 | 完全贴合业务 trace | 上线决策与回放 |

GenAI-Perf 的价值在于：**跨实现用同一套指标定义对话**，减少「我家 TTFT 和他家不是一个东西」。业务决选仍要靠生产形状回放；工具统一不等于场景同类。

## 5. 报告最小字段

一次可信压测报告至少包含：

| 字段 | 说明 |
|---|---|
| `benchmark_id` / 日期 / 执行人 | 可追溯 |
| 模型、精度、引擎版本、镜像 digest | 栈钉死 |
| 硬件：GPU 型号、数量、TP/PP、驱动/CUDA | 环境钉死 |
| 关键 flag：缓存、chunked prefill、图、投机等 | 自变量清晰 |
| 负载画像：数据集、长度、到达率阶梯、流式 | 场景钉死 |
| 采样：temperature、max_tokens、seed | 随机性可控 |
| warmup / 正式窗时长或请求数 | 冷热分离 |
| **结果表**：每负载点的 TTFT/TPOT(ITL) P50/P95、tok/s、错误率、（可选）Goodput | 曲线而非单点 |
| 客户端与网络备注 | 排除假瓶颈 |

示例结果行（教学示意）：

```text
rate=8 req/s | TTFT P95=720ms | TPOT P95=28ms | tok/s=2050 | err=0.0%
rate=12     | TTFT P95=1100ms | TPOT P95=35ms | tok/s=2400 | err=0.2%
SLO: TTFT P95≤800ms → 有效容量落在 8 与 12 之间，取 8 为发布口径
```

取舍句：**rate=12 的 tok/s 更高，但已破 TTFT SLO**——若只报峰值吞吐，会把超卖点写成「最优配置」。

🔑 **核心概念**：报告的最小交付物是**带负载阶梯的曲线 + 配置四元组**，不是一张最大 tokens/s 截图。

## 6. 可复现配置管理

把一次基准固化为机器可读清单：

```yaml
benchmark_id: chat-7b-fp8-2026-08-10
model: org/model-7b-fp8
engine: vllm==x.y.z
image_digest: sha256:abc...
flags:
  max_model_len: 8192
  enable_prefix_caching: true
  gpu_memory_utilization: 0.9
hardware:
  gpu: H100-80GB
  tp: 1
workload:
  dataset: sharegpt_v3_sample
  num_prompts: 1000
  request_rate: [1, 2, 4, 8, 12]
  streaming: true
sampling:
  temperature: 0.0
  max_tokens: 256
warmup_requests: 50
seed: 42
```

配套要求：

- 结果 JSON/CSV 与配置同目录归档；
- 复跑对比 diff，而不是只看截图；
- 记录驱动、CUDA、容器 digest。

**可复现 = 配置 + 数据 + 环境 + 种子** 四元组，缺一不可。

## 7. 常见误区与反作弊

| 作弊/误区 | 为何失真 | 纠正 |
|---|---|---|
| 只报最大值吞吐 | 隐藏破 SLO 的超卖点 | 强制阶梯 + P95 |
| 预热计入正式窗 | 冷启动污染 | 分离 warmup |
| 流式/非流式混比 | TTFT 定义漂移 | 标明并分桶 |
| Temperature>0 且不修种子 | 随机当回归 | 性能对比用 0 或固定 seed |
| 客户端成瓶颈 | 冤枉引擎 | 先确认压测机 CPU/网卡 |
| 换数据集却称同场景 | 长度分布偷换 | 一次一自变量 |
| 无缓存流量对高命中业务 | 低估或高估可迁移性 | 画像写清复用率 |

⚠️ **注意**：客户端与网络可能成为瓶颈。先确认压测机不是短板，再给引擎下结论；门禁与发布口径见 [9.5](./9.5-性能回归门禁.md)。

## 8. 代价与权衡

| 选择 | 收益 | 代价 / 不适用 |
|---|---|---|
| 完整并发阶梯 | 找到真实有效容量 | 时间更长 |
| 只跑 throughput 峰值 | 快、好看 | 不能做产品验收 |
| 公开 ShareGPT 对比 | 横向可聊 | 不等于你的线上分布 |
| 生产 trace 回放 | 上线决策可信 | 脱敏与维护成本 |
| 极长正式窗 | 方差更小 | CI 变慢，需分层（[9.5](./9.5-性能回归门禁.md)） |

适用：已按 [9.1](./9.1-推理指标体系.md) 写清 SLO 与目标函数。  
若目标仍是「海报上的最大 tok/s」，任何工具都会帮你自欺。

## 📝 总结

- 压测前固定模型、硬件、版本、负载与采样；一次只动一个自变量。
- **负载画像 + 预热 + 并发阶梯**是可信基准的三块底板。
- `latency` / `throughput` / `serve` 分别回答基线延迟、上限吞吐与在线综合表现；峰值吞吐不能单独验收。
- 报告最小字段包含配置四元组与每负载点的 P95/吞吐/错误率。
- GenAI-Perf 统一指标对话；业务决选靠生产形状回放。
- 反作弊优先于工具品牌：分离冷热、禁止混比、排除客户端瓶颈。

## 🎯 自我检验清单

- 能说明三次 `vllm bench` 子命令各自回答什么问题
- 能区分 request rate 与并发飞行数，并说明为何要阶梯扫描
- 能列出预热要消化的至少三类冷启动成本
- 能写出报告最小字段清单，并解释为何不能只报峰值
- 能设计「基线—饱和—混合」三层压测
- 能点名至少四个导致基准不可信的误区/作弊点
