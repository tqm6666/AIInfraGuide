提示词可以要求模型“只输出固定结构”，却不能证明下一次生成一定守约。
结构化输出把愿望变成运行时约束：每产生一个 Token 前，系统先计算哪些 Token 仍可能通向合法终局。
本节沿用[第 8 章总览](/AIInfraGuide/inference/模块四-推理优化/第8章-生产级服务特性/第8章-生产级服务特性)的统一请求合同 $\mathcal R=(I,M,D,P,S)$，只追踪租户 `ops-a` 的值班 Agent。
它要检查 `gpu-prod`；本节只研究工具参数和最终结论的结构怎样约束生成，不讨论工具执行闭环。

## 1. 问题：提示词不是硬合同

`ops-a` 的最终阶段要提交三个业务字段：
- 集群只能是 `gpu-prod`；
- 状态只能取 `healthy`、`degraded` 或 `down`；
- 摘要必须是长度受限的字符串。

提示词只能提高守约概率，仍可能在结构前加解释、漏结束括号、拼错枚举、生成额外字段，或在对象完成前耗尽预算。
生成后修复也不等价：修复器可能猜错模型原意，并把“合同失败”伪装成正常成功。

生产系统需要的是：
$$\Pr(Y\in\mathcal L_D\mid\text{正常接受结束})=1$$
$Y$ 是提交输出，$\mathcal L_D$ 是合同 $D$ 允许的字符串集合。
这只承诺形式合法，不承诺内容真实。

五元合同在这里分别承担：
- $I$：模型看到的 `gpu-prod` 请求及上下文；
- $M$：模型、Tokenizer、模板和 `ops-diagnosis@17` Adapter；
- $D$：允许的输出语言与结束条件；
- $P$：在合法候选中选择 Token 的策略；
- $S$：编译、排队和逐 Token 约束的时限与配额。

结构化输出主要落实 $D$，但它依赖 $M$ 中的 Tokenizer，也会改变 $P$ 的支持集并消耗 $S$。

## 2. 把输出合同写成语言

### 2.1 语言不是一份示例

形式语言是字符序列的集合：
$$\mathcal L(G)=\{y\mid y\text{ 可由约束 }G\text{ 生成}\}$$
一份示例只展示集合中的一个元素；Grammar、正则或可编译结构规则描述整个集合。

对 `ops-a`，最终对象的核心形状可抽象为：
```text
object  := "{" cluster "," status "," summary "}"
cluster := '"cluster":"gpu-prod"'
status  := '"status":"' ("healthy" | "degraded" | "down") '"'
summary := '"summary":"' safe-char{1,120} '"'
```
这是教学 Grammar，省略了转义和空白细节。
生产约束必须明确这些细节，否则“看起来一样”的字符串可能属于不同语言。

### 2.2 表达能力有层次

有限候选和许多正则模式属于正规语言，可用有限状态自动机处理。
任意嵌套括号需要记住深度，通常还要解析栈，接近上下文无关语言与下推自动机。
结构规则还可能维护有限业务形状状态：
- 哪些必填字段尚未出现；
- 数组已经生成多少项；
- 当前是否位于字符串转义中；
- 某个枚举还剩哪些可能前缀。

“自动机”在工程语境中常是统称。
完整实现可能组合词法器、解析栈、位集与有限状态，而不是一个小型纯 DFA。

### 2.3 语言条件不等于业务条件

“状态来自三个枚举”容易形式化。
“`gpu-prod` 当前确实故障”依赖外部事实，Grammar 无法判定。
“摘要不得泄漏任何密钥”也难靠字符语言完整表达。

最终验收至少分两层：
$$\mathrm{Accepted}=\mathrm{SyntacticallyValid}\land\mathrm{BusinessValid}$$
受约束解码负责前一项，可信业务验证器负责后一项。

## 3. 从语言到自动机状态

### 3.1 完整句、活前缀与死前缀

生成逐步进行，系统不能只在结束时判断成员关系。
定义语言的前缀闭包：
$$\operatorname{Pref}(\mathcal L)=\{s\mid\exists u,\;su\in\mathcal L\}$$

已生成前缀 $s$ 有三种状态：
1. **接受状态**：$s\in\mathcal L$，此刻允许正常结束；
2. **活前缀**：$s\notin\mathcal L$，但 $s\in\operatorname{Pref}(\mathcal L)$；
3. **死前缀**：$s\notin\operatorname{Pref}(\mathcal L)$，任何后缀都无法补救。

前缀 `..."status":"degr` 尚未完整，却仍是活前缀。
若只有三个枚举，前缀 `..."status":"broken` 就是死前缀。
受约束解码的核心是不让状态进入死前缀。

### 3.2 状态转移

字符级 DFA 的转移可写成：
$$q'=\delta(q,c)$$
对字符串 $w$，扩展转移记为 $\delta^*(q,w)$。

带解析栈的 Grammar 状态可抽象为：
$$g=(q_{\text{lexer}},q_{\text{parser}},\sigma,F)$$
$\sigma$ 是栈，$F$ 可表示尚未满足的字段集合。

最终可执行状态还必须包含增量 Detokenizer：
$$q=(g,\eta_{\text{detok}})$$
$\eta_{\text{detok}}$ 保存词首、空白清理、未完成 UTF-8/byte fallback 和特殊 Token 等会影响后续可见字节的状态。
运行时只需持有当前联合状态，不必保存全部推导历史。

### 3.3 EOS 也受约束

结束不是自动合法的：
$$\mathrm{EOS}\in A(q)\iff g\in F_{\text{accept}}\land\operatorname{FlushOK}(\eta_{\text{detok}})$$
活前缀尚未闭合时，提前 EOS 必须被屏蔽。
即使 Grammar 已接受，Detokenizer 中仍有未完成字节或结束时还会产生额外可见字符，也不能正常提交。
达到接受状态后，停止策略还要决定立即提交还是允许合同内的后续字符。

`max_tokens` 用尽与到达接受状态不是同一件事。
前者只能返回“截断或合同未完成”，不能把合法前缀冒充完整对象。

## 4. 从字符合法到 Token 合法

### 4.1 必须消费完整 Token

模型词表记为 $V$。
一个 Token 可能是标点、多个字母、前导空白加单词、跨 Grammar 边界的一段文本，或 UTF-8 的 byte fallback。
因此只检查第一个字符并不正确。

更重要的是，Token 的可见输出不一定是无状态映射。
WordPiece 的续词前缀、Metaspace 的句首处理、清理规则和跨 Token byte fallback 都可能依赖已有前缀。
定义增量解码步骤：
$$
\operatorname{Step}_M(\eta,v)=(\eta',b,\kappa)
$$
$b$ 是本步新产生的可见字节，$\kappa$ 是 EOS、控制或普通内容等 Token 语义。
联合转移为：
$$
\Delta((g,\eta),v)=
\begin{cases}
(\delta^*(g,b),\eta'),&\kappa\text{ 合法且联合状态仍是活状态}\\
\bot,&\text{否则}
\end{cases}
$$

当前状态的允许集合为：
$$A(q)=\{v\in V\mid\Delta(q,v)\neq\bot\}$$
$\bot$ 表示 Grammar、Detokenizer 或控制语义已经无合法终局。
对非确定或带栈解析器，右侧实际推进状态集合，但判断原则相同。

只有在已证明 Token 可独立、可组合地映射为原始字节时，才能把上式简化为：
$$A(g)=\{v\in V\mid\delta^*(g,D_M(v))\neq\bot\}$$
不能把普通的单 Token `decode(v)` 默认当成这种映射。

### 4.2 跨边界 Token

假设当前输出停在：
```text
..."status":"
```
词表中存在：
```text
"de"
"degraded"
"degraded\",\"summary\":\""
"down"
"debug"
```

前三个 Token 都可能合法；第三个甚至跨过枚举、分隔符和下一字段起点。
`"debug"` 与合法枚举共享前缀，却最终进入死状态，必须整体拒绝。

若约束器只允许与“下一个 Grammar 终结符”完全对齐的 Token，
它会错误删除跨边界 Token，迫使模型采用罕见分词。
这种错误叫**不完备**：输出仍可能合法，但模型概率和任务质量已被无谓扭曲。

### 4.3 Tokenizer 属于约束身份

同一字符 Grammar 搭配不同 Tokenizer，会产生不同 Token 集。
added token、特殊 Token、正规化、Decoder 配置和 byte fallback 都会改变结果。

编译缓存身份至少应包含：
```text
canonical constraint
+ tokenizer/vocabulary/decoder revision
+ special-token and control semantics
+ compiler semantics version
```
只按 Grammar 文本缓存，会把一个词表的 Mask 错用到另一个词表。

## 5. Token Mask 与生成循环

### 5.1 允许集合变成 Mask

将 $A(q_t)$ 编码为词表大小的 Mask：
$$m_t[i]=\begin{cases}1,&i\in A(q_t)\\0,&i\notin A(q_t)\end{cases}$$
模型产生原始 Logits $z_t$，硬约束后：
$$\tilde z_t(i)=\begin{cases}z_t(i),&m_t[i]=1\\-\infty,&m_t[i]=0\end{cases}$$

采样策略 $P$ 只能在 $\tilde z_t$ 的有限支持集上工作。
Temperature 能改变合法候选间的相对概率，却不能让被屏蔽 Token 复活。

### 5.2 逐 Token 循环

```text
读取 Grammar + Detokenizer 联合状态 q_t
 -> 计算或命中允许集合 A(q_t)
 -> 与其他硬约束求交
 -> 把非法 Logit 置为 -∞
 -> 按 P 选择 Token v_t
 -> 用 Step_M 和 Delta 原子推进联合状态
 -> Grammar 接受、Detokenizer 可安全结束且满足停止策略后提交
```

批处理中，每条序列有自己的 $q_t$。
即使共享 Grammar，也可能因输出前缀或 Detokenizer 缓冲不同而处于不同状态。
概念上的批 Mask 为：
$$M_t\in\{0,1\}^{B\times|V|}$$
实现不必物化完整二维布尔数组；位图、稀疏列表、Token trie 和状态索引都可保持同一语义。

8.1 对采样只规定一个不变量：
$$\operatorname{support}(P_t)\subseteq A(q_t)$$
合法集合内部怎样做 Greedy、Top-k 或随机采样，留到 8.5。

## 6. 编译期与运行期

### 6.1 编译期

编译期把高层合同变成可增量执行的表示：
1. 规范化约束并生成稳定身份；
2. 检查语法、引用和受支持语义；
3. 构建词法状态、解析表或自动机；
4. 建立 Token 字节 trie 或等价索引；
5. 预计算与上下文无关的 Token 判定；
6. 检查状态数、栈深和资源上限；
7. 将成功或确定性失败写入有界缓存。

若语言本身为空，应在编译期直接拒绝。
缓存键来自所有影响结果的身份：
$$K_c=H(D_{\text{canonical}},M_{\text{tokenizer}},V_{\text{compiler}},C_{\text{semantics}})$$

### 6.2 运行期

每条序列持有：
- 编译对象的只读引用；
- 当前自动机或解析栈状态及增量 Detokenizer 状态；
- 接受状态和停止状态；
- Mask 缓存索引或稀疏候选；
- 输出长度、截止时间与取消标志。

采样提交与状态推进必须一致，不能“选中 Token 但状态没推进”后继续。
取消请求时要释放引用和临时工作区，不能由已取消序列长期 pin 住缓存。

### 6.3 冷路径与热路径

延迟可拆为：
$$T=T_{\text{queue}}+\mathbf{1}_{\text{miss}}T_{\text{compile}}+T_{\text{prefill}}+\sum_{t=1}^{L}(T_{\text{decode},t}+T_{\text{mask},t}+T_{\text{advance},t})$$
冷请求多付一次编译；热请求仍支付 Mask、状态推进和可能的 CPU/GPU 同步。

高基数动态约束会降低命中率并放大 CPU、内存和 TTFT。
入口应限制约束字节、分支、枚举总长度、递归深度和编译并发。

## 7. ops-a 手算

假设 `ops-a` 已生成：
```text
{"cluster":"gpu-prod","status":"
```
词表大小为 $128\,000$，相关 Token 为：
```text
v1="healthy"   v2="degraded"   v3="down"
v4="de"        v5="debug"
v6="degraded\",\"summary\":\""  v7=EOS
```

完整字节推进后：
- $v_1$、$v_2$、$v_3$ 到达合法枚举尾部；
- $v_4$ 停在合法活前缀；
- $v_6$ 跨过多个语法片段，仍合法；
- $v_5$ 最终进入死状态；
- $v_7$ 在对象未完成时不合法。

局部 Mask 是：
```text
token  v1 v2 v3 v4 v5 v6 v7
mask    1  1  1  1  0  1  0
```

128K 词表按 1 byte/Token 存布尔值约为：
$$128\,000\text{ bytes}\approx125\text{ KiB/state}$$
按 bitset 存储约为：
$$128\,000/8\approx15.625\text{ KiB/state}$$

批中 32 个不同状态时：
```text
byte mask: 32 × 125 KiB     ≈ 3.91 MiB/step
bitset:    32 × 15.625 KiB  = 500 KiB/step
```
若输出 80 Token，byte mask 的逻辑处理量可超过 300 MiB。
这不等于发生同量 PCIe 传输；缓存、压缩、融合或 GPU 生成都会改变物理流量。

再假设冷编译 24 ms、热查找 0.2 ms，每 Token 约束链增加 18 $\mu$s。
80 Token 的热路径增量约为：
$$80\times18\ \mu s=1.44\text{ ms}$$
冷路径增量约为 $25.44$ ms。
这些数字只是容量演算，不是任何引擎的承诺。

## 8. 运行时成本

### 8.1 模型前向通常没有消失

Mask 常发生在完整词表 Logits 产生后。
即使合法候选只有三个，Transformer 和输出头通常仍先完成计算。
“候选更少”不自动等于模型 FLOPs 更少；主要收益可能来自减少格式重试或缩短输出。

### 8.2 CPU、GPU 与同步

CPU 可能承担约束规范化、编译、Token trie、状态推进、Mask 生成、缓存和最终验收。
GPU 可能承担全词表 Mask 应用、候选筛选与采样。
若 Mask 在 CPU 生成，搬运与 Host/GPU 同步会进入关键路径。

第 $t+1$ 步约束计算有时可与第 $t$ 步模型前向重叠。
重叠只能隐藏时延，不能消除 CPU、带宽和工作区成本。

### 8.3 Batch 兼容与表示选择

不同 Grammar 并非语义上不能共批，只要 Kernel 能接受每行独立 Mask。
性能却取决于：
- 批中唯一编译对象和运行状态数量；
- 宽、窄 Mask 表示是否混杂；
- CPU 能否及时提供下一步状态；
- 一个复杂约束是否拖慢整批同步。

窄状态适合稀疏允许列表，宽状态更适合位图或非法列表。
共享状态可复用只读 Mask；状态高度分散时复用率下降。

### 8.4 正确性和性能指标

至少分别观察：
- 编译成功率、耗时与失败原因；
- 缓存命中、占用和驱逐；
- 正常接受、截断和 dead-end 次数；
- 结构验证与业务验证通过率；
- 冷、热 TTFT 与约束 TPOT 增量；
- 每批唯一约束状态数；
- CPU 约束线程、Mask 搬运与 GPU 应用时间。

只报告“可解析率 100%”会遗漏不完备、业务错误和尾延迟。

## 9. 失败与降级

### 9.1 四层正确性

**健全性**：正常提交的输出都属于 $\mathcal L_D$。
**完备性**：合法且可由 Tokenizer 表达的路径不会被错误删除。
**终止正确性**：只有接受状态才报告正常完成。
**业务正确性**：结果与 observation 和业务规则一致。

Mask 主要保证健全性。
Tokenizer 对齐与测试决定完备性和终止正确性，业务验证器负责最后一层。

### 9.2 无合法后继

若 $A(q_t)=\varnothing$，系统必须停止并报告合同失败。
把 Mask 全部打开继续采样，会把硬合同静默改成普通文本。

空集合可能来自：
- 语言为空或编译错误；
- Tokenizer 对齐算法不完备；
- 其他处理器屏蔽了全部合法 Token；
- EOS、最小长度或特殊 Token 规则冲突；
- 状态并发错误或内存污染；
- 剩余预算不足以到达接受状态。

错误事件应携带约束身份、Tokenizer Revision、状态摘要和处理器阶段。
日志不应无限保存含租户隐私的完整 Grammar 或输出。

### 9.3 其他失败

编译超时应拒绝或使用调用方明确允许的已注册版本。
不支持的规则应在准入阶段报错，不能静默忽略。
相同约束的并发冷编译应合并，避免缓存惊群。
达到输出上限时，流式内容仍只是前缀。
Tokenizer 或编译语义升级后必须换缓存身份。
结构通过但事实错误时，业务校验仍应拒绝。

### 9.4 降级也是新合同

资源不足时可以排队、拒绝、转异步，或选择调用方预先允许的简化约束。
不能静默关闭约束、放宽枚举、删除必填字段或把前缀当成功。

从 $D$ 改为 $D'$ 等于执行：
$$\mathcal R'=(I,M,D',P,S')$$
调用方、Trace 和审计必须看见变化。

## 10. 能力边界

结构化输出能保证可形式化的形状和 Token 路径，不能证明：
- `gpu-prod` 的状态判断符合事实；
- `ops-a` 有权访问该集群；
- 某个工具应该被执行；
- 工具参数不会产生副作用；
- observation 没有被污染；
- 业务事务已经提交。

## 总结

- 合同 $D$ 定义语言 $\mathcal L_D$，约束器阻止生成进入死前缀。
- 正则可用有限状态表达，递归结构通常还需要解析栈。
- Token 判定必须消费增量 Detokenizer 产生的完整字节，Decoder 状态与 Revision 都属于约束身份。
- Token Mask 保证最终采样支持集不越过合法集合。
- 编译影响冷 TTFT，Mask、状态推进与同步影响热 TPOT。
- dead-end、截断和不支持语义都必须显式失败，不能解除约束。
- 形式合法不等于事实、权限或业务正确。
