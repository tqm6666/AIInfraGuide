Multi-LoRA 让多个租户共享昂贵的底座权重，只为每个租户保留较小的低秩增量。
它节省的是底座副本，不会让 Adapter 加载、显存、带宽、计算和隔离成本消失。
本节继续追踪统一请求合同 $\mathcal R=(I,M,D,P,S)$：租户 `ops-a` 必须使用固定底座与 `ops-diagnosis@17`，不能静默切到底座或其他租户的 Adapter。

## 1. 问题与低秩数学

### 1.1 LoRA 保存什么

对线性层：
$$W\in\mathbb R^{d_{\text{out}}\times d_{\text{in}}}$$
LoRA 不复制完整 $W$，而是学习：
$$A\in\mathbb R^{r\times d_{\text{in}}},\qquad B\in\mathbb R^{d_{\text{out}}\times r}$$
前向为：
$$y=Wx+sBAx,\qquad s=\frac{\alpha}{r}$$

$W$ 是共享底座，$(A,B,s)$ 是某个 Adapter 的增量；当 $r\ll\min(d_{\text{in}},d_{\text{out}})$ 时，增量远小于完整矩阵。

完整矩阵参数量：
$$N_W=d_{\text{out}}d_{\text{in}}$$
低秩增量参数量：
$$N_L=r(d_{\text{in}}+d_{\text{out}})$$
若输入、输出维度都为 $d$：
$$\frac{N_L}{N_W}=\frac{2r}{d}$$

当 $d=4096,r=16$ 时，单个方阵的比例为：
$$\frac{32}{4096}=0.78125\%$$
这个比例只适用于被挂载的矩阵，不能直接代表整个模型 Adapter 大小。

### 1.2 计算也分成两部分

对一个 Token，基础矩阵乘近似需要：
$$C_W\approx2d_{\text{out}}d_{\text{in}}$$
LoRA 两次低秩乘法近似需要：
$$C_L\approx2r(d_{\text{in}}+d_{\text{out}})$$

理论 FLOPs 比例也约为 $2r/d$。
但在线 Decode 的低秩矩阵很小，Kernel 启动、索引、权重读取和异构组批可能比 FLOPs 更显著。
所以“参数只占 0.78%”不能推出“TPOT 只增加 0.78%”。

### 1.3 target modules 同样重要

Adapter 只修改被选中的线性层。
总参数量为：
$$N_{\text{adapter}}=r\sum_{l,m}(d_{\text{in},lm}+d_{\text{out},lm})$$

相同 rank 若挂载层数不同，大小和计算会相差数倍。
容量规划必须读取实际张量形状、dtype、缩放和目标层，不能只看 rank 或文件名。

## 2. 底座复用怎样发生

### 2.1 一份 $W$，多份 $\Delta W_i$

若为每个租户合并权重：
$$W_i=W+\Delta W_i$$
服务要保存多份接近完整大小的 $W_i$。

Multi-LoRA 保留一份 $W$，按请求选择：
$$\Delta W_i=s_iB_iA_i$$
批次中的底座计算可以共享高效大矩阵乘，低秩分支按 Adapter 身份路由。

概念执行路径为：
```text
请求固定 adapter identity
 -> 确认 Adapter 已批准且兼容
 -> 获取 CPU/GPU 驻留引用
 -> 调度器记录每行 adapter id
 -> 计算共享底座结果
 -> 加上各行对应的低秩增量
 -> 请求结束后释放引用
```

### 2.2 复用不包含什么

共享底座不等于共享所有状态。
每个请求仍有自己的：
- 输入与位置状态；
- Grammar、Parser 和 RNG；
- KV Cache；
- Adapter 路由元数据；
- SLO、优先级和租户配额。

不同 Adapter 产生不同隐藏状态和 Logits。
未经证明等价的 KV、Prefix Cache 或输出不能跨 Adapter 复用。

## 3. Adapter identity

### 3.1 名称不是身份

显示名 `ops-diagnosis` 可以随发布指向新版本，不能直接作为数值缓存键。
`ops-diagnosis@17` 也应最终解析到不可变 Artifact Hash。

一个概念身份包含：
```text
base weight revision/hash
+ adapter artifact revision/hash
+ target-module map
+ rank, scaling, dtype
+ tokenizer/extra-vocabulary identity when present
+ runtime semantics affecting the delta
```

租户别名只用于路由：
```text
ops-a -> ops-diagnosis@17 -> immutable adapter hash
```

### 3.2 加载兼容性

加载前至少验证：
- 底座权重 Revision 与训练绑定一致；
- 每个张量名称、Shape 和 dtype 合法；
- rank、缩放与 target modules 完整；
- Artifact 大小、Hash、签名和来源可信；
- 额外词表或 Tokenizer 变更与 $M$ 一致。

Shape 能对上不代表语义底座一致。
错误底座可能不报加载错误，却让输出质量悄悄崩坏。

### 3.3 请求必须 pin Revision

`ops-a` 在准入时解析并固定 `@17`。
运行中即使别名切到 `@18`，当前序列仍使用 `@17` 直至结束。

这要求：
- 路由更新原子化；
- 运行请求持有 Revision 引用；
- 旧版停止接收新流量后再排空；
- 卸载等待引用归零；
- Trace 记录最终解析身份，而不只记录别名。

在生成中途换 Adapter 会改变后续层状态，不能当作无感热更新。

## 4. CPU/GPU 驻留与生命周期

### 4.1 三级驻留

Adapter 通常经过：
```text
Artifact Store -> CPU Cache -> GPU Active Slots
```

Artifact Store 保存不可变文件和元数据，容量大但延迟最高。
CPU Cache 保存已下载、校验和反序列化的张量，避免重复远端读取；GPU Slot 保存当前可直接参与 Kernel 的 Adapter，容量最紧张。

CPU “命中”仍可能需要 pinned memory 准备、H2D 拷贝、布局转换和同步。
GPU 命中才跳过这段换入路径。

### 4.2 生命周期状态

一个 Revision 可按 `ABSENT → FETCHING → CPU_READY → GPU_LOADING → GPU_READY → IN_USE → EVICTABLE → EVICTED` 推进。
校验、加载或健康检查失败则进入带原因的失败状态。
同一 Revision 的并发加载应使用 singleflight，共享一个结果。

状态所有者还要维护 CPU/GPU 字节、槽位 epoch、活跃引用、复用信息、安全域和失败退避。

### 4.3 淘汰

只按最近使用时间淘汰容易被大 Adapter 或长尾流量扰动。
更稳妥的策略同时考虑大小、频率、加载代价、租户份额、优先级和是否仍被引用。

可用原则包括：
- 热点或关键 Adapter 可 pin，但有上限；
- 大对象按“释放字节”而非个数评估；
- 冷加载高峰实施准入和带宽限流；
- 每租户保留公平份额，避免单租户扫空缓存；
- 正在使用的槽位不可复写；
- 驱逐后短期又加载要作为 thrashing 指标。

## 5. 显存与带宽手算

### 5.1 一个 Adapter 有多大

假设 32 层、隐藏维度 4096、中间维度 11008、rank 16。
每层挂载四个注意力投影，以及三个 MLP 投影。

注意力增量参数：
$$N_{\text{attn}}=4\times16\times(4096+4096)=524{,}288$$
MLP 增量参数：
$$N_{\text{mlp}}=3\times16\times(4096+11008)=724{,}992$$
全模型：
$$N_L=32\times(524{,}288+724{,}992)=39{,}976{,}960$$

BF16 原始张量约为：
$$39{,}976{,}960\times2\text{ bytes}\approx76.25\text{ MiB}$$
还未计对齐、元数据、工作区和加载峰值。

若仅挂载两个 4096 方阵投影，同样 rank 的原始张量约为 16 MiB。
差异来自 target modules，而不是 rank。

### 5.2 底座复用收益

假设一个 80 亿参数底座用 2 byte/参数，权重约 14.9 GiB。
20 个上述 Adapter 的原始张量总计约 1.49 GiB。

只看权重：
```text
共享底座方案  ≈ 14.9 GiB + 1.49 GiB
20 份完整副本 ≈ 20 × 14.9 GiB = 298 GiB
```
这说明底座复用价值巨大，但没有计入 KV、运行工作区和 Adapter 槽位预留。

### 5.3 GPU 槽位上界

若 8 个槽位都按最大 rank 64 为上述全模块布局预留，保守估算为：
$$M_{\text{slots}}\approx8\times\frac{64}{16}\times76.25\text{ MiB}=2440\text{ MiB}\approx2.38\text{ GiB}$$

实际实现可能按 rank 分组、按需分配或采用不同 Padding，这不是固定分配公式。
它说明 `slot count × max rank × target dimensions` 会共同挤压显存。

若权重外运行时余量为 12 GiB，再预留 1 GiB 工作区：
```text
无这些 LoRA 槽位：KV 约可用 11 GiB
有 2.38 GiB 槽位：KV 约可用 8.62 GiB
```
若平均每条长请求占 350 MiB KV，粗略上界从 32 条降到 25 条。
真实容量还受 Block 粒度、长度分布和安全水位影响。

### 5.4 搬运时间

76.25 MiB Adapter 在有效 H2D 带宽 18 GiB/s 下，纯传输下界约为：
$$T_{\text{H2D}}\approx\frac{76.25}{18\times1024}\text{ s}\approx4.14\text{ ms}$$
若 CPU Cache 未命中，从 600 MiB/s 的远端存储读取，纯读取约 127 ms。

实际还要加排队、下载抖动、校验、反序列化、布局拷贝和同步。
峰值链路带宽不能替代 P99 实测。

## 6. Adapter-aware batching

### 6.1 混合批次的计算

设批输入为 $X$，按 Adapter 划分为组 $G_i$。
概念输出为：
$$Y=XW^\top+\operatorname{scatter}_i\left(s_i(X_iA_i^\top)B_i^\top\right)$$

底座项可在整个批次执行。
LoRA 项要按每行 Adapter ID gather 权重、分组计算，再 scatter 回原行。

成本可写成：
$$C_{\text{batch}}\approx C_W(B)+\sum_i C_L(|G_i|,r_i)+C_{\text{gather/scatter}}+C_{\text{launch}}$$

唯一 Adapter 越多，每组越小，低秩 Kernel 越难达到高利用率。
不同 rank 还会带来 Padding、分支或更多专门化形状。

### 6.2 能共批不等于适合共批

语义上，只要每行路由正确，不同 Adapter 可以共批。
性能上仍会受到：
- GPU 槽位是否都已就绪；
- 冷加载是否阻塞该组；
- 每批唯一 Adapter 数；
- rank 与 target map 的异构程度；
- Token 行重排和访存局部性；
- 图捕获或工作区形状；
- 长尾租户等待时间。

把同 Adapter 请求多等一会儿可提高组大小，却增加排队。
调度器要在吞吐和 deadline 之间权衡，不能为同质批次饿死低 QPS 租户。

## 7. KV Cache 正确性

### 7.1 为什么 Adapter 会改变 KV

LoRA 改变线性层输出，进而改变隐藏状态。
后续层的 Key 和 Value 是这些隐藏状态的函数：
$$K_l=H_{l-1}W^K_l,\qquad V_l=H_{l-1}W^V_l$$
即使 LoRA 没直接挂在某层 $K/V$ 投影，早先隐藏状态变化也可能传播到这里。

因此相同 Token ID、相同底座但不同 Adapter 的 KV 通常不同。
“Adapter 文件很小”与“KV 可以共享”没有逻辑关系。

### 7.2 Prefix Cache 身份

概念键至少包含所有影响数值的字段：
```text
exact input token/embedding identity
+ base revision and numerical mode
+ adapter revision, scale and activation scope
+ tokenizer/template consequences
+ positional state
```

`ops-a@17` 的 Prompt KV 不能给 `ops-a@18` 或底座请求使用。
别名相同但 Artifact 已替换时，也必须得到不同键。

只有严格证明某段前缀在 Adapter 生效前计算且数值等价，才能做更细粒度共享。
这种优化需要显式作用域和测试，不能作为默认假设。

### 7.3 中途切换

序列生成到一半再换 Adapter，会让旧 KV 与新权重不一致。
安全选择是固定整个请求的 Adapter，或从明确边界重新计算受影响状态。
简单替换 GPU 槽位指针后继续 Decode 属于正确性故障。

引用计数和 epoch 还要防止“槽位已被复写、旧请求仍持有 ID”的竞态。

## 8. 多租户隔离与 SLO

### 8.1 身份隔离

数据面只接受已授权别名，不能接受任意路径、URL 或内部槽位 ID。
控制面维护：
```text
tenant -> allowed immutable adapter revisions
```
`ops-a` 不能请求其他租户的 Adapter，也不能通过名称碰撞覆盖 `@17`。

Artifact 仓库、CPU Cache 和 GPU Slot 都应保留安全域与所有权。
跨租户去重虽节省内存，却可能产生权限错误或命中延迟侧信道。

### 8.2 资源隔离

每租户至少限制：
- 已注册和可驻留 Adapter 字节；
- rank、target modules 与 GPU 槽位份额；
- 冷加载频率、并发和 H2D 字节；
- CPU Cache、pinned memory 和下载带宽；
- KV Cache、活跃序列和队列时间；
- 发布、回滚和失败重试速率。

只按请求数限流不够。
一个高 rank 冷 Adapter 请求可能比一个热点低 rank 请求昂贵得多。

### 8.3 SLO 分解

Adapter 感知 TTFT 可写为：
$$T_{\text{TTFT}}=T_{\text{queue}}+\mathbf{1}_{\text{artifact miss}}T_{\text{fetch}}+\mathbf{1}_{\text{GPU miss}}T_{\text{H2D}}+T_{\text{prefill}}$$
TPOT 还包含低秩 Kernel、路由和异构批次成本。

应按 GPU hit、CPU hit 和全冷分别报告 P50/P95/P99。
平均值会掩盖长尾 Adapter 的加载尖刺和饥饿。

关键观测包括命中与加载字节、驱逐后重载、每批唯一 Adapter、rank 分布、槽位引用、KV 可用块和租户 deadline miss。

## 9. 失败与降级

### 9.1 典型失败

**底座误配**：Shape 可兼容但语义 Revision 错误；加载前必须校验不可变绑定。

**Artifact 损坏**：Hash、签名、张量或 dtype 不符；保持旧路由，不做部分加载。

**缓存惊群**：大量请求同时加载同一 Revision；singleflight 合并工作。

**CPU OOM**：按个数限制忽略了对象大小；同时限制总字节、pinned memory 和反序列化峰值。

**GPU 无槽位**：只能排队、驱逐可回收对象或拒绝；不能覆盖正在使用的槽位。

**thrashing**：工作集大于缓存且近均匀访问；实施准入、预热、大小感知与租户配额。

**卸载竞态**：路由已切换但旧请求未排空；以 Revision 引用和 epoch 保证生命周期。

**KV 污染**：缓存键缺 Adapter 身份；立即隔离缓存并视为正确性事故。

### 9.2 显式降级

允许的应对包括：
- 等待已在进行的同 Revision 加载；
- 在 deadline 前排队；
- 转到已预热且身份完全相同的副本；
- 返回“Adapter preparing”或资源不足；
- 使用调用方事先批准的旧 Revision，并明确记录；
- 为低优先级请求转异步。

禁止：
- 静默使用底座；
- 静默改成另一 Adapter；
- 忽略部分 target modules；
- 降 rank 或改变缩放后仍声称是 `@17`；
- 为命中缓存而省略 Adapter identity；
- 驱逐正在运行请求的权重。

降级改变 $M$ 时，就是新的 $\mathcal R'=(I,M',D,P,S')$，必须重新授权并可观测。

## 10. 能力边界

Multi-LoRA 适合多个租户共享同一底座且 Adapter 相对较小的场景。
若底座不同、Adapter 修改范围很大、单租户可独占 GPU，或法规要求物理隔离，独立服务可能更合适。
本节不承诺某种 Kernel、槽位布局或缓存策略在所有引擎中相同。
也不提供运行时加载 API、CLI、部署步骤或支持矩阵。

## 总结

- LoRA 用 $BA$ 表示低秩增量，参数量为 $r(d_{\text{in}}+d_{\text{out}})$。
- Multi-LoRA 共享底座，但 Adapter、KV、路由和租户状态仍需独立管理。
- Adapter 身份必须绑定底座、Artifact、目标层、rank、缩放和相关 Tokenizer 状态。
- Artifact、CPU Cache 与 GPU Slot 构成三级驻留，加载和淘汰都进入 TTFT。
- 槽位数与最大 rank 会挤压 KV；异构 Adapter 会造成 Batch 碎片和路由成本。
- KV 数值依赖 Adapter，未经证明不能跨 Revision 复用或中途切换。
- 多租户隔离同时覆盖身份、显存、CPU、带宽、加载频率、队列和 SLO。
