## 1. 问题与合同

### 1.1 完整 VLM 链路

```text
media reference
 -> fetch bytes
 -> decode
 -> normalize
 -> multimodal processor
 -> encoder
 -> projector / resampler
 -> LLM prefill
 -> LLM decode
```

前四步通常以 CPU、网络和主存为主；Encoder 与 Projector 通常使用 GPU，也可能有独立设备或并行策略。
LLM 阶段同时消费文本 Token Embedding 与媒体特征。

每一阶段都可能排队、缓存、失败或持有大块内存；只记录总 TTFT 无法定位下载、解码、Encoder 或 LLM Prefill。

### 1.2 五元合同中的多模态状态

对 `ops-a`：
- $I$：文本、截图类型、内容身份、顺序、占位关系和允许的预处理；
- $M$：Processor、Encoder、Projector、LLM、Tokenizer、Template 与 `ops-diagnosis@17` 的不可变 Revision；
- $D$：工具阶段和 final 阶段的输出合同；
- $P$：从 Logits 到 Token 的选择策略；
- $S$：媒体字节、像素、特征 Token、TTFT、KV、租户配额和端到端时限。

截图变化、裁剪规则变化或 Encoder Revision 变化，都会改变模型实际看到的 $I$ 或 $M$。
它们不能被隐藏成一次“相同请求”。

### 1.3 两类主要成本

媒体成本分为一次性的 Fetch/Decode/Processor/Encoder/Projector，
以及媒体特征进入上下文后产生的 LLM Prefill 与 KV。
Encoder Cache 只能消除前者的一部分，不能自动消除本次序列的 KV。

## 2. 媒体获取、解码与 Normalize

### 2.1 Fetch：引用不是内容

URL、上传句柄或对象 Key 都只是媒体引用。
同一 URL 可能改变内容，而不同 URL 也可能指向同一字节。

更稳妥的入口是：
```text
untrusted reference/upload
 -> media gateway
 -> validated immutable object
 -> content identity
 -> inference pipeline
```

媒体网关应限制协议、域名与解析后 IP，逐跳复查重定向，并限制连接时间、下载字节和总时长。
网络层还要阻断内网、回环、Link-local 和云元数据地址，避免推理服务成为 SSRF 代理。

客户端声称的 Hash 只能作为 Hint，除非服务端验证实际字节。
可复用身份最终应绑定不可变内容，而不是可变 URL 字符串。

### 2.2 压缩大小不等于解码大小

压缩图片很小，解码后仍可能巨大。
RGB 图像的基础内存为：
$$M_{\text{decoded}}=H\times W\times3\text{ bytes}$$

$8192\times8192$ 的 RGB uint8 图像约为：
$$8192^2\times3=192\text{ MiB}$$
还没有计解码库缓冲、颜色转换和后续浮点 Tensor。

因此入口要同时限制：
- 压缩字节；
- 解码后宽、高和总像素；
- 宽高比与帧数；
- 单请求所有媒体的总预算；
- 解码并发和进程内存。

只限制“最多一张截图”无法防止解码炸弹。

Decode 还会解释真实格式、EXIF 方向、颜色空间、Alpha、帧序列和损坏数据。
这些语义变化会改变像素；若缓存解码结果，就必须进入身份或触发失效。

### 2.3 Normalize

Normalize 通常包含方向校正、颜色通道统一、Resize、Crop、数值缩放和均值方差变换。
顺序不可随意交换：先 Crop 再 Resize 与先 Resize 再 Crop 会得到不同像素。

概念上：
$$X_{\text{pixel}}=\operatorname{Normalize}_{M}(\operatorname{Decode}(B_{\text{media}}))$$

`ops-a` 的同一截图若用不同裁剪框或分辨率处理，模型输入已经改变。
为了节省成本而降分辨率属于显式降级，不是透明优化。

## 3. Processor、Encoder、Projector 与 LLM

### 3.1 Multimodal Processor

Processor 把媒体像素、文本与模板规则组织成模型需要的张量和元数据。
它可能执行：
- 媒体侧：动态分辨率、Tile、Patch 网格、有效区和 Batch Shape；
- 协议侧：文本 Tokenization、占位展开、媒体顺序和位置映射。

Processor 不只是图片变换器。
它还定义“第几张图对应文本中的哪个位置”，因此 Revision 属于 $M$。

占位数量、媒体数量或顺序不一致时，应在进入 Encoder 前失败。
异步 Fetch 的完成顺序不能改变原始消息顺序。

### 3.2 Encoder

以 Patch 型视觉 Encoder 为例，Patch 尺寸为 $P_h\times P_w$：
$$N_{\text{patch}}\approx\left\lceil\frac{H}{P_h}\right\rceil\left\lceil\frac{W}{P_w}\right\rceil$$
若使用多 Tile，还要对每个 Tile 求和并加特殊位置。

Patch Embedding 进入多层视觉网络：
$$H_v=\operatorname{Encoder}(X_{\text{pixel}})\in\mathbb R^{N_v\times D_v}$$

标准全局 Attention 的主要计算随 $N_v^2$ 增长，线性层随 $N_vD_v^2$ 增长。
实际实现可能使用局部 Attention、分块或融合，但视觉 Token 增加仍会放大计算和激活。

### 3.3 Projector 或 Resampler

Encoder 维度 $D_v$ 往往不同于语言隐藏维度 $D_l$。
Projector 将特征映射到 LLM 空间：
$$H_l=\operatorname{Projector}(H_v)\in\mathbb R^{N_{\text{vision}}\times D_l}$$

Resampler 还可能把多个 Patch 压缩为较少的语言特征。
因此：
$$N_{\text{patch}}\neq N_v\neq N_{\text{vision}}$$
三者不能混为一个“图片 Token 数”。

Cache 若保存在 Projector 前，命中后仍要运行 Projector。
若保存在 Projector 后，Cache identity 必须包含 Projector Revision。

### 3.4 LLM

文本 Embedding 与视觉特征按占位位置组合：
$$E_{\text{llm}}\in\mathbb R^{(N_{\text{text}}+N_{\text{vision}})\times D_l}$$

随后 LLM 对整段序列做 Prefill。
视觉位置和文本位置一样会产生逐层 K/V，并占用上下文窗口。

`ops-diagnosis@17` 若只作用于 LLM，不改变 Encoder 特征，却仍会改变 LLM KV；若也修改 Encoder 或 Projector，则必须进入对应 Cache identity。

## 4. Image Token 与 Feature 成本

### 4.1 “一张图”不是统一计量单位

两张图可能因为分辨率、Tile、帧数、裁剪和压缩策略产生完全不同的特征数。
容量调度应使用像素、Patch、Encoder Token、Projected Feature 和 LLM Context Token，而不只使用媒体数量。
一个文本占位符也可能扩展为数百个特征；Tokenizer 中一个占位 ID 不代表 LLM 只处理一个位置。

### 4.2 Encoder 输出大小

Encoder 输出内存近似为：
$$M_{\text{enc-out}}=N_vD_vb_e$$
$b_e$ 是每元素字节数。

Projected Feature 近似为：
$$M_{\text{feature}}=N_{\text{vision}}D_lb_p$$
这部分可能短暂存在，也可能进入 Encoder Cache。

### 4.3 LLM KV 成本

对 $L$ 层、$n_{\text{kv}}$ 个 KV Head、Head 维度 $d_h$、每元素 $b_{kv}$ 字节：
$$M_{\text{KV/token}}=L\times2\times n_{\text{kv}}\times d_h\times b_{kv}$$

媒体带来的额外 KV 为：
$$M_{\text{vision-KV}}=N_{\text{vision}}\times M_{\text{KV/token}}$$

Encoder Feature Cache 与 LLM KV 保存的是不同对象。
命中前者节省重复编码，却不会自动消除当前序列的后者。

若图片两边都扩大 2 倍，Patch 数约为 4 倍，标准全局视觉 Attention 的交互数可能为 16 倍。
动态 Tile 还会产生阶梯变化，因此预算必须使用 Processor 的实际输出 Shape。

## 5. Encoder Cache identity

### 5.1 三类缓存不要混淆

多模态链路至少有：
- **媒体/Processor Cache**：保存解码或预处理结果，节省 I/O 与 CPU；
- **Encoder Cache**：保存 Encoder 或 Projector 特征，节省模态 GPU 计算；
- **LLM KV Cache**：保存语言模型注意力状态，节省或承载 Prefill/Decode。

它们的值、存储位置、命中条件和淘汰代价都不同。

### 5.2 值依赖决定键

Processor key 由内容身份、解码/颜色语义、Resize/Crop/Tile/抽帧配置和 Processor Revision 构成。
Encoder key 再加入 Encoder 权重、数值模式、输出阶段与 dtype；缓存 Projector 后结果时加入 Projector Revision，Adapter 影响该路径时也加入 Adapter。
LLM KV key 还要加入精确文本与特征、媒体顺序与位置、LLM Revision、`ops-diagnosis@17`、位置和数值状态。

原则不是把所有字段机械塞入每个键，而是：任何改变缓存值的字段都不能缺席。

### 5.3 内容身份与作用域

裸 URL 不能作为唯一 key。
更稳妥的是已验证内容 Hash、不可变对象版本，或服务端签发的 opaque media id。
即使内容相同，跨租户共享 Cache 也可能违反数据隔离或产生时延侧信道。
敏感媒体应按 tenant 或安全域分 Namespace，并有 TTL、字节配额、删除和审计语义。
media id 已驱逐时应明确 miss 或从授权对象仓库恢复，不能猜内容、用空图或命中其他租户对象。

Encoder Cache 要先 acquire、结束或取消后 release，只能淘汰引用为零的项。
容量按字节管理，并同时报告请求命中、特征字节命中和节省的 Encoder 时间。

## 6. CPU-GPU 流水线

### 6.1 分阶段队列

可将数据面拆成：
```text
fetch queue -> decode workers -> processor queue
 -> H2D staging -> encoder queue -> feature handoff
 -> LLM scheduler
```

Fetch 消耗连接和带宽，Decode/Processor 消耗 CPU 与主存，H2D 消耗 pinned memory 与互连，
Encoder 消耗 GPU 激活与工作区，LLM 则消耗 Prefill、KV 和 Decode 槽位。

一个无界总队列会让大媒体同时占满多个阶段。
应在昂贵解码前做早期准入，并在每段设置字节、像素、Token 和并发上限。

### 6.2 单请求依赖与跨请求重叠

单个冷请求的关键路径近似为：
$$T_{\text{TTFT}}=T_{\text{fetch}}+T_{\text{decode}}+T_{\text{processor}}+T_{\text{enc-queue}}+T_{\text{encoder}}+T_{\text{projector}}+T_{\text{llm-prefill}}$$

不同请求之间可以流水重叠：GPU 编码请求 A 时，CPU 解码请求 B。
重叠提高吞吐，但会让更多中间 Buffer 同时存活，增大峰值内存。

流水线容量受最慢阶段限制：
$$Q_{\max}\lesssim\min(Q_{\text{fetch}},Q_{\text{cpu}},Q_{\text{encoder}},Q_{\text{llm}})$$

只扩 LLM 并发，若 Decode 已饱和，不会提高端到端 Goodput。

### 6.3 Backpressure 与取消

Encoder 队列满时应把反压传回 Processor、Fetch 和准入层，阻止继续产生大 Tensor。
取消信号也要传播到下载、解码、Encoder 和 LLM，避免后台工作继续侵占 SLO。

## 7. ops-a 显存与延迟手算

### 7.1 从截图到视觉特征

假设 `ops-a` 上传一张 $3840\times2160$ RGB 截图，压缩文件为 2 MiB。
解码后的 uint8 像素为：
$$3840\times2160\times3\approx23.73\text{ MiB}$$

Processor 将它缩放、裁剪到 $672\times672$，再用 FP32 Normalize：
$$672\times672\times3\times4\approx5.17\text{ MiB}$$
若实现先在原分辨率转 FP32，临时 Tensor 可接近 94.9 MiB。
因此操作顺序会显著影响 CPU 峰值。

Patch 为 $14\times14$：
$$N_{\text{patch}}=(672/14)^2=48^2=2304$$
若 Projector 每 $2\times2$ Patch 合并，进入 LLM 的特征数为：
$$N_{\text{vision}}=2304/4=576$$

### 7.2 Feature 与 KV

若 Encoder 维度为 1024，BF16 Encoder 输出约为：
$$2304\times1024\times2=4.5\text{ MiB}$$
若合并后投影到 LLM 维度 4096，Projected Feature 也是：
$$576\times4096\times2=4.5\text{ MiB}$$

假设 LLM 有 32 层、8 个 KV Head、Head Dim 128，KV 为 BF16：
$$M_{\text{KV/token}}=32\times2\times8\times128\times2=128\text{ KiB}$$
576 个视觉位置产生：
$$M_{\text{vision-KV}}=576\times128\text{ KiB}=72\text{ MiB}$$

Feature 只有约 4.5 MiB，但对应 LLM KV 达 72 MiB。
因此只盯 Encoder Cache 大小会低估媒体对并发的影响。

### 7.3 单请求与并发

若文本 Prompt 为 512 Token、输出上限 128 Token：
$$N_{\text{total}}=512+576+128=1216$$
走到最大长度时，KV 约为：
$$1216\times128\text{ KiB}=152\text{ MiB/request}$$

8 条同规格请求仅 KV 就约 1.19 GiB，其中视觉位置贡献 576 MiB。
还要同时容纳 Encoder 权重、激活、Feature、`ops-diagnosis@17`、工作区和缓存。

### 7.4 延迟状态

同一输入要分别测全冷、Processor 热、Encoder 热和 LLM Prefix 热。
Processor 命中不一定省 Fetch；Prefix 只有输入、位置、模型与 Adapter 身份一致时才可复用。
把 Encoder 热路径当普通请求容量，会严重高估 TTFT。

## 8. 限额、失败与降级

### 8.1 多维限额

准入至少检查：
- 单媒体与总压缩字节；
- 解码宽高、总像素和宽高比；
- 图片、视频帧、音频时长；
- Tile、Patch、Encoder Token 和 Projected Feature；
- 文本加媒体后的上下文长度；
- CPU 内存、Encoder 激活、Feature Cache 和 KV 预算；
- 每租户并发、缓存字节和媒体处理速率。

媒体数量只是最外层限额，不能替代这些预算。

### 8.2 典型失败

**Fetch 失败**：超时、重定向越界、对象不存在或超过字节上限。

**Decode 失败**：格式伪造、损坏文件、解码炸弹或像素超限。

**Normalize 漂移**：方向、颜色、Crop 或 Revision 变化却错命中旧 Cache。

**占位错配**：媒体数量、顺序和文本位置不一致，应在 Encoder 前拒绝。

**Encoder OOM**：平均截图可运行，但最大 Patch Batch 的激活峰值溢出。

**Cache 错命中**：漏掉 Processor、Encoder、Projector 或 Adapter 依赖，产生静默质量错误。

**异步乱序**：按 Fetch 完成顺序拼媒体，导致图文对应关系变化。

**取消泄漏**：请求结束后下载、Tensor 或 Cache 引用仍未释放。

**隐私泄漏**：跨租户 media id、Cache 命中时延或日志暴露内容。

### 8.3 显式降级

降低分辨率、减少帧、缩短音频或省略截图都会改变 $I$。
只有合同预先允许并能表达质量损失时才可采用。

对必须依据截图判断的请求，文本模式不能冒充成功。
可返回“媒体不可用”、转异步、使用新鲜度合格且获授权的缓存，或明确拒绝。

不能静默使用旧 Feature、空图、错误顺序或其他租户缓存。
降级后的 $\mathcal R'$ 必须记录新媒体预算、处理身份和结果置信边界。

## 9. 观测与容量验证

### 9.1 阶段指标

至少分别观测：
```text
fetch/decode: time, bytes, pixels, result
processor/encoder: time, queue, output shapes, tokens, cache state
projector/LLM: feature count, prefill tokens, time
resource/SLO: KV blocks, TTFT, deadline result
```

Trace 关联内容身份的低敏摘要、Processor/Encoder/Projector Revision、视觉特征数、Adapter Revision 和租户。
不要记录签名 URL、原始 Base64、截图内容或可长期反查隐私的映射。

### 9.2 压测矩阵

容量验证要覆盖：
- 输入：无图、常见/最大截图、宽高比和 Tile 阈值；
- 缓存：全冷、Processor 热、Encoder 热、驱逐与 Revision 切换；
- 负载：单请求、稳态、突发和多租户争用；
- 故障：Fetch/Decode 变慢、Encoder OOM 和取消。

报告 P50/P95/P99 并同步检查任务质量；丢失事故细节的降分辨率不是有效优化。

### 9.3 峰值而非稳态张量

GPU 峰值为权重、Pixel Batch、Encoder 激活、Feature/Cache、LLM KV 与工作区之和。
CPU 峰值还包括压缩字节、解码像素、浮点 Tensor、队列和 pinned memory。
Profiling 要覆盖最大 Shape 与阶段重叠；只取各阶段单独峰值会低估叠加。

## 10. 能力边界

本节描述可迁移的数据与资源链路，不罗列模型、接口、启动参数或引擎支持表。
具体架构可能动态切块、压缩 Token、交织 Encoder 与 Decoder，公式应由实际 Processor Shape 校准。

VLM 能读取截图不代表视觉结论一定正确。
最终状态仍需工具 observation、业务校验和权限边界；采样分布留到 8.5。

## 总结

- VLM 链路包含 Fetch、Decode、Normalize、Processor、Encoder、Projector 和 LLM。
- 媒体成本同时来自一次性 Encoder 计算与视觉位置的 Prefill/KV。
- Patch、Encoder Token、Projected Feature 和占位 Token 不是同一个数量。
- Cache key 由值依赖决定，URL 不是可靠内容身份。
- CPU-GPU 流水提高吞吐，也会放大中间 Buffer 和显存峰值。
- 限额应覆盖字节、像素、帧、特征、上下文、缓存和租户资源。
- 降分辨率、减帧或去掉媒体都会改变 $I$，必须显式协商。
