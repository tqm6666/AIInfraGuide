投机解码最容易被两个局部数字误导：

1. 一轮接受多个 Token，于是把接受长度直接当加速倍数。
2. 单请求 TPOT 下降，于是推断高并发吞吐和 Goodput 也会提高。

真正发生的交换是：系统少走若干 Target 串行 step，却多做 Proposal、宽验证、候选 KV 和状态处理。
收益不仅取决于候选是否正确，还取决于 GPU 在普通 Decode 与 Verify 时分别受带宽、计算还是 Attention 限制。

本节只负责统一成本与服务边界。
方法结构已在 5.1～5.3 说明，运行时状态怎样实现留到 5.5。

## 1. 先明确优化目标
“更快”必须先说明观察对象。

### 1.1 TPOT
TPOT 描述 Decode 阶段平均输出一个 Token 的时间。
投机减少 Target 串行轮次，最直接的潜在收益通常落在 TPOT。
但一轮会成批提交 $L$ 个 Token，测量时应按真实提交数摊销，而不是把每个轮次当一个输出 Token。

### 1.2 TTFT
TTFT 包含排队、Prefill 和首次采样。
投机主要作用于后续 Decode，不会消除 Prompt Prefill。
Draft 权重占用、Verify Token Budget 或调度竞争还可能使新请求更晚进入 Prefill，因此 TTFT 可能不变甚至上升。

### 1.3 吞吐
吞吐关心单位时间交付多少输出 Token 或完成多少请求。
低并发节省串行延迟不等于饱和 GPU 处理了更多有效工作；高并发时额外候选可能挤掉其他请求的真实 Token。

### 1.4 Goodput
Goodput 只计算满足服务合同的请求，例如同时满足 TTFT、TPOT 和尾延迟门槛的请求数。
若平均 TPOT 改善，但 P99 TTFT 因排队竞争恶化，Goodput 可以下降。

### 1.5 容量
显存还决定最大并发、可服务上下文长度与 OOM 安全余量。
一个降低单请求 TPOT、却因 Draft 权重挤掉大量 Target KV 的方案，可能减少整体容量。

所以收益判断至少有三层：

- 算法层：$\mathbb E[L]$ 是否足够大；
- 执行层：$t_D+t_V+t_O$ 是否足够小；
- 服务层：TTFT、TPOT、Goodput 与容量是否共同满足目标。
## 2. 统一轮次成本模型
沿用总览变量：

- $B$：当前活跃请求数；
- $C$：已确认上下文长度；
- $K$：Proposal 最大未来深度；
- $B_V$：Target 本轮打包验证的候选位置总数；
- $t_T(B,C)$：普通一次 Target 单 Token Decode step 时间；
- $t_D(K,B,C)$：本轮 Proposal 总成本；
- $t_V(B_V,C)$：Target 验证成本；
- $t_O$：采样、调度、mask、通信、候选 KV 提交与回收等其余成本。

一轮接受的 Draft Token 数为 $A\in[0,K]$，位置存活率为：

$$s_i=P(A\ge i)$$
于是：

$$\mathbb E[A]=\sum_{i=1}^{K}s_i$$
一轮最终提交长度：

$$L=A+1,\qquad \mathbb E[L]=1+\sum_{i=1}^{K}s_i$$
额外的 1 是首次拒绝后的校正 Token，或全部接受后的 bonus Token。
以上等式限定于 accepted prefix 不触发 EOS/stop、剩余输出配额至少为 $K+1$ 的非终止内轮；终止轮可能在 accepted prefix 内结束，应以实际提交长度 $L\le A+1$ 计入端到端统计。

投机轮次成本：

$$t_{\text{round}}=t_D(K,B,C)+t_V(B_V,C)+t_O$$
生成同样 $\mathbb E[L]$ 个 Token，普通 Target 近似需要：

$$\mathbb E[L]\,t_T(B,C)$$
因此 Decode 加速估计为：

$$S_{\text{decode}}\approx\frac{\mathbb E[L]\,t_T(B,C)}{t_D(K,B,C)+t_V(B_V,C)+t_O}$$
获得正收益的必要近似条件是：

$$t_D+t_V+t_O<\mathbb E[L]\,t_T$$
这条不等式比“接受率超过某个阈值”更可靠。
接受率只影响分子中的前进距离，不能描述 Draft、Verify 和系统开销。

单位提交 Token 的投机成本为：

$$\frac{t_D+t_V+t_O}{\mathbb E[L]}$$
它必须低于普通单 Token 成本 $t_T$。
## 3. 统一教学点：为什么是 1.875 倍
本章统一设置：

$$B=1,\quad K=4,\quad t_T=10\text{ ms}$$
并继续假设样本是非终止内轮，因此 $L=A+1$。
Proposal、Verify 与其余成本为：

$$t_D=3\text{ ms},\quad t_V=12\text{ ms},\quad t_O=1\text{ ms}$$
逐位置存活率为：

$$(s_1,s_2,s_3,s_4)=(0.80,0.60,0.40,0.20)$$
所以：

$$\mathbb E[A]=2.0,\quad \mathrm{AR}=0.50,\quad \mathbb E[L]=3.0$$
投机一轮需要：

$$t_{\text{round}}=3+12+1=16\text{ ms}$$
普通 Target 生成期望三个 Token 约需：

$$\mathbb E[L]t_T=3\times10=30\text{ ms}$$
于是：

$$S_{\text{decode}}\approx\frac{30}{16}=1.875$$
这个结果成立于给定的 $B$、$C$、$B_V$ 和执行测量。
它没有声称接受率为 0.5 时总能加速，也没有声称端到端请求延迟变为原来的 $1/1.875$。

接下来所有边界分析都只改变这组统一变量中的某些输入，而不另建一套指标。
## 4. Roofline：Verify 为什么可能便宜
普通 Decode 在低 $B$ 时常是 memory-bound。
每个 Target step 都要从 HBM 读取大量权重和历史 KV，但每个请求只产生一个 query 位置。
权重元素参与的计算不够多，算力单元等待数据。

投机 Verify 已经知道未来候选，因此一次 Target 前向可以处理更多位置。
对固定深度单链：

$$B_V\approx BK$$
这让同一次权重读取服务约 $B_V$ 个候选位置。
如果权重搬运仍是主项，增加候选带来的计算可以落在原本空闲的算力上。
于是 $t_V(B_V,C)$ 可能只比一次 $t_T(B,C)$ 稍大，远小于 $K\,t_T$。

这并不违反自回归因果性。
Target 不是同时决定未知 Token，而是在给定候选祖先的条件下并行计算各位置分布。

可以把 Roofline 直觉分成两边：

- 带宽侧：每次前向搬运多少权重与 KV；
- 计算侧：这些数据支持多少矩阵乘加与 Attention 工作。

普通低并发 Decode 往往停在带宽侧。
Verify 增大有效工作宽度，提高算术强度，可能向 Roofline 转折点靠近。

理想区域具有以下特征：

- $B$ 较小，普通 Decode 尚未摊薄权重读取；
- $C$ 不太长，历史 KV 流量没有压过权重流量；
- $B_V$ 足以利用空闲计算，但没有大到使计算饱和；
- 候选 shape 紧凑，padding 和 mask 开销较小；
- $t_D$ 与 $t_O$ 相对 Target step 足够小。

“一次 Verify 多个 Token”之所以可能有利，核心是权重搬运被复用，而不是多 Token 计算免费。
## 5. 从 Memory-bound 到 Compute/Attention-bound
随着 $B$ 增大，普通 Decode 已经让同一次权重读取服务更多请求。
权重带宽的摊销机会被 continuous batching 提前利用，投机可利用的空闲算力变少。

此时再把每个请求扩成 $K$ 个候选，$B_V$ 快速增长。
矩阵计算、LM Head 和采样不再是“顺带完成”，Verify 会逐渐转为 compute-bound。

上下文长度 $C$ 增大时，另一个边界出现。
每个候选 query 都要读取更长的历史 KV，Attention 的数据量随 $C$ 增长。
即使 Target 权重仍只读一次，$B_V$ 个 query 的历史 KV 访问也不能忽略。
Verify 因而可能转为 attention-bound。

三个区域可这样理解：

| 区域 | 普通 Decode 的主要限制 | 增加候选后的典型结果 |
|---|---|---|
| 低 $B$、较短 $C$ | Target 权重带宽 | Verify 摊薄权重，最可能获益 |
| 较大 $B$ | 矩阵计算或 LM Head | 候选接近增加真实 FLOPs |
| 很长 $C$ | 历史 KV / Attention | 每个候选都放大 KV 读取 |

边界不是由一个固定 batch size 决定。
模型大小、量化、GPU 带宽与算力比、Attention backend 和并行方式都会移动 Roofline 转折点。

因此 $t_T(B,C)$ 与 $t_V(B_V,C)$ 必须在目标工作负载上测量。
不能从 $B=1$ 的比例外推到饱和并发。
## 6. 反转算例一：单请求赚，高并发亏
先看统一教学点：

$$B=1,\quad \mathbb E[L]=3,\quad t_T=10\text{ ms}$$
且：

$$t_D+t_V+t_O=3+12+1=16\text{ ms}$$
因此：

$$S_{\text{decode}}=\frac{3\times10}{16}=1.875$$
单请求下，Target Decode 的权重搬运尚未被 batch 摊薄，Verify 可以利用空闲算力。

现在保持同一个 $K=4$ 和同一存活率向量，但负载升到 $B=64$。
假设该负载下测得：

$$t_T(64,C)=15\text{ ms}$$
虽然这次 batch step 比 $B=1$ 的 $10\text{ ms}$ 更长，但它同时推进 64 个真实 Token，单位 Token 的权重摊销已经明显更好。
以及：

$$t_D=8\text{ ms},\quad t_V=43\text{ ms},\quad t_O=3\text{ ms}$$
存活率没变，所以仍有 $\mathbb E[L]=3$。
新的速度比为：

$$S_{\text{decode}}\approx\frac{3\times15}{8+43+3}=\frac{45}{54}\approx0.833$$
同一个 Proposal 从 $1.875\times$ 加速反转为约 16.7% 变慢。
原因不是候选突然变差，而是普通 Decode 已经被 64 个请求高效摊薄；Verify 再扩宽到约 $B_V=256$，主要增加计算和 Attention 工作。

这就是“单请求赚、高并发亏”的典型反转。
它要求运行时按 $B$ 观察收益，而不是把静态接受率当开关。
## 7. Continuous Batching 怎样改变机会成本
Continuous Batching 在每个调度轮次混合处于不同阶段的请求。
普通 Decode 请求通常各消费一个新 Token 位置，Prefill 请求则可能消费一个多 Token chunk。

投机请求一轮希望调度多个候选位置。
单链近似下：

$$B_V\approx BK$$
树式候选或变长 Proposal 会使 $B_V$ 更不规则。
这些候选位置必须与其他请求的 Decode、Prefill 和恢复工作共享有限 Token Budget。

### 7.1 候选占据的不是空白名额
在低负载时，GPU 确有空闲，额外候选主要利用闲置资源。
在高负载时，每个候选都可能排挤：

- 另一个请求的真实下一个 Token；
- 新请求的 Prefill；
- Chunked Prefill 的下一段；
- 长尾请求的推进机会。

所以高并发下应比较“候选 Token”与“可直接交付的真实 Token”的机会成本。

### 7.2 变长轮次造成 shape 波动
不同请求可能拥有不同 $K$，也可能在 N-gram 未命中时没有候选。
候选树的节点数还会随上下文变化。
这会改变 padding、图执行 shape、Attention metadata 与每轮 $B_V$。

### 7.3 请求完成会移动边界
批处理开始时 $B$ 可能很大，普通 Decode 已经高效，较小 $K$ 或关闭投机更合适。
短请求陆续结束后，剩余 $B$ 下降，投机又可能进入 memory-bound 甜点区。

因此最优深度不是模型启动时的永久常量，而是负载状态的函数。
## 8. 候选 KV 与显存容量
Target Verify 每处理一个候选节点，都会计算该节点对应的 K/V。
这些 K/V 在接受结果出来前只是暂存状态。
最终只有被提交路径对应的状态能进入后续已确认前缀，其余候选必须回收或覆盖。

候选 KV 带来两类成本。

### 8.1 轮次成本
分配 slot、写入、标记接受前缀和回收拒绝后缀都会进入 $t_O$。
若 block 粒度大于实际候选长度，还可能有块内碎片。

### 8.2 峰值容量
即使被拒绝节点很快回收，Verify 执行时仍需要容纳它们。
峰值近似随 $B_V$、层数、KV head 数、head dimension 和 KV dtype 增长。
树的祖先逻辑可共享，但每个新节点自己的 K/V 不是免费的。

独立 Draft 还要占用 Draft 权重与 Draft KV。
Self-Draft 可能占用附加权重、特征缓冲和树 workspace。
N-gram 不加载第二模型，也仍要承担 Target 候选 KV。

显存机会成本可写成一个决策问题：

```text
把显存给 Draft / 候选 workspace，降低部分请求 TPOT
还是
把显存给 Target KV，提高最大并发与可服务上下文？
```

如果额外显存使最大稳定 $B$ 下降，单请求延迟收益可能被容量损失抵消。
因此“启动时能装下”远不是收益成立的充分条件。
## 9. 反转算例二：接受率高，Draft 仍太贵
考虑仍为 $B=1$、$K=4$、$t_T=10\text{ ms}$ 的 Target。
换用一个更强但更昂贵的独立 Draft，得到很高的存活率：

$$(s_1,s_2,s_3,s_4)=(0.95,0.90,0.85,0.80)$$
于是：

$$\mathbb E[A]=3.50,\quad \mathrm{AR}=0.875,\quad \mathbb E[L]=4.50$$
若 Verify 与其余成本为：

$$t_V=12\text{ ms},\quad t_O=1\text{ ms}$$
但生成四个候选的 Draft 总成本达到：

$$t_D=34\text{ ms}$$
则普通 Target 生成期望 4.5 个 Token 约需：

$$\mathbb E[L]t_T=4.5\times10=45\text{ ms}$$
投机轮次却需：

$$t_D+t_V+t_O=34+12+1=47\text{ ms}$$
因此：

$$S_{\text{decode}}\approx\frac{45}{47}\approx0.957$$
尽管 $\mathrm{AR}=87.5\%$，结果仍约慢 4.3%。
高接受只说明 Proposal 与 Target 匹配，不说明获得这些候选的成本合理。

这个反转还说明“Draft 越强越好”并不成立。
更小但略低接受的 Draft，或轻量 Self-Draft，可能因显著降低 $t_D$ 得到更低单位提交成本。
## 10. TTFT、TPOT 与 Goodput 为什么会分叉
投机最直接缩短的是 Decode 中 Target 串行轮数，所以 TPOT 最可能改善。
但服务指标还经过排队、Prefill、调度和容量四层放大。

### 10.1 TPOT 改善而 TTFT 变差
Verify 为每个已有请求调度多个候选，可能占用本轮 Token Budget。
新请求的 Prefill 被推迟，排队时间增长。
于是老请求输出更快，新请求却更晚看到首 Token。

### 10.2 平均延迟改善而 P99 变差
重复性强的请求有高 $s_i$，能快速完成。
开放文本、长上下文或低匹配请求承担额外 Proposal 和 Verify，却只提交接近一个 Token。
平均值被快请求改善，尾部却被慢请求拉长。

### 10.3 Tokens/s 上升而 Goodput 下降
系统可能在低优先级请求上产生大量候选计算，同时挤压高优先级请求的 TTFT。
总交付 Token 仍增加，但满足 SLO 的请求数减少。

### 10.4 TPOT 改善而容量下降
Draft 权重与候选 workspace 挤压 Target KV，使最大并发下降。
低负载体验更好，流量高峰却更早进入排队或 OOM 边缘。

因此服务评估必须同时观察：

- TTFT 的 P50 与尾部；
- TPOT 的 P50 与尾部；
- 饱和吞吐；
- 满足联合 SLO 的 Goodput；
- 最大稳定 $B$ 与显存峰值。

投机是否上线，是多目标约束问题，不是一个平均加速比的判断。
## 11. 上下文、量化与并行怎样移动边界
### 11.1 上下文长度 $C$
$C$ 增大时，Prefill 在端到端时间中的占比通常提高。
投机只优化 Decode，整体收益因此被 Prefill 稀释。

同时，每个候选 query 要读取更长历史 KV，$t_V(B_V,C)$ 更容易由 Attention 带宽主导。
独立 Draft 也要维护更长的 Draft KV，N-gram/Suffix 的索引范围也会增长。

### 11.2 Target 量化
权重量化减少普通 Decode 的权重字节，使 $t_T$ 下降。
投机原本通过摊薄权重读取获得的空间可能缩小，Verify 则可能更早转为 compute-bound。

量化也会释放显存，可能容纳更多 Target KV 或 Draft。
所以量化与投机的收益不能直接相乘，必须重新测 $t_T$、$t_V$ 和容量。

### 11.3 Draft 量化
Draft 量化可能降低 $t_D$ 和额外显存，但也可能改变 $q$。
若逐位置存活率下降，节省的 Draft 时间未必能抵消 $\mathbb E[L]$ 损失。

### 11.4 Tensor Parallel
Target TP 的每个 step 包含跨卡通信。
投机减少 Target 串行轮数，可能减少通信轮次；更宽 Verify 又会增加每轮工作。

若 Draft 同样使用 TP，$K$ 个 Draft step 的 collective 可能吞掉小模型计算收益。
若 Draft 只在单卡执行，候选与 Proposal 概率又要送到 Target ranks。
这些时间分别进入 $t_D$ 与 $t_O$。

### 11.5 MoE 与其他并行
候选 Token 会触发专家路由和 all-to-all。
被拒候选的专家计算仍真实发生，高接受率也不能消除旁支成本。
不同并行组合会改变 $t_V$ 与通信占比，不能从稠密单卡结果外推。
## 12. 怎样判断 K 是否过深
从深度 $K$ 增加到 $K+1$，期望提交长度只增加：

$$\Delta\mathbb E[L]=s_{K+1}$$
设新增候选使轮次成本增加 $\Delta t$。
新深度值得保留的边际条件是：

$$\frac{t_{\text{round}}+\Delta t}{\mathbb E[L]+s_{K+1}}<\frac{t_{\text{round}}}{\mathbb E[L]}$$
整理后得到：

$$\frac{\Delta t}{s_{K+1}}<\frac{t_{\text{round}}}{\mathbb E[L]}$$
含义是：新增深度每带来一个期望提交 Token 的成本，必须低于当前平均单位提交成本。

这条边际判断同时解释：

- 深处 $s_i$ 接近 0 时应减小 $K$；
- 更便宜的 Proposal 可以支持更深候选；
- 长 $C$ 使每个新增 Verify query 更贵；
- 大 $B$ 使候选占用更多系统机会；
- 树增加的旁支也应接受类似的边际审视。

实际系统可以根据近期 $s_i$、当前 $B$、$C$、显存与 SLO 动态改变 $K$。
动态策略的目标不是永远猜更多，而是在负载变化时保持单位提交成本最低。
## 13. 决策边界与限制
适合优先尝试投机的条件通常是：

- 普通 Decode 在目标 $B$ 下明显 memory-bound；
- 输出足够长，Decode 占端到端时间的较大部分；
- Proposal 的 $t_D$ 小，且前几位 $s_i$ 高；
- $B_V$ 尚未把 Verify 推到 compute/attention-bound；
- 额外显存不会破坏并发容量；
- 业务更重视交互 TPOT，而非极限饱和吞吐。

应减小 $K$ 或关闭投机的信号包括：

- $B$ 增大后 $S_{\text{decode}}\le1$；
- 深处 $s_i$ 很低；
- $t_D$ 占轮次成本过高；
- 长 $C$ 让 Verify 受 Attention 限制；
- 候选 KV 或 Draft 权重挤压容量；
- TTFT、P99 或 Goodput 违反 SLO。

严格采样保证 Target 分布，不保证性能。
近似验收可能改变质量，也同样不能绕过成本不等式。
## 总结
- 投机收益的统一条件是 $t_D+t_V+t_O<\mathbb E[L]t_T$，接受率本身不是加速比。
- 低 $B$、较短 $C$ 的 memory-bound Decode 最有利，因为 Verify 可以摊薄 Target 权重读取。
- 随 $B$ 或 $C$ 增大，Verify 会转向 compute-bound 或 attention-bound，收益可能反转。
- Continuous Batching 让候选与其他请求的真实 Token、Prefill 共享预算，单请求加速不等于高并发吞吐提高。
- 候选 KV、Draft 权重和 workspace 同时影响轮次时间与最大服务容量。
- 两个反转算例分别说明：相同接受率在高并发下会亏，以及高接受率也可能被昂贵 Draft 抵消。
- 最终决策必须联合观察 TTFT、TPOT、Goodput、显存、并发与逐位置存活率。
