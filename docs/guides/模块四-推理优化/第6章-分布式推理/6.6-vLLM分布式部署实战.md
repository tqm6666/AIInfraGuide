## 1. 三个并行参数的含义

| 参数 | 作用 | 典型约束 |
|---|---|---|
| `--tensor-parallel-size` / `TP` | 层内切分宽度 | 整除注意力头/KV 头等模型约束；优先 ≤ 单机 GPU 数 |
| `--pipeline-parallel-size` / `PP` | 层段数 | 总层数可切；跨节点扩展主力 |
| `--data-parallel-size` / `DP` | 副本数 | 复制整实例，扩吞吐 |

GPU 总数需满足：

\[
\#GPU \ge TP \times PP \times DP
\]

（MoE 若启用 EP，再按文档计入专家并行度。）

🔑 **核心概念**：这三个旋钮对应三种完全不同的扩展轴——**切层内、切层段、复制实例**。设错轴，会出现"能启动但更慢"或"启动即 OOM"。

## 2. 单机多卡：先打通 TP

```bash
# 示例：8 卡装 70B
vllm serve meta-llama/Llama-3.1-70B-Instruct \
  --tensor-parallel-size 8 \
  --gpu-memory-utilization 0.90
```

Python 等价：

```python
from vllm import LLM

llm = LLM(
    model="meta-llama/Llama-3.1-70B-Instruct",
    tensor_parallel_size=8,
    gpu_memory_utilization=0.90,
)
```

启动后立刻检查：

1. 日志里 world size / TP size 是否为 8；
2. `nvidia-smi` 八张卡是否都有相近显存占用；
3. 用短 Prompt 跑通一次生成，确认不是"只在 cuda:0 上跑起来的假多卡"。

📌 **关键点**：单机 TP 是分布式的单元测试。单机都切不匀、跑不通，不要急着上多机。

## 3. 多机：TP × PP

假设 2×8 卡，模型需要跨机：

```bash
# 概念示例：具体多节点启动方式以当前 vLLM 文档为准
# （Ray 集群就绪后）
vllm serve <model> \
  --tensor-parallel-size 8 \
  --pipeline-parallel-size 2
```

放置目标：

- 节点 A：PP stage 0 的 TP=8；
- 节点 B：PP stage 1 的 TP=8。

验证重点从"能不能 generate"升级为：

1. rank → node 映射是否符合上表；
2. 段间通信是否走预期网卡；
3. 对比 `PP=1`（若有更大单机）或更小模型代理实验的延迟。

💡 **提示**：多节点第一次建议用**小模型 + 同并行度**打通初始化与 generate，再换大权重，避免每次失败都重新下载/加载数十分钟。

## 4. 横向扩展：DP

当单实例（某组 TP/PP）已稳定，吞吐不够时：

```bash
vllm serve <model> \
  --tensor-parallel-size 4 \
  --data-parallel-size 2
```

含义是：两套 `TP=4` 副本（需 8 GPU）。也可以在 K8s/服务网格层复制多个独立 `vllm serve`，那是更广义的 DP。

注意：

- DP 不会降低单副本显存；
- 要在负载均衡层关注前缀亲和与长连接粘性；
- 验证时应看**系统总 QPS** 与 **P99 延迟**，而不是单个副本的表面繁忙。

## 5. 验证清单：显存、拓扑、性能

### 5.1 显存分布

| 检查项 | 期望 |
|---|---|
| 各 TP rank 显存 | 大致接近（允许少量不均） |
| 提高 TP 后单卡权重占用 | 近似下降 |
| 开启 DP 后 | 出现多组相似的显存镜像 |

若只有 GPU0 爆满、其余空闲，多半并行没有真正启用。

### 5.2 拓扑与通信

```bash
nvidia-smi topo -m          # 看 NVLink 连接
# 必要时：
NCCL_DEBUG=INFO            # 观察是否走对网卡/IB
```

确认：

- TP 组内是否在 NVLink 域；
- 跨节点是否只有 PP/DP 预期中的流量。

### 5.3 性能

用固定负载对比配置（同一模型、同一输入分布）：

| 指标 | 关注 |
|---|---|
| TTFT P50/P95 | Prefill 是否因 TP 受益 |
| TPOT P50/P95 | Decode 是否被通信拖慢 |
| 输出 Token 吞吐 | 系统级 tokens/s |
| 请求成功率 | 有无 OOM/超时 |

⚠️ **注意**：**能 serve 不等于配置正确。** 错误的跨节点 TP 也能吐 Token，只是 TPOT 惨不忍睹。

## 6. 常见错误配置

| 错误 | 后果 | 纠正 |
|---|---|---|
| `TP` > 单机 GPU 且无足够跨机带宽 | 延迟崩 | 降 TP，升 PP/换机器 |
| 只加 `DP` 想解决装不下 | 每副本仍 OOM | 先 TP/PP |
| `TP×PP×DP` > 实际 GPU | 启动失败 | 对齐资源 |
| 忽略头数整除约束 | 初始化报错 | 调整 TP 度 |
| 多节点网卡选错 | hang 或极慢 | 设 NCCL 网卡变量 |
| 未做放置约束 | 隐性跨机 TP | Ray Placement / 手动钉卡 |

## 7. 推荐实验路径

按下面顺序做，认知成本最低：

```text
1) 单卡小模型 baseline（正确性）
2) 单机 TP=2/4/8（看显存与 TPOT）
3) 固定总卡数对比：TP=8 vs TP=4×PP=2（同机模拟或真多机）
4) 单实例达标后加 DP=2（看 QPS 与 P99）
5) 记录一份「配置 → 指标」表，作为后续容量规划基线
```

示例记录表：

| 配置 | GPU | TTFT P95 | TPOT P95 | tokens/s | 备注 |
|---|---|---|---|---|---|
| TP8 PP1 DP1 | 8 | | | | 同机 |
| TP8 PP2 DP1 | 16 | | | | 两机 |
| TP8 PP1 DP2 | 16 | | | | 两副本 |

把表格填完，6.1 的选型原则就会从"口头正确"变成"数据正确"。

## 📝 总结

- vLLM 用 `tensor/pipeline/data-parallel-size` 分别控制切层内、切层段、复制实例。
- 实战顺序：**单机 TP → 多机 TP×PP → 达标后 DP**，并用小模型先打通多节点。
- 验证分三层：显存是否均匀、拓扑/通信是否走对、TTFT/TPOT/吞吐是否达预期。
- 最常见的性能陷阱是隐性跨节点 TP 与只看能否启动不看尾延迟。
