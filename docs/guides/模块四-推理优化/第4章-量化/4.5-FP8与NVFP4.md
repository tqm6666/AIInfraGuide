## 1. 为什么需要低比特浮点

整数量化依赖 scale 把实数拽到固定网格；遇到宽动态范围时，要么被 outlier 绑架（[4.2](./4.2-W8A8-SmoothQuant.md)），要么把粒度切得很细并配套复杂算法。**低比特浮点**把一部分动态范围能力做进格式本身：用指数位表达量级，用尾数位表达精度。

对 LLM 而言，这意味着：

- 激活/KV（推理）更不容易"一夜之间不可量化"；
- 硬件可以提供原生 Tensor Core 吞吐，而不是只做压缩存储；
- 工具链逐步从"研究特性"变成"引擎默认路径之一"。

📌 **关键点**：FP8/FP4 的战略意义是 **格式 + 硬件 + 软件栈** 一起到位；只有 checkpoint 而没有 Kernel，或只有硬件而没有稳定量化配方，都形不成产品能力。

## 2. 硬件前提：能跑不等于能加速

先把前提写死，避免"改个 dtype 就期待翻倍"：

| 目标 | 大致硬件前提 | 没有前提时常见结局 |
|---|---|---|
| FP8 GEMM 加速 | Hopper（如 H100）等对 FP8 Tensor Core 支持良好的 GPU；软件栈启用对应 Kernel | 能加载/能算，但走模拟或高精路径，墙钟不美 |
| FP8 KV | 引擎实现 + 合适 GPU 世代；与 Attention 后端对齐 | dtype 变了，读路径仍慢或质量不稳 |
| NVFP4/MXFP4 | Blackwell 等新硬件 + 匹配的驱动/引擎版本 | 旧卡上不可假设同等加速 |

⚠️ **注意**：**可移植加载**与**峰值加速**是两件事。INT4 权重往往在多代 CUDA GPU 上"至少能跑"；FP8/FP4 的峰值收益更绑硬件世代。集群主力卡决定你该把精力投哪条栈。

## 3. FP8：E4M3 与 E5M2

常见 FP8 有两种布局（名称即指数/尾数位数）：

| 格式 | 布局直觉 | 动态范围 | 精度 | 常见用途 |
|---|---|---|---|---|
| **E4M3** | 4 位指数 + 3 位尾数 | 较小 | 相对更高 | 推理权重/激活很常用 |
| **E5M2** | 5 位指数 + 2 位尾数 | 更大 | 更粗 | 更偏训练中需要更大范围的张量 |

没有绝对冠军：推理里若数值范围可控，**E4M3** 往往因更高尾数精度更受欢迎；若某种张量更容易溢出/下溢，才会更看重 E5M2 的范围。

🔑 **核心概念**：**E4M3 偏精度，E5M2 偏范围。** 选型是数值分布问题，不是"版本号越高越好"。

此外，FP8 实务几乎必然伴随 **缩放（scaling）策略**——块级、张量级或按硬件支持的微缩放——以把数值塞进可表示范围。看到 FP8 方案时，要同时问："scale 怎么存、怎么更新、Kernel 是否融合"。

## 4. Hopper 上的推理含义

Hopper（如 H100）原生强化了 FP8 矩阵乘能力。对推理团队，这意味着一条极具吸引力的路径：

- 权重 FP8 + 激活 FP8 的 W8A8 风格（这里的 "8" 是浮点 8-bit）；
- KV Cache 也可走 FP8（见 [4.4](./4.4-KV-Cache量化.md)）；
- 相对纯 INT4 weight-only，常在**质量与吞吐之间更均衡**，尤其当你有 Hopper 且不想维护太复杂的 INT4 工具链时。

```mermaid
flowchart LR
    A["BF16/FP16 基线"] --> B["FP8 权重/激活"]
    B --> C["FP8 Tensor Core GEMM"]
    A --> D["可选：FP8 KV Cache"]
    D --> E["更长上下文 / 更高并发"]
    C --> F["端到端吞吐？实测"]
    E --> F
```

💡 **提示**：FP8 推理不是"改个 dtype 就完成"。需要量化配方（静态或延迟缩放）、可靠的 checkpoint、以及引擎对融合 Kernel 的支持。vLLM 等框架已提供 FP8 相关后端，但模型族覆盖与性能仍需实测。

## 5. Blackwell：NVFP4 与 MXFP4

Blackwell 一代把竞争推进到 **4-bit 浮点** 生态。你会在资料里看到相近但并不完全相同的名字：

- **NVFP4**：NVIDIA 在其软件/硬件叙事中强调的 4-bit 浮点能力与对应支持路径；
- **MXFP4**：与微缩放（micro-scaling）家族相关的 4-bit 浮点格式思路，强调更细的共享缩放以保住精度。

对学习者，不必先死记每个比特字段，先抓住工程含义：

1. **比 FP8 更省带宽与显存**，理论上挑战 INT4 的容量收益；
2. **比 INT4 更希望保留浮点式动态范围**，以降低对重型 PTQ 算法的依赖；
3. **强绑定新硬件与新软件栈**——在旧 GPU 上不可假设"有 NVFP4 就有同样加速"。

⚠️ **注意**：FP4 生态仍在快速演进，格式命名、中间表示、引擎开关在半年内都可能变化。写进生产方案时，请以你目标驱动与引擎版本的发布说明为准，把本文当作选型地图而非 API 手册。

## 6. 纸面 FLOPS 与业务吞吐

厂商幻灯片常见"FP8 相对 FP16 峰值算力约 2×"一类表述。把它直接当成业务承诺，会踩坑：

| 纸面数字在说什么 | 业务 tok/s 还取决于 |
|---|---|
| Tensor Core 峰值 FLOPS | 是否 Memory Bound（Decode 常是） |
| 理想大矩阵利用率 | batch、序列长度、Kernel 融合 |
| 单算子 microbench | 调度、KV、采样、通信、Python 开销 |
| 某模型官方 blog 加速比 | **基线精度、负载（并发/长度）、版本** 是否一致 |

**教学对照（数量级直觉，非某一跑分）**：若 Decode 阶段 70% 时间花在读权重/KV，30% 花在可被 FP8 加速的算术上，即便算术部分理想加速 2×，端到端加速也只有：

$$
\frac{1}{0.7 + 0.3/2} \approx 1.18\times
$$

取舍句：**纸面 FLOPS 是上限叙事；Memory Bound 的服务里，FP8 更常通过"减流量 + 偶尔抬算术"改善 TPOT/吞吐，幅度要用你的负载实测，而不是用峰值倍数外推。**

## 7. 和 INT8/INT4 路线如何并存

一张对照表帮助把第 4 章串起来：

| 路线 | 典型硬件 | 主要收益 | 主要风险 |
|---|---|---|---|
| INT4 weight-only（GPTQ/AWQ） | 通用 CUDA GPU | 权重显存大降 | 质量依赖算法；算力加速看 Kernel |
| INT8 W8A8 + SmoothQuant | 支持 INT8 Tensor Core | 计算与带宽 | Activation Outlier |
| FP8 | Hopper+（及部分其它） | 质量/吞吐较均衡 | 需要缩放与引擎支持 |
| NVFP4/MXFP4 | Blackwell 等新硬件 | 更激进的低比特浮点 | 生态与可移植性 |

它们不是互斥：生产上常见 **权重一种格式、KV 另一种格式**（例如 AWQ 权重 + FP8 KV），前提是引擎组合矩阵允许，并做质量回归。

📌 **关键点**：硬件换代时，优先问"我的集群明年主力卡是什么"，再决定是把精力投入 INT4 工具链还是 FP8/FP4 栈。

## 8. 落地时的现实约束

1. **可移植性**：INT4 权重在多代 GPU 上更容易"至少能跑"；FP8/FP4 的峰值收益更绑硬件。
2. **模型供应**：有现成高质量 FP8 权重，往往比自己从 BF16 现场量化更稳。
3. **观测**：用 profiler 确认进入了预期 GEMM；否则你可能只是在用 FP8 存储、却以更高精度计算。
4. **评测**：对推理任务，除了吞吐，还要看长上下文与工具调用——低比特浮点同样可能在尾部行为上露怯。

```python
# 示意：vLLM 加载 FP8 模型（格式名/参数随版本变化，以当前文档为准）
from vllm import LLM

llm = LLM(
    model="your-org/llama-3.1-8b-fp8",
    quantization="fp8",
)
```

## 9. 从 FP16 迁到 FP8/FP4 的演进路径

若团队还在 FP16/BF16，不建议直接跳到 NVFP4。更稳的台阶是：

1. **基线**：BF16/FP16 + 完善的质量/性能看板；
2. **Hopper 上试 FP8 权重（或权重+激活）**：验证 Kernel 与业务指标；
3. **长上下文再加 FP8 KV**：把容量收益从权重扩展到状态；
4. **Blackwell 就绪后评估 NVFP4/MXFP4**：用同一套评测集做世代对比，而不是只看峰值 FLOPs。

| 阶段 | 成功标准 |
|---|---|
| FP8 权重 | 质量过线，GEMM 命中 FP8，**端到端**吞吐相对同负载基线有增益 |
| FP8 KV | 同显存下上下文或并发提升，长文任务不崩 |
| FP4 | 在目标卡上端到端优于 FP8，且工具链可复现 |

💡 **提示**：迁移的隐藏成本是**权重供应链**——谁负责出品、如何签名校验、如何回滚。格式越新，越要把供应链与引擎版本绑在一起做变更管理。同一阶段内建议保留 **A/B 开关**：新会话走 FP8，出问题可瞬时切回 BF16 池。

## 10. 权衡与可用性

| 选择 | 收益 | 代价 / 可用性陷阱 |
|---|---|---|
| FP8 计算 | 有 Hopper 时质量/吞吐常较均衡 | 无对应 Tensor Core 时收益可能很薄 |
| FP8 KV | ~2× KV 容量（相对 FP16） | 长上下文质量需单独过线 |
| NVFP4/MXFP4 | 更激进密度 | 生态窗口期短，可移植性差 |
| 死磕纸面 2× FLOPS | 汇报好看 | 线上 Memory Bound 时预期管理失败 |
| 统一低精度栈 | 运维简单 | 单点格式风险；回滚要成套准备 |

适用：集群已有或明确将上 Hopper/Blackwell，且愿意做 Kernel 命中与业务双评。  
不适用：把 FP8/FP4 写成"全面优于 INT4"的默认答案——在通用 GPU、权重装不下为唯一主诉时，INT4 weight-only 往往仍是更务实的第一刀。

---

## 📝 总结

- 低比特浮点用指数位换动态范围，缓解整数量化对 outlier 与复杂 scale 的依赖。
- 硬件前提要写清：能加载 ≠ Tensor Core 加速；FP4 强绑 Blackwell 类新栈。
- FP8 中 E4M3 偏精度、E5M2 偏范围；推理常优先考虑 E4M3 + 合适缩放。
- 纸面 FLOPS 不是业务吞吐；Memory Bound 下端到端加速可能远小于峰值倍数。
- 迁移宜分台阶：BF16 基线 → FP8 计算 → FP8 KV → 再评估 FP4，并管好权重供应链与回滚。
