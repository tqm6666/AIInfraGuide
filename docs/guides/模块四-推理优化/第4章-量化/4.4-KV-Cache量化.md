## 1. 问题：权重固定，KV 按请求增长
模型权重是每个副本的固定成本。
KV Cache 则是每个活跃请求的状态，随已处理 token 数线性增长。

在第 $l$ 层，新 token 生成：
$$
K_l=X_lW_l^K,\qquad V_l=X_lW_l^V
$$
后续 token 的 Query 会反复读取历史 K/V：
$$
A_l=\operatorname{softmax}\left(\frac{Q_lK_l^\top}{\sqrt{d_h}}\right)
$$
$$
O_l=A_lV_l
$$

不缓存 K/V，就要为全部历史 token 重算投影。
KV Cache 用显存换计算；KV 量化再用精度换回一部分容量和读取带宽。

它可能改善：
- 同卡可缓存的 token 总数；
- 最大上下文长度；
- 稳定并发；
- 长上下文 Decode 的 KV 读取流量。

它也新增：
- 新 KV 写入时的量化；
- 每次 Attention 读取时的反量化或低精度消费；
- scale、残差窗口和分页元数据；
- 对 Attention backend 的格式要求；
- 会被未来所有 token 重用的状态误差。

因此 KV 量化与权重量化不是“同一模型再少几 bit”。
前者压缩按请求增长的状态，后者压缩所有请求共享的固定参数。

## 2. 先算每 token 的 KV 账
忽略分页与 scale，单个序列的 KV 数据本体近似为：
$$
M_{\text{KV}}
=L\times T\times2\times H_{kv}\times D_h\times\frac{b_{kv}}8
$$

其中：
- $L$：Transformer 层数；
- $T$：已缓存 token 数；
- 2：Key 与 Value 两份；
- $H_{kv}$：KV head 数；
- $D_h$：每个 head 的维度；
- $b_{kv}$：每个 KV 元素的位宽。

每 token 成本为：
$$
m_{\text{token}}
=L\times2\times H_{kv}\times D_h\times\frac{b_{kv}}8
$$

总容量应对所有活跃序列求和：
$$
M_{\text{batch}}
=m_{\text{token}}\sum_{r=1}^{R}T_r
$$

不能用“最大长度 × 最大并发”代替真实 token 分布做性能预测，但它可作为保守容量上界。

MHA 中通常 $H_{kv}=H_q$。
GQA/MQA 让多个 Query heads 共享较少的 KV heads，因此在量化之前就已经减少 KV。

Tensor Parallel 下，每个 rank 的 KV 是否简单除以 TP，取决于 KV heads 怎样切分。
当 KV heads 少于 TP degree 时，某些实现会复制而不是继续切分。
容量应以运行时实际 cache shape 为准。

## 3. 7B 与 70B 手算
沿用本章教学结构：

```text
7B：  L=32，Hkv=32，Dh=128，MHA
70B： L=80，Hkv=8， Dh=128，GQA
```

### 3.1 7B BF16
$$
m_{\text{7B}}
=32\times2\times32\times128\times2
=524{,}288\ \text{bytes/token}
$$
即：
$$
m_{\text{7B}}=512\ \text{KiB/token}
$$
4096 token 的单序列 KV 本体为：
$$
512\ \text{KiB}\times4096=2\ \text{GiB}
$$

若改为 8-bit，数据本体约 1 GiB；若改为 2-bit，约 256 MiB。
这只是位宽比例，不包含 scale 和对齐。

### 3.2 70B BF16
$$
m_{\text{70B}}
=80\times2\times8\times128\times2
=327{,}680\ \text{bytes/token}
$$
即：
$$
m_{\text{70B}}=320\ \text{KiB/token}
$$
4096 token 的单序列本体为：
$$
320\ \text{KiB}\times4096=1.25\ \text{GiB}
$$

70B 参数更多，KV 却比教学 7B 小，是因为它只有 8 个 KV heads。
参数规模不能代替 $L,H_{kv},D_h$ 做 KV 预算。

### 3.3 并发算例
20 个 7B 请求都达到 8192 token 时，BF16 KV 数据本体为：
$$
20\times8192\times512\ \text{KiB}=80\ \text{GiB}
$$
8-bit 理论本体约 40 GiB，2-bit 理论本体约 10 GiB。

真实可承载请求数还受长度分布、分页块利用率、前缀共享、调度保留和安全余量影响。
所以“八倍原始压缩”不能直接翻译为“八倍并发”。

## 4. KV 误差怎样进入 Attention
令量化恢复后的缓存为：
$$
\hat K=K+E_K,\qquad \hat V=V+E_V
$$

### 4.1 Key 误差先改变 logits
原 logits：
$$
Z=\frac{QK^\top}{\sqrt{d_h}}
$$
量化后的变化：
$$
\Delta Z=\frac{QE_K^\top}{\sqrt{d_h}}
$$

$E_K$ 会被当前 Query 投影，并作用于每个历史位置。
若两个候选 token 的 logits 很接近，小变化也可能通过 Softmax 改变注意力排序。

Softmax 对所有位置共同归一化。
因此 Key 误差不是仅作用于一个 Value 的局部噪声，而可能重新分配整行注意力权重。

### 4.2 Value 误差进入加权和
记：
$$
\hat A=\operatorname{softmax}(Z+\Delta Z)
$$
则输出差可分解为：
$$
\hat O-O=(\hat A-A)V+\hat AE_V
$$

第一项来自 Key 误差引起的权重变化。
第二项来自量化 Value 被加权求和。

这个分解解释了 K 与 V 为什么可能适合不同量化粒度：
K 决定“看哪里”，V 决定“取回什么”。

### 4.3 误差会跨层和跨生成步传播
第 $l$ 层 Attention 输出进入后续层。
最终 hidden state 又决定下一个 token 的 logits，并生成新的 K/V。

如果采样路径因小误差选中了不同 token，之后的输入序列已经发生离散分叉。
所以长序列误差不能简单写成“单 token 误差 × 序列长度”。

另一方面，历史 KV 不会在每个 Decode step 被重复量化；它通常量化一次、读取多次。
这使 scale 选择错误具有长期影响，也使读带宽节省能被多次兑现。

## 5. 量化粒度为什么 K 与 V 不同
KV 在运行时按 token 到达，既可以沿 token 维共享 scale，也可以沿 channel/head-dimension 共享。

### 5.1 Per-token
一个 token 的一组 K 或 V 元素共享 scale。
优点是 scale 可随 token 幅值变化，在线追加自然。
缺点是若固定通道长期出现 outlier，每个 token 的整组刻度都可能被该通道拉大。

### 5.2 Per-channel
同一 channel 跨 token 共享或分组计算 scale。
它能隔离稳定的通道离群值，却需要观察或缓冲 token 维数据。
在自回归追加场景中，纯粹对完整序列做离线 per-channel 量化不现实。

### 5.3 Per-group / per-head / per-block
把 head dimension 或 token 块切成小组可缩小共享范围。
代价是更多 scale、复杂索引和额外加载。

粒度必须与 Attention Kernel 的 tile 方式一致。
数学上更细的 scale 若导致不连续读取或频繁解码，可能降低系统收益。

### 5.4 K 与 V 的经验结构
KIVI 的观察是：
- Key 更常表现出固定 channel 上的离群结构；
- Value 的离群结构更适合按 token 处理。

因此 K 使用 per-channel 思路、V 使用 per-token 思路。
这不是所有模型上永恒不变的定律，而是该方法基于实测分布作出的非对称设计。

## 6. FP8 KV Cache
FP8 用 8-bit 浮点 code 保存 K/V，常见 E4M3 路线保留指数以覆盖较大动态范围。
相对 BF16/FP16，raw 数据本体约减半，但仍可能配合 scale：
$$
q=\operatorname{FP8}(x/s),\qquad \hat x=sq
$$
scale 可按 tensor、head、block 或实现定义的其他粒度共享；只写“FP8 KV”不足以确定数值语义。

主要优势：
- raw 数据从 2 bytes 降到约 1 byte；
- 相比 2-bit，压缩温和且通常更易保持质量；
- 新硬件和 Attention backend 更可能提供融合路径。

主要限制：
- 写入时仍要选择 scale 并转换；
- E4M3 变体、范围与舍入规则必须匹配；
- 读取是否更快取决于 Attention Kernel；
- 静态 scale 可能因分布失配而饱和。

FP8 KV 适合先解决“容量减半已够用”的问题，不是所有 GPU 上天然加速的开关。

## 7. KIVI 2-bit 的核心机制
KIVI 追求更激进的 2-bit KV，并按分布差异使用非对称粒度：
```text
Key：   per-channel 为核心，隔离通道离群
Value： per-token 为核心，跟随每个 token
```
2 bit 只有 4 个 codes；若整个张量共享 scale，少量 outlier 会让主体失去分辨率，因此还需要分组。

在线 Decode 又不能在单 token 到达时预知未来的 per-channel 范围。
KIVI 用高精度 residual window 保留最近 K/V，但 K 与 V 写入低比特历史的方式不同：
- **Key 批量刷新**：Key 的 per-channel scale 需要同时观察一批 token。Key residual 累积到窗口大小 \(R\) 后，整批 Key 按 channel 分组量化并刷新到低比特缓存，再为后续 Key 建立新的高精度窗口；
- **Value 逐 token 迁移**：Value 采用 per-token 量化，每个 token 向量可独立确定 scale。Value residual 已满时，每到一个新 token，就从队首弹出最老的 Value，按该 token 分组量化并迁入低比特缓存，同时把新 Value 留在高精度队尾。

因此，两条路径虽然都保留最近状态，却不是同一种“窗口满后批量量化”：
```text
最近 token：高精度 residual，便于追加
较老 token：分组 2-bit codes
辅助信息：scale / zero-point 等元数据
```
残差窗口也保护了靠近当前 token 的状态，但会稀释短序列压缩比。

KIVI 的 tuning-free 表示无需重新训练，不表示无需 Kernel 和质量验证。
2-bit 相对 BF16 的 raw 比例为 $1/8$；加入 scales、残差、padding 和 page 元数据后，实际压缩必然更小。

## 8. Kernel、Prefill 与 Decode
### 8.1 写路径
Prefill 一次产生大量 K/V，量化写入可以处理较大的 tile。
Decode 每步只追加少量 K/V，在线求 scale、打包和更新页内位置的固定成本更突出。

若采用 KIVI residual，Decode 先把新 K/V 写入各自的高精度窗口。Key 在窗口达到 \(R\) 时触发 per-channel 批量刷新，形成间歇性块级工作；Value 则在窗口满后逐 token 弹出并按 per-token 粒度迁移，形成持续的小粒度工作。
两条路径都会引入额外状态与延迟，但峰值形态不同：Key 更可能出现周期性刷新尖峰，Value 更接近每步固定迁移成本。

### 8.2 读路径
Decode 的每个 Query 要读取全部有效历史 K/V。
序列越长，读路径越可能受 HBM 带宽限制。

理想 Kernel 会：
1. 按页和 tile 读取压缩 codes 与 scales；
2. 在片上解码；
3. 立即参与 $QK^\top$ 与 $AV$；
4. 不把完整高精度 KV 写回 HBM；
5. 与在线 Softmax 保持数值稳定。

若先把整段 KV 展开，容量可能仍节省，但每步临时带宽与 workspace 会削弱收益。

### 8.3 Prefill/Decode 收支
Prefill 的主要 Attention 工作处理新 token 之间的关系，并写出一次 KV。
KV 量化在此首先增加写入工作，不一定显著缩短计算受限的 Prefill。

Decode 会多次读取同一历史 KV。
一次量化成本可以被未来许多 step 的少读字节摊销，因此长上下文更可能获得带宽收益。

但短上下文、小模型或非 Attention 占主导时，转换成本可能超过节省。

## 9. 与 PagedAttention、长上下文和并发的关系
PagedAttention 解决 KV 的物理分配与碎片，KV 量化改变每个有效元素的 bit；二者作用在不同维度，可以组合。

设 KV 池可用字节为 $M_{\text{pool}}$，每 token 实际占用为 $m_{\text{actual}}$，则理想 token slots 为：
$$T_{\text{slots}}\approx\left\lfloor\frac{M_{\text{pool}}}{m_{\text{actual}}}\right\rfloor$$

$m_{\text{actual}}$ 不只包含 codes，还包含 scale、对齐和 block 内未使用空间。
PagedAttention 的 block size 越大，短尾浪费可能越明显；block 太小又会增加表项和调度成本。

量化后每个 page 的 payload 布局会改变。
Attention backend 必须知道：
- page 的 token 数、codes/scales 排列与最后一页有效长度；
- GQA/TP 下每个 rank 保存哪些 heads，以及 prefix sharing 页的只读语义。

### 9.1 长上下文
更低位 KV 让同一池容纳更多历史 token，但“能放下 128K”不等于“128K 仍能正确检索”。
长上下文质量至少涉及远距离召回、位置敏感任务、多轮一致性和长输出稳定性。

### 9.2 并发
释放出的 slots 可以用于更长单请求，也可以用于更多请求。
两者不能同时把全部收益花两次。

并发增加还会改变调度、batch shape、排队与每请求带宽份额。
最终应报告满足 TTFT/TPOT/P99 门槛的稳定并发，而不是只报告理论 token 数。

### 9.3 前缀共享
Prefix Cache 让相同 token 前缀共享物理 KV page。
量化减少每页字节，前缀复用减少需要多少页；二者也可以叠加。

但 cache identity 必须包含会改变 KV 数值语义的模型 revision、量化格式和 scale 约定。
不同 KV 格式不能因 token 相同而错误共享。

## 10. 容量、带宽与精度取舍
可以把 KV 方案放在三条轴上：

### 10.1 容量
- BF16/FP16：约 16 bit/element，基线简单；
- FP8：约 8 bit codes，raw 容量约减半；
- KIVI 2-bit：约 2 bit codes，raw 压缩激进，但元数据和 residual 占比更大。

### 10.2 带宽
只有 Attention 直接读取压缩布局并片上解码，raw 压缩才可能转为 HBM 节省。
scale 流量、解码指令、访问连续性和 page layout 都会缩小理论比例。

### 10.3 精度
位宽越低，格子越少，对粒度、outlier 和残差策略越敏感。
Key 误差会改变 Attention 权重，Value 误差会改变取回内容；二者需分别检查。

选择顺序应是：
1. 用模型结构和 workload 算出 KV 是否为容量或带宽瓶颈；
2. 核对硬件与 Attention backend 的可用格式；
3. 在可用集合中比较 FP8 与更低位方案的质量；
4. 检查释放容量是否真的提高 SLO 下的并发；
5. 若长上下文质量不过线，保留高精度 KV。

权重量化与 KV 量化可组合，但误差和兼容矩阵也会组合。
组合风险与三层验收在 4.6 收束；完整性能验证回指第 9～11 章。

## 总结
KV Cache 容量随层数、token 数、KV heads、head dimension 和元素位宽线性增长。
GQA/MQA、量化、PagedAttention 与前缀共享分别改变 head 数、每元素字节、分配效率和实际 token 数。

FP8 KV 以较温和的 8-bit 浮点压缩换取容量；KIVI 用 K per-channel、V per-token、分组 2-bit 与高精度 residual 追求更激进压缩。
真实收益取决于 Attention Kernel 能否直接消费压缩页，并必须用长上下文质量和 SLO 验收。
