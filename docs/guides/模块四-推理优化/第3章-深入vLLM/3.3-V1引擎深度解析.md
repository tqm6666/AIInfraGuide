3.2 已经把 vLLM 抽象为 Frontend、EngineCore、Worker 三层，并沿一次请求找到了长期状态与单轮执行的边界。

本节追问：为什么 vLLM 还要从 V0 走向 V1？答案不是“换了一个更快 Kernel”，而是旧的数据流很难继续压缩 Host seam，也很难让调度、缓存和图执行自然组合。

正文讨论稳定设计原则。某个版本的进程数、消息类型或默认开关只适合作为案例，不构成这些原则本身。

## 1. 问题起点：V0 的瓶颈为什么不只在 GPU

V0 已经拥有 PagedAttention、Continuous Batching 等重要能力。V1 不是第一次发明分页 KV，也不能用“旧版什么都没有、新版全部重写”来理解。

变化的根因是：当 GPU Kernel 越来越快，运行时组织工作的方法开始决定设备能否持续收到任务。

### 1.1 阶段分叉会放大组合复杂度

Prefill 和 Decode 的计算形态不同，但它们都在推进请求的 Token 位置。若调度器把它们维护成两套主流程，加入 Chunked Prefill、Prefix Cache、Speculative Decoding 和 Structured Output 后，每个功能都要回答“在哪一套流程生效、二者切换时状态怎样交接”。

假设有 \(p\) 类阶段分支和 \(f\) 个可选功能，潜在交互不是简单的 \(p+f\)，而更接近要检查 \(p\times f\) 组边界。功能继续增加时，正确性测试与维护成本会先于 Kernel 成为瓶颈。

### 1.2 CPU 工作夹在每个短 Decode step 之间

Decode 由许多短迭代组成。每轮都可能包含调度、对象变换、批次构造、设备提交、结果读取、停止判断与输出处理。

当一次 GPU step 只有几毫秒甚至更短时，数百微秒的 Host 工作会重复几百次。它不一定让 CPU 总利用率达到 100%，却可能恰好位于下一次 GPU 提交的关键路径。

### 1.3 全量 Batch 重建重复搬运稳定状态

相邻两个 Decode Batch 往往高度重叠：大多数请求仍在运行，只增加少量 Token，只有少数请求进入或退出。

若每轮把全部请求元数据重新展开、排序、复制到设备，工作量按 Batch 总大小付费，而不是按变化量付费。Batch 越稳定，这种全量重建越浪费。

### 1.4 前端高方差会污染核心循环

Tokenize、Detokenize、协议解析和 Python 对象管理都可能发生长尾停顿。若它们和 Scheduler、设备提交处于同一串行循环，一次复杂模板或垃圾回收就会让 GPU 断粮。

问题不是 CPU 工作“没用”，而是它与设备关键路径的耦合过强。

### 1.5 图执行需要更稳定的形状合同

CUDA Graph 希望重复执行可重放的工作图，编译器也希望看到可优化的张量程序。若 Batch 元数据和控制分支每轮剧烈变化，捕获、填充与 fallback 会抵消图执行收益。

所以 V1 要同时重构状态表示、调度货币和执行接口，才能为后续图优化提供稳定地基。

## 2. 从瓶颈推导 V1 的五条设计原则

V1 可以先看成五条原则，而不是功能列表。

| 观察到的瓶颈 | 设计原则 | 主要机制 | 新代价 |
|---|---|---|---|
| 前端 CPU 方差进入核心循环 | 隔离不同时间尺度 | 多进程与窄消息边界 | IPC、取消竞态 |
| Prefill/Decode 分支膨胀 | 用统一进度表达工作 | Token Budget | Token 不等于精确 FLOPs |
| 相邻 Batch 高度重叠 | 按变化量维护执行状态 | Persistent Batch | 增量一致性 |
| 重复前缀反复 Prefill | 把复用纳入 KV 生命周期 | Prefix Cache | Hash、淘汰、局部性 |
| 短 step 的 Launch 成本显眼 | 稳定并复用执行程序 | Compile / CUDA Graph | 编译时间、Shape 与显存 |

这五条原则共同服务于一个目标：

> 让控制面用更少、更稳定的工作描述下一轮，让数据面尽可能连续执行，同时不丢失请求与资源的正确生命周期。

### 2.1 优化对象从“一次 forward”扩大到“跨轮数据流”

单次 forward 仍然重要，但运行时性能是许多轮串起来的结果。V1 关注的不只是每轮 GPU 用时，也包括两轮之间暴露的 Host seam、元数据流量和状态提交成本。

### 2.2 统一不等于抹去差异

Prefill Token 与 Decode Token 的 FLOPs、访存和延迟影响并不相等。统一 Token 表示是在控制层获得共同货币，不是宣称每个 Token 成本相同。

### 2.3 异步不等于取消依赖

多进程、队列和多 Batch 在途只能移动彼此独立的工作。下一轮若真实依赖上一轮采样结果、KV 写入或释放决定，仍必须在最窄边界同步。

## 3. 多进程隔离：让不同时间尺度解耦

3.2 的三层可以同进程实现，也可以跨进程部署。V1 倾向把前端相关 CPU 工作与 EngineCore 的调度执行循环隔开，其价值来自时间尺度和故障方式，而不是“进程越多越快”。

### 3.1 隔离高方差前端工作

Frontend 可以继续接收连接、模板化、Tokenize 和 Detokenize，EngineCore 则维护更规则的请求状态和设备提交节奏。

当 GPU 执行第 \(t\) 轮时，前端可处理新请求或更早的输出。只要这些工作不修改本轮权威状态，就存在重叠空间。

### 3.2 消息边界迫使所有权清晰

跨进程后，不能依赖任意 Python 对象共享可变引用。入口消息必须表达“新增/取消哪条请求”，输出消息必须表达“哪条请求取得何种进展”。

这种窄合同减少隐式双写，也让请求身份成为跨层不变量。代价是消息 schema 本身需要版本一致，双方对字段语义不能各自解释。

### 3.3 EngineCore 仍是单实例的关键故障域

隔离前端不表示 EngineCore 可无损重启。Waiting/Running、KV 逻辑引用和未交付进度通常仍是内存状态；核心进程失败后，在途请求往往要由上游重试。

多进程缩小污染面，不能替代事务日志、业务幂等或跨副本容错。

### 3.4 IPC 收益取决于可隐藏工作

设一段前端 CPU 工作耗时 \(T_f\)，GPU 执行窗口为 \(T_g\)。只有彼此独立且满足 \(T_f\le T_g\) 的部分，才可能被完整隐藏。

若每个 Token 都要同步跨进程往返，IPC 固定成本会重新进入关键路径。消息合并、异步输出与稳定所有权比“选哪种 socket”更关键。

## 4. 统一 Token Budget：用进度差表达工作

V1 调度器的核心抽象不是先问“这是 Prefill 还是 Decode”，而是问“这条请求距离目标进度还差多少 Token，本轮最多给它多少”。

### 4.1 用目标位置减去已计算位置

对请求 \(i\)，记目标可计算位置为 \(n_i^{\text{target}}\)，已经完成 KV 计算的位置为 \(n_i^{\text{computed}}\)，则需求可抽象为：

$$
d_i
=
\max\left(0,
n_i^{\text{target}}-n_i^{\text{computed}}\right)
$$

本轮实际分配 \(c_i\) 还受全局预算、单请求上限、KV 容量与就绪条件限制：

$$
0\le c_i\le d_i,
\qquad
\sum_i c_i\le B_{\text{token}}
$$

### 4.2 Prefill 是较大的进度差

新请求尚未计算 Prompt 时，目标位置远大于已计算位置，\(d_i\) 很大。若预算不足，Scheduler 只分配一部分，天然形成 Chunked Prefill。

因此 Chunk 不必成为另一套请求类型，它只是本轮截断后的进度增量。

### 4.3 Decode 是较小的进度差

普通 Decode 在已有上下文后通常只需要推进下一位置，\(d_i\) 很小。许多 Running 请求可以一起占据少量 Token Budget，形成连续批处理。

### 4.4 Speculative Decoding 扩大候选区间

投机解码可能一次验证多个候选，所以目标进度差可大于 1。计划的 Token 数代表要计算或验证的候选工作，最终接受进度却可能更小。

这要求“计划进度”和“提交进度”分开；统一预算简化 admission，却没有消除回滚。

### 4.5 Token Budget 是近似货币

一个长 Prefill Token 和一个单序列 Decode Token 对设备的边际成本并不相同，模型结构、Batch 形状和 Attention Backend 也会改变成本。

Token Budget 的价值是提供稳定、可切分的控制量。若需要严格 SLO，还要结合实测服务时间、序列数、KV 和请求优先级。

## 5. Persistent Batch：从全量重建到增量维护

统一调度告诉 Worker 本轮推进什么，Persistent Batch 解决“相邻两轮高度相似时，为什么还要重建全部设备输入”。

### 5.1 利用相邻 Batch 的集合重叠

记第 \(t\) 轮成员集合为 \(S_t\)，下一轮为 \(S_{t+1}\)。通常：

$$
|S_t\cap S_{t+1}|
\gg
|S_t\triangle S_{t+1}|
$$

也就是保留成员远多于进入和退出成员。

Persistent Batch 在设备侧或执行侧保留稳定槽位与元数据，只传达：

- 哪些请求新增；
- 哪些请求移除；
- 哪些请求进度变化；
- 哪些 Block Table 或约束需要更新。

### 5.2 工作量从 Batch 大小转向变化量

全量重建的 Host 工作可粗略记为 \(O(|S_t|)\)。

增量维护更接近：

$$
O(|A_t|+|R_t|+|U_t|)
$$

其中 \(A_t\)、\(R_t\)、\(U_t\) 分别表示新增、移除和必须更新的槽位。高重叠 Decode 负载下，变化量远小于总 Batch。

### 5.3 槽位不是请求

设备槽位可以被复用，请求身份不能被复用。旧请求退出、同一槽位放入新请求时，Token 位置、Block Table、采样状态和输出映射必须一起更新。

若只改了 ID 没改 KV 映射，会读到旧请求状态；若只清元数据没处理在途结果，迟到输出可能写入新请求。

### 5.4 Persistent 不表示永不整理

请求不断退出会留下空槽。实现可能需要压紧、重排或批量更新，以保持张量布局规则。

低并发、成员频繁变动或大量短请求时，增量 bookkeeping 与整理成本可能接近全量重建。收益来自稳定重叠，不是名字本身。

## 6. Prefix Cache：把复用纳入统一块生命周期

V1 并不是第一次拥有 Prefix Cache。重要变化是让 Prefix 复用更自然地进入统一 KV 块池、请求进度和调度路径。

### 6.1 命中改变已计算起点

`infra-guide-001` 有 1,024 Token 共享前缀。若这些 Token 的 KV 块可复用，运行时可以把相应位置视为已有计算状态，从后续未命中位置继续。

用进度差表示时，命中直接提高 \(n_i^{\text{computed}}\)，从而减少 \(d_i\)。Scheduler 不需要切换到另一套“缓存请求”执行模型。

### 6.2 缓存与空闲池需要统一生命周期

一个已无活跃请求引用的块，可以仍保留可复用内容，同时成为必要时可淘汰的候选。逻辑上“没有运行引用”和“字节可用于缓存”可以同时成立。

新请求命中时增加引用；容量紧张时，淘汰无保护的缓存块；请求结束时再根据引用和缓存策略决定去向。

### 6.3 “零开销”应理解为设计目标

所谓零开销 Prefix Cache，合理理解是：未命中路径不应因为启用缓存而复制 KV、维护第二套物理池或走完全不同的执行主干。

它不表示 Hash 计算、元数据查询和块边界检查在物理上耗时为零；命中也不表示 TTFT 变为零。后缀 Prefill、排队和 Decode 仍然存在。

### 6.4 块身份必须包含模型语义

只有 Token 序列、模型/适配器语义和相关缓存身份一致时，KV 才能安全共享。字符串相同但 Tokenizer、模板或 LoRA 不同，不能仅凭文本强行命中。

缓存是可重算优化状态。缓存丢失应降低性能，而不改变输出正确性。

## 7. Compile 与 CUDA Graph：减少设备提交成本

运行时层减少 Host bookkeeping 后，单步模型执行内部的 Python、算子调度和 Kernel launch 仍可能形成固定成本。Compile 与 CUDA Graph 处理不同层次的问题。

### 7.1 Compile 优化张量程序

`torch.compile` 一类编译机制分析模型执行图，进行算子融合、代码生成和图分段，目标是减少框架开销并生成更合适的 Kernel 路径。

它关注“执行哪些算子、怎样生成程序”。代价包括首次编译时间、缓存、动态 Shape 处理、Graph break 和模型兼容性。

### 7.2 CUDA Graph 优化重复提交

CUDA Graph 预先捕获一串设备操作，之后用较少 Host 启动重放，目标是减少每轮重复 Kernel launch 的 CPU 开销。

它关注“怎样低成本再次提交已知设备工作”。代价包括捕获时间、固定地址/Shape 合同、填充浪费和额外显存。

### 7.3 二者正交但相互约束

编译后的程序仍可成为 Graph 捕获对象；Graph 也不会自动完成算子融合。

Persistent Batch 和统一调度提供更稳定的执行描述，Compile/Graph 再利用这种稳定性。若 Batch Shape 不在可重放范围，运行时仍需要 Eager 或其他 fallback。

### 7.4 Shape 规则化有成本

动态 Batch 可能被填充到某个已捕获 Shape。若实际处理 17 个序列，却按更大 Shape 重放，多出来的槽位消耗设备时间与内存。

捕获更多 Shape 可减少填充，却增加启动时间和 Graph 内存。最佳集合取决于真实 Batch 分布，不来自一份通用默认值表。

## 8. 从单步优化到 CPU–GPU 流水线

五项设计最终在时间线上会合。

### 8.1 普通串行循环

保守路径是：

```text
CPU 结算 t-1 → 调度并构造 t → GPU 执行 t → CPU 读取 t → 构造 t+1
```

它容易保证正确，却让 CPU 与 GPU 交替等待。

### 8.2 可重叠路径

当 GPU 执行 \(t\) 时，Frontend 可处理新输入，CPU 可结算更早输出，执行侧可准备 \(t+1\) 中不依赖 \(t\) 结果的部分。

多进程隔离提供并行位置，Persistent Batch 减少准备量，Graph 降低提交量，统一状态让跨拍工作仍能关联到正确请求。

### 8.3 真实依赖形成最小串行缝

下一轮成员若取决于本轮 EOS、投机接受数、Grammar 状态或 KV 释放，就不能在结果未知时完全确定。

正确目标不是消灭同步，而是把同步缩小到真实依赖：

$$
T_{\text{step}}^{\text{steady}}
\approx
T_{\text{seam}}
+\max(T_{\text{host,overlap}},T_{\text{gpu}})
$$

### 8.4 多 Batch 在途扩大状态空间

若允许多个 Batch 同时处于准备、执行、回传阶段，系统需要知道每个请求有多少乐观进度、哪些 Buffer 仍被引用、取消应从哪一轮生效。

吞吐收益来自更深流水线，调试成本则来自迟到结果、回滚和资源生命周期。异步深度越大，越需要显式轮次与不变量。

## 9. 带单位的 Decode 流水线算例

假设一个稳定 Decode 区间有 128 个 step。旧串行路径每步包含：

- 调度与全量 Batch 准备：\(0.45\ \text{ms}\)；
- GPU 执行：\(1.80\ \text{ms}\)；
- 结果结算与下一轮前置处理：\(0.25\ \text{ms}\)。

串行每步为：

$$
T_{\text{serial}}
=0.45+1.80+0.25
=2.50\ \text{ms}
$$

128 步理想化总时间为：

$$
128\times2.50
=320.0\ \text{ms}
$$

现在假设 V1 的增量维护和流水化使 \(0.55\ \text{ms}\) Host 工作可与 GPU 重叠，只剩 \(0.15\ \text{ms}\) 真实串行缝：

$$
T_{\text{steady}}
=0.15+\max(0.55,1.80)
=1.95\ \text{ms}
$$

若首拍填充为 \(2.50\ \text{ms}\)，末拍排空为 \(0.25\ \text{ms}\)，总时间近似：

$$
T_{128}
\approx2.50+127\times1.95+0.25
=250.4\ \text{ms}
$$

教学算例中的加速比为：

$$
\frac{320.0}{250.4}\approx1.28
$$

它说明三件事。

第一，V1 没有让 Host 工作消失，只把可独立部分藏进设备窗口。

第二，GPU 仍是 \(1.80\ \text{ms}\) 主体，所以继续压缩 Host 的边际收益会下降。

第三，短输出只有少数 step，首尾 Bubble 占比更大，达不到稳态收益。

这些数字不是 vLLM 的性能承诺。实际结果取决于模型、硬件、Batch 重叠、Shape 命中、IPC 与功能组合。

## 10. 设计代价、失败边界与适用条件

### 10.1 多进程

适合前端 CPU 方差明显、多个请求持续到达的服务。低并发小模型中，IPC 与进程调度的固定成本可能更显眼。

失败时要分别观察入口、EngineCore 和 Worker；“进程还活着”不代表跨进程消息仍在推进。

### 10.2 统一 Token Budget

它降低阶段分叉，便于表达 Chunked Prefill 与投机验证。代价是 Token 只是一阶工作量，不能代替设备时间、序列上限和 KV 预算。

若只追求预算填满，长 Prefill 仍可能伤害 TPOT；策略还需体现 SLO 与优先级。

### 10.3 Persistent Batch

高并发、长 Decode、相邻 Batch 高重叠时收益大。大量一次性短请求、频繁抢占或成员持续抖动时，增量更新与压紧成本会上升。

错误通常表现为身份、槽位、Block Table 或迟到结果不一致，而不是普通数学精度误差。

### 10.4 Prefix Cache

稳定长前缀重复出现时，它减少 Prefill 和 KV 重写。前缀短、变化频繁、缓存抖动或跨副本路由破坏局部性时，收益可能不足以覆盖管理成本。

命中率只能描述复用比例，不能单独预测 TTFT。

### 10.5 Compile 与 Graph

稳态 Shape 集中、重复 step 多时更有价值。模型动态图分支多、Shape 极分散、显存紧张或冷启动敏感时，编译和捕获可能成为负担。

Eager 是重要的正确性与归因基线，不应被简单理解为“落后模式”。

### 10.6 组合优化会产生二阶交互

更大的 Token Budget 改变 Batch Shape 分布，进而改变 Graph 命中；Prefix Cache 减少 Prefill，又会改变 Persistent Batch 与队列；投机解码改变每轮候选数，也改变 KV 峰值与提交逻辑。

所以 V1 提供的是更可组合的结构，不是一组对所有 Workload 自动最优的开关。

## 11. 与 SGLang、TensorRT-LLM 的机制对照

### 11.1 SGLang

SGLang 同样关注长期请求到单轮 Batch 的转换，也通过 Scheduler 侧状态、执行 Batch 与 CPU–GPU Overlap 压缩 Host seam。

它的 RadixAttention 用 Radix Tree 组织可复用前缀，状态组织更直接地服务多轮和程序化请求。vLLM 的 Hash/Block 复用与 SGLang 的 Radix 路径解决相近问题，但索引结构、淘汰与路由耦合不同。

比较两者时，应问真实 Workload 有多少可复用前缀、Batch 重叠和结构约束，而不是比较特性名字。

### 11.2 TensorRT-LLM

当前 TensorRT-LLM 使用 PyTorch 原生 PyExecutor 组织请求循环、资源管理和模型执行，并通过 NVIDIA 专用 Kernel、Paged KV、In-flight Batching、CUDA Graph 与 Overlap Scheduler 压缩运行时开销。

它可以获得高度专门化的 NVIDIA 设备路径，代价主要是硬件绑定、模型与 Kernel 覆盖、Shape/精度组合和升级回归矩阵。vLLM V1 则更强调广泛模型生态下的统一动态状态、可插拔 Backend 与服务集成。

### 11.3 交接调度器

V1 的原则最终都要在每轮调度中兑现：谁先获得 Token、谁拿到 KV、谁因约束等待、谁在容量不足时被抢占。

下一节不逐行展开函数，而用计算、KV 和请求状态三本账验证这些决策。

## 总结

V1 的核心是跨轮状态与数据流重构，不是单一 Kernel 更新。

多进程隔离高方差 CPU 工作，统一 Token Budget 用进度差表示 Prefill、Decode 与投机验证，Persistent Batch 按变化量维护执行状态，Prefix Cache 进入统一 KV 生命周期，Compile/Graph 则减少程序与提交开销。

这些机制共同压缩 Host seam，并为 CPU–GPU 流水化创造条件。代价是 IPC、增量一致性、乐观状态、Shape 合同和更复杂的组合边界。

判断 V1 是否更快，必须回到模型、硬件、Batch 重叠、前缀复用和 SLO，而不能引用脱离条件的固定倍数。
