前五节一直在 vLLM 内部追踪请求状态、KV、调度与执行。本节把观察尺度横向展开，但不把三个项目压成一张“功能有/无”表。框架选型是一项条件化决策：

$$
\text{Choice}
=
f(\text{contract},\ \text{workload},\ \text{SLO},
\text{hardware},\ \text{team},\ \text{risk})
$$

任何脱离这些自变量的绝对排名，都无法迁移到另一个业务。

## 1. 真实问题：“谁最快”缺少什么
“vLLM、SGLang、TensorRT-LLM 谁最快？”至少缺少六项定义：
1. 哪个模型、Tokenizer、模板与精度；
2. 输入和输出 Token 的联合分布；
3. 请求怎样到达，是否突发；
4. 共享前缀、Structured、Spec 或多模态占比；
5. TTFT、TPOT、E2E、质量与错误率门槛；
6. 使用几张什么 GPU，以及允许多少工程维护成本。
“快”本身也可能指不同目标：
- 单请求最低延迟；
- 峰值输出 Tokens/s；
- 固定并发下平均 TTFT；
- P99 TPOT；
- 满足全部 SLO 的请求数；
- 每 GPU 小时的合格请求数；
- 从发布模型到可服务的总时间。
一个候选可以在第一项领先、在第五项落后。把它们压成一个总榜，会隐藏业务真正支付的代价。

### 1.1 框架不是唯一变量
性能来自一组共同决定的系统：

```text
框架版本
+ 模型制品
+ Tokenizer / Template
+ 精度与量化
+ Kernel / Backend
+ 并行拓扑
+ 运行时策略
+ 服务前后处理
+ 硬件与驱动
```

比较框架时若同时改变其中多项，结论只能描述两套整体方案，不能把差异单独归因于 Runtime。
### 1.2 选型目标是兑现合同
推理基础设施的价值不是让 GPU 看起来最忙，而是稳定完成正确请求。因此先问“哪组方案在成本和风险约束内兑现业务合同”，再问“某个机制为何造成差异”。

## 2. 选型的稳定合同：模型、Workload、SLO
公平比较的起点不是启动参数，而是一份对三个候选完全相同的外部合同；`infra-guide-001` 是这份 Workload 中必须得到相同语义处理的一条样本。

### 2.1 模型合同
至少固定：
- Checkpoint revision；
- Tokenizer revision；
- Chat Template 与特殊 Token；
- 权重精度或量化格式；
- KV 精度；
- 最大上下文；
- 采样、停止与随机性语义；
- Structured/Tool/Logprob 等实际使用能力。
OpenAI 风格字段相同，不保证默认值和边界行为相同。必须用相同消息核对实际输入 Token、输出上限、停止原因和流式拼接结果。
### 2.2 Workload 合同
LLM 请求成本至少是二维的：

$$
W_i=(L_i^{\text{input}},L_i^{\text{output}})
$$

还要保留：
- 到达间隔与突发程度；
- 共享前缀长度和重复频率；
- 多轮相关性；
- Structured Grammar 复杂度；
- Speculative Decoding 是否启用；
- 多模态输入；
- 取消与超时比例。
只给平均输入长度会丢掉长 Prompt 对 TTFT 和 KV 的影响；只给固定并发会掩盖开放到达下的排队失稳。

### 2.3 SLO 合同
对交互请求，可以定义：

$$
\text{good}(r)
=
\text{correct}(r)
\land TTFT_r\le S_{\text{TTFT}}
\land TPOT_r\le S_{\text{TPOT}}
\land E2E_r\le S_{\text{E2E}}
$$

协议正确、任务质量、错误率和完整输出也应进入门禁。一个因提前停止而“延迟更低”的请求不应计为性能胜利。
### 2.4 运行边界合同
还要固定：
- GPU 数量与功耗边界；
- TP/PP/DP 拓扑；
- CPU、RAM、NUMA 与网络；
- 缓存是 Cold、Warm 还是持续 Churn；
- 是否计算启动、构建与发布成本；
- 测量窗口和过载后的恢复要求。
这些条件共同定义赛道。没有赛道，就没有公平冠军。

## 3. 三个框架分别优先解决什么问题
三个候选都能进行动态服务、KV 管理和多 GPU 执行，但工程重心不同。

### 3.1 vLLM：通用动态服务运行时
vLLM 优先解决广泛模型生态下的高吞吐在线推理：
- 用 PagedAttention 与统一块池管理动态 KV；
- 用迭代级调度和 Token Budget 混合请求；
- 用 Hash-based Prefix Cache 复用块对齐前缀；
- 用可插拔执行后端适配模型与硬件；
- 提供较完整的服务接口和生态集成。
它常适合作为通用基线：模型迭代快、请求类型多、团队希望先获得可用服务，再按证据深入优化。代价是版本演进与组合矩阵较快。某个模型、量化、Backend 和高级功能组合仍需单独验证，不能用生态广度替代目标场景性能。
### 3.2 SGLang：围绕生成程序与前缀状态组织运行时
SGLang 优先关注复杂生成 Workload 中的状态复用与控制：
- RadixAttention 用前缀树表达共享 Token 路径；
- Runtime 把请求、缓存节点与 Batch 调度结合；
- Structured Generation 和程序化接口靠近 Agent/多步生成；
- 层次化缓存、状态化路由与 PD 等能力服务更大系统。
当业务具有长而稳定的 System/Tool 前缀、多轮分叉、JSON/Grammar 和 Agent 流程时，SGLang 的状态组织值得重点验证。
代价是缓存层次、路由、Grammar 和跨组件状态都会增加运维面。若真实流量没有共享前缀或复杂生成，这些机制的优势可能落在测量噪声内。
### 3.3 TensorRT-LLM：NVIDIA 平台上的 PyTorch 原生专门化执行
当前 TensorRT-LLM 优先解决受控 NVIDIA 栈上的专门化执行：
- 从 Hugging Face checkpoint 装载 PyTorch 模型，无需显式构建 TensorRT Engine；
- 由 PyExecutor 组织请求循环、Scheduler、ResourceManager 与模型执行；
- 深度利用 CUDA、NVIDIA 专用 Kernel、CUDA Graph 与通信优化；
- 通过 In-flight Batching、Paged KV 和 Overlap Scheduler 管理动态请求。
版本边界必须写清：TensorRT-LLM 1.0 及后续主线已移除旧式 TensorRT Engine 后端，这是架构断点，不能再用 `trtllm-build`、Engine Artifact 或“构建期固化”解释当前运行时。
当模型与 Kernel 覆盖良好、硬件固定、极限延迟或吞吐足以抵消 NVIDIA 专用路径的适配与验证投入时，它是重要候选。代价主要是 NVIDIA 硬件绑定、模型/精度/Shape 覆盖和 CUDA/TensorRT/PyTorch 版本回归矩阵。

### 3.4 “优先解决”不是能力排他
vLLM 也支持 Structured、Spec 和专门化 Backend；SGLang 也能通用服务；TensorRT-LLM 也有动态调度。
这里讨论的是设计重心与团队成本，不是宣布某功能只属于一个项目。能力矩阵随版本变化，稳定比较单位应是问题、机制和证据。

## 4. 状态组织方式决定优化方向
第 3 章的主线是有状态推理运行时。框架差异最值得比较的，也是它们怎样组织可变状态。
### 4.1 vLLM：请求进度加块级 Hash 索引
运行时请求保存已计算位置、输出、约束与 KV 引用；Scheduler 每轮形成 Token 计划；Prefix Cache 以连续块 Hash 查找可复用 KV。
这种组织适合把动态请求放入统一 Token/KV 预算，并让缓存与普通块共享生命周期。优化重点常落在 Batch 重叠、Token Budget、KV 容量和 Hash 前缀局部性。

### 4.2 SGLang：请求进度加 Radix Tree
Radix Tree 直接表达 Token 前缀的共享与分叉，缓存节点拥有前缀路径和引用/淘汰状态。请求在树上匹配最长前缀，再把未命中后缀交给 Scheduler。
这种组织让多轮、分支和稳定前缀更自然地落在同一结构中。代价是树状态、缓存局部性和多副本路由更紧密耦合。
### 4.3 TensorRT-LLM：PyTorch 模型状态加 PyExecutor 运行时状态
PyTorch 模型权重与配置描述模型，PyExecutor 的 Scheduler、ResourceManager 和模型执行器维护请求、KV 页、In-flight Batch、MicroBatch 与输出生命周期。
CUDA Graph、专用 Kernel 和通信策略会为常见 Shape 提供专门化路径，但它们是当前运行时中的选择与缓存，不应再抽象成一个预构建 Engine Artifact。优化重点横跨模型/Kernel 覆盖、Graph 与重叠调度、运行时请求分布。

### 4.4 状态决定缓存与故障语义
三个框架的优化状态都应可由模型制品和输入重建。缓存、Graph 或 Engine 本地状态丢失可以影响冷启动和性能，不应悄悄改变模型合同。
多副本时，每个副本拥有不同 KV 与队列。Round-robin、最短队列和缓存亲和会产生不同局部性；若路由策略不同，就不是单纯框架比较。

## 5. 硬件与团队约束也是系统变量
### 5.1 硬件可移植性
vLLM 与 SGLang 都在扩展不同设备和 Backend，但目标模型在某个非 NVIDIA 平台是否完整支持，需要按版本核对。
TensorRT-LLM 的核心价值与 NVIDIA 栈紧密绑定。若组织明确需要多硬件供应商，硬件约束可能在性能实验前就缩小候选范围。

### 5.2 模型变化速度
模型每周变化时，模型支持、模板、量化和调试速度可能比单个稳定模型的最后 5% 吞吐更重要。模型半年稳定、流量巨大时，专门构建、校准和 Kernel 优化的固定成本更容易摊薄。
### 5.3 团队能力
选型还取决于团队能否维护：
- CUDA/驱动/框架版本矩阵；
- 模型装载、Kernel/Graph 覆盖与发布回归；
- Prefix Cache 和状态化路由；
- Structured/Agent 正确性；
- 性能回归与质量门禁；
- 故障时的摘流、回退和重建。
一个实验室数字领先、但团队无法稳定升级和诊断的方案，不是生产最优。

### 5.4 迁移成本
已有监控、客户端、模型仓库、量化流水线和发布系统都形成资产。新框架带来的 Goodput 增益必须覆盖迁移、双栈运行、回归和长期维护成本。若现有方案已满足 SLO，微小差异可能不足以支持迁移。

## 6. 公平实验的不可变原则
本节只给原则，不给完整命令和数据集 SOP。
### 6.1 同模型语义
三个候选使用同一 Checkpoint、Tokenizer、Template、BOS/EOS 和最大位置语义。若输入 Token 数不同，Prefill 成本和 Prefix 身份已经不同，后续性能不能直接比较。

### 6.2 同质量赛道
权重精度、KV 精度和量化校准应一致，或者明确分成两条赛道：
- **Iso-quality**：质量达到相当水平后比较性能；
- **Best-validated**：每个框架选择通过同一质量门禁的最佳配置。
不能用 BF16 与 FP8 的速度差全部归因于框架，也不能忽略量化导致的任务质量变化。
### 6.3 同资源边界
固定 GPU 型号、数量、功耗、并行拓扑、CPU/NUMA、内存和网络。如果一个候选用 8 卡、另一个用 4 卡，至少应转为每 GPU 小时成本，并明确比较的是整体方案而非等资源性能。
### 6.4 同请求语义
固定采样、随机种子能力、输出上限、EOS/Stop、流式、Logprob、Structured Schema 和取消规则。实际输出 Token 与完成原因必须被记录。更早停止会同时提高吞吐和降低 E2E，却可能违反输出合同。

### 6.5 同 Workload 与到达过程
用同一请求序列和到达时间驱动候选，保留长短输入、输出相关性和 Burst。Closed-loop 并发会受服务端变慢反向限制到达率；Open-loop 更接近外部流量，但会暴露过载。二者回答不同问题，不能混在同一排名。
### 6.6 同缓存状态
Cold、Warm 与 Churn 要分开报告。
- Cold 回答无历史状态时的基线；
- Warm 回答稳定复用收益；
- Churn 回答容量有限、前缀变化时的淘汰与尾延迟。
只测重复同一 Prompt 的 Warm 峰值，会高估真实 Prefix 收益。

### 6.7 同测量边界
以统一外部客户端计量到达、首字节/首 Token、每个 Token 和完成时刻。框架内部指标用于解释原因，不按相似名字直接横拼。客户端自身也要有余量，否则测到的是客户端序列化、连接池或事件循环上限。
### 6.8 先正确，再性能
所有候选先通过：
- 基础生成与停止；
- 流式拼接；
- 超长输入错误；
- 取消与资源回收；
- Structured/Tool 合同；
- 任务级质量；
- 长上下文正确性。
性能再高但正确率、JSON Valid Rate 或成功率不达标，不进入性能前沿。

### 6.9 重复、随机化和恢复
实验应重复，并随机化候选执行顺序，避免温度、后台负载和长期降频造成顺序偏差。过载测试还要观察停止增压后多久恢复。高峰值吞吐但队列无法收敛的系统，不适合按稳态数字选型。

## 7. 从峰值吞吐转向 Goodput 与成本
### 7.1 Goodput
设观察窗口为 \(T\)，请求集合为 \(\mathcal R\)：

$$
\text{Goodput}
=
\frac{
\sum_{r\in\mathcal R}\mathbf 1[\text{good}(r)]
}{T}
$$

它只统计同时满足正确性、成功和全部 SLO 的请求。完成吞吐可以增长，而 Goodput 因 P99 越界下降。这个分叉通常出现在容量 Knee 附近。

### 7.2 Token Goodput
若业务价值更接近有效输出 Token，可统计满足合同请求的有效 Token：

$$
\text{TokenGoodput}
=
\frac{
\sum_r N_r^{\text{valid-output}}
\mathbf 1[\text{good}(r)]
}{T}
$$

但不能让超长输出完全淹没短交互请求。按请求和按 Token 的指标应一起报告。
### 7.3 成本归一化
每 GPU 小时合格请求数：

$$
\eta_{\text{cost}}
=
\frac{N_{\text{good}}}
{N_{\text{GPU}}\times T_{\text{hour}}}
$$

若电价、实例价格或功耗不同，还可换成每千合格请求成本与能耗。构建时间、冷启动和工程人力应作为单独维度，不要伪装成精确的 GPU 成本。

### 7.4 尾延迟与错误不能被平均
平均 TTFT 可能在超时请求被丢弃后变得更好。报告分位数时要同时给出分母、错误、超时和完成数量。Goodput 的价值就是让“快但失败”不能贡献正收益。

## 8. 带单位的条件化选型算例
下面是虚构的教学结果，不代表三个框架的真实排名。固定条件：

```text
测量窗口：600 s
资源：每个候选 8 GPU
到达请求：15,000 request
模型/精度/Tokenizer/Template：相同
请求级 Goodput 门槛：TTFT ≤ 300 ms，TPOT ≤ 30 ms；另报告总体 P99
质量与协议：必须通过同一门禁
```

观测结果：

| 候选 | 完成请求 | 正确请求 | 同时满足请求级门槛的正确请求 |
|---|---:|---:|---:|
| vLLM | 13,800 | 13,700 | 12,600 |
| SGLang | 13,400 | 13,350 | 12,900 |
| TensorRT-LLM | 14,200 | 14,100 | 12,300 |

按完成吞吐：

$$
\text{Throughput}_{\text{TRT}}
=\frac{14{,}200}{600\ \text{s}}
\approx23.67\ \text{request/s}
$$

TensorRT-LLM 在这组虚构结果中最高。按 Goodput：

$$
\text{Goodput}_{\text{vLLM}}
=\frac{12{,}600}{600}
=21.00\ \text{request/s}
$$

$$
\text{Goodput}_{\text{SGLang}}
=\frac{12{,}900}{600}
=21.50\ \text{request/s}
$$

$$
\text{Goodput}_{\text{TRT}}
=\frac{12{,}300}{600}
=20.50\ \text{request/s}
$$

同样 8 GPU、窗口 \(600\ \text{s}=1/6\ \text{hour}\)，每个候选消耗：

$$
8\times\frac{1}{6}
=1.333\ \text{GPU-hour}
$$

SGLang 的合格请求效率为：

$$
\eta_{\text{SGLang}}
=\frac{12{,}900}{1.333}
\approx 9{,}675
\ \text{good request/GPU-hour}
$$

这组合同下，完成量排名与 Goodput 排名相反。原因还不能从表中得出，需要回到分层证据检查 Queue、Prefix 命中、Shape、错误和 P99。
若把 Workload 改成没有共享前缀、固定 Shape 的单请求延迟任务，排名完全可能变化。算例证明的是选型方法，不是框架结论。

## 9. 三类典型场景怎样提出候选假设
### 9.1 通用模型服务
条件：
- 模型与量化频繁变化；
- OpenAI 风格服务和生态集成重要；
- 请求长度与功能类型多样；
- 团队希望快速建立可观测基线。
候选假设：先用 vLLM 建立通用基线，再验证目标模型的 Backend、调度和 KV 配置。需要关注版本组合回归，而不是假设所有模型都走同一最佳路径。

### 9.2 共享前缀与 Agent 工作流
条件：
- 长 System/Tool 前缀重复；
- 多轮或分支生成比例高；
- Grammar/JSON 合同重要；
- 团队愿意维护缓存局部性与状态化路由。
候选假设：重点验证 SGLang RadixAttention、Structured 路径和多副本状态组织。反假设是前缀复用不足、缓存 Churn 太高或新增状态成本抵消收益。
### 9.3 固定 NVIDIA 模型与专门化执行
条件：
- NVIDIA 硬件与模型版本长期稳定；
- 流量足以摊薄模型装载、Graph 预热和专用路径验证；
- 极限延迟/吞吐价值高；
- 团队能维护 TensorRT-LLM/PyTorch/CUDA 与 Kernel 覆盖回归矩阵。
候选假设：重点验证 TensorRT-LLM 的 PyExecutor、专用 Kernel、CUDA Graph、Overlap Scheduler 和 In-flight Batching。反假设是模型变化太快、Shape 太散或 NVIDIA 专用路径的适配回归成本超过稳态收益。
### 9.4 场景不是框架绑定
三类条件只决定“先验证谁”，不决定最终胜者。同一组织可以让不同 Workload 使用不同 Runtime，也可以因统一运维价值选择一个稍慢但足够合格的平台。平台标准化本身也是成本优化。

## 10. 没有绝对冠军，只有 Pareto 前沿

### 10.1 多目标不能压成一个总分
选型至少同时观察：
- Goodput 与 Token Goodput；
- TTFT/TPOT/E2E 分位数；
- 质量、协议与错误；
- GPU 成本与能耗；
- 冷启动、模型装载、Graph 预热和发布；
- 模型覆盖与功能交付速度；
- 可观测性、排障与回退；
- 硬件锁定和团队风险。
给每项随意加权得到“87 分 vs 85 分”，往往比保留原始维度更不透明。
### 10.2 Pareto 前沿
若方案 A 在所有关键维度都不差于 B，且至少一项更好，B 才能被明确淘汰。未被支配的方案构成 Pareto 前沿。业务可以在前沿上选择更低延迟、更低成本或更低运维风险的点。

### 10.3 容量 Knee
每个候选都应画出到达率上升时 Goodput、Queue 和 P99 的曲线。生产容量位于排队发散之前，而不是峰值完成吞吐出现的位置。一个候选峰值更高、但 Knee 更早或过载恢复更慢，未必适合突发在线流量。
### 10.4 “无显著差异”也是结论
如果候选差异落在重复实验波动内，应报告无法拒绝等价假设，而不是用小数点后差距宣布冠军。此时模型覆盖、维护成本和迁移风险往往成为更可靠的决策因子。

## 11. 选型记录、复评与后续交接

### 11.1 决策记录
最终 ADR 至少保存：
- 业务合同、质量门禁与 SLO；
- 候选版本、镜像和模型 Artifact 身份；
- 硬件与并行拓扑；
- Workload 摘要与缓存状态；
- 各候选 Pareto 点与原始证据；
- 已知失败模式和容量边界；
- 迁移、构建、运维和回退成本；
- 被否决假设及原因。
它记录“在什么条件下为何选择”，而不是“哪个框架永远最好”。
### 11.2 复评触发条件
以下变化应触发重新比较：
- 模型、精度或硬件更换；
- 输入/输出长度与前缀分布变化；
- SLO、Structured 或 Agent 合同变化；
- 当前瓶颈被新版本明确改写；
- 运维或构建成本超过阈值；
- 多副本路由与缓存策略改变。
版本升级本身不保证重跑全部选型，但跨越关键机制变化时，旧结论的前提可能已经消失。

### 11.3 与后续章节交接
第 4～8 章会分别改变量化、Spec、分布式、PD 和服务特性；每一项都会改写本节的固定合同。
第 9 章负责把测量方法扩展为系统 Benchmark，第 10 章处理生产运维，第 11 章把优化组合成端到端方案，第 12 章再以 SGLang 为另一条实例主线深入状态化缓存与 Agent。
本节只建立选型理论，不重复完整实验 SOP。

## 总结
vLLM、SGLang 与 TensorRT-LLM 没有脱离条件的绝对冠军。
vLLM 的重心是通用动态服务运行时，SGLang 强调前缀树、生成程序与复杂状态，当前 TensorRT-LLM 强调 NVIDIA 平台上的 PyTorch 原生运行时与专用 Kernel/调度协同。
公平比较必须固定模型语义、质量、资源、请求、Workload、缓存和测量边界，再用 Goodput、成本、尾延迟和运维风险形成 Pareto 前沿。
选型结果只对当时的模型、硬件、流量、SLO 和团队成立。最重要的产物不是排行榜，而是一份可复核、可推翻、可在条件变化时重跑的决策记录。
