## 1. 实战目标与角色

目标示例（请替换成你的数字）：

- 模型：7B～14B 指令模型，FP8 或 BF16
- SLO：TTFT P95 ≤ 800ms，TPOT P95 ≤ 35ms，错误率 ≤ 0.1%
- 峰值：业务混合负载下 25 QPS
- 约束：单集群，GPU 型号固定，两周内可灰度

角色：推理业主、平台/K8s、业务服务端、on-call。

📌 **关键点**：没有写成数字的 SLO 与峰值，后面所有"优化"都无法验收。

---

## 2. 需求分析

收集并文档化：

| 维度 | 问题 |
|---|---|
| 模型 | 哪个权重？是否多 LoRA？是否 VLM？ |
| 质量 | 允许的量化损失？是否要结构化输出/工具？ |
| 流量 | QPS、长度分布、系统提示复用率、日夜差异 |
| 体验 | 流式？首包要求？P99 是否进 SLO？ |
| 合规 | 数据驻留、日志脱敏、鉴权要求 |
| 硬件 | GPU 型号/数量上限、能否多卡 TP |

产出：《推理需求说明书》一页纸即可，但字段要全。

---

## 3. 方案设计

按第 11.1 / 11.2 决策：

1. **框架**：vLLM OpenAI 兼容服务
2. **精度**：在质量集上选 BF16 / FP8 / INT4 等
3. **并行**：单卡优先；装不下再 TP
4. **特性开关**：Prefix Cache（若复用高）、Chunked Prefill、（可选）投机
5. **服务特性**：Tool parser / JSON Schema / LoRA 按需
6. **部署**：镜像 + K8s；网关 TLS/API Key；HPA 信号
7. **观测**：第 10.2 指标与告警
8. **容量**：第 10.4 估算 GPU，留冗余

```mermaid
flowchart LR
    A["需求"] --> B["模型/精度/并行"]
    B --> C["引擎特性组合"]
    C --> D["K8s+网关+观测"]
    D --> E["容量与成本"]
```

⚠️ **注意**：方案里写明**不做**什么（例如首版不上 P/D），防止范围膨胀。

## 4. 部署与压测验证

### 4.1 部署

1. 构建并钉死镜像 digest
2. 配置 ConfigMap：模型路径、`max_model_len`、缓存与利用率等
3. 挂载权重或启动预取
4. 设置 startup/readiness，滚动发布
5. 网关接入：TLS、API Key、限流、超时

```bash
# 概念：集群内探活
curl -sS https://llm-gateway.example/v1/models \
  -H "Authorization: Bearer $API_KEY"
```

### 4.2 压测

1. 微观基线：并发 1，固定长度
2. 饱和曲线：找到 SLO 内 Q*
3. 业务混合：含系统提示复用与长尾
4. 对比方案中的关键开关（A/B）
5. 写入基线，配置门禁

未达 SLO：按 OOM→TTFT→TPOT→尾延迟顺序回调，而不是同时拧所有旋钮。

💡 **提示**：灰度环境与生产同型号 GPU；在异型号上"验过"的数字不可直接搬运。

## 5. 上线监控与复盘

上线当日：

- 盯 L1 看板：QPS、错误率、TTFT/TPOT P95、KV、队列
- 准备一键回滚镜像/配置
- 网关限流阈值与熔断确认

上线一周：

- 对比预测 Q* 与真实 Goodput
- 调整 HPA 最小副本与冗余
- 复盘：哪项优化真的赚到了、哪项属噪声

🔑 **核心概念**：上线不是终点，而是**容量模型的第一次校准**。

### 时间盒参考（两周项目）

| 天数 | 产出 |
|---|---|
| D1～D2 | 需求说明书、质量小集、硬件确认 |
| D3～D5 | 方案冻结、镜像与配置、单副本跑通 |
| D6～D8 | 三层压测、定 Q*、算 GPU |
| D9～D10 | 网关/观测/HPA、安全验收 |

节奏可按团队裁剪，但**不要跳过压测与安全验收直接全量**。

## 📝 总结

- 端到端实战按需求→方案→部署压测→监控复盘推进。
- 需求必须数字化；方案写清做与不做。
- 部署钉死镜像与探针，网关补齐安全面。
- 压测分基线/饱和/混合，用 Q* 驱动容量。
- 上线用看板与回滚托底，并用真实流量校准模型。
- 用时间盒保证关键门禁不被"赶工期"挤掉。
