可观测性不是收集尽可能多的数字，而是从系统外部结果推断内部状态。
当用户说“首 token 变慢”，我们需要知道请求何时到达、是否被准入、在哪一层排队、命中了多少前缀、何时获得 GPU、哪个控制动作改变了副本池。
这些事件只有落在同一语义和时间边界中，才构成可用于决策的 feedback。
本文讲观测理论与推理方法，不提供查询语句、仪表盘清单、采集搭建步骤或告警规则。

## 1. 问题：有指标为什么仍然无法解释故障

三个常见画面是：
- GPU 利用率很高，但用户延迟正常；
- GPU 利用率不高，但 TTFT 已经超时；
- 所有副本都 Ready，Goodput 却在下降。

它们并不矛盾。
GPU 利用率描述设备忙碌程度，Ready 描述能否接收新请求，Goodput 描述请求最终是否正确且按时完成。
三者观察的是不同对象和时间阶段。

观测失败通常不是“没有数”，而是缺少以下连接：
1. **边界连接**：入口到达、服务接受和请求完成使用不同分母；
2. **时间连接**：请求事件、设备采样和发布动作无法对齐；
3. **身份连接**：模型版本、逻辑副本、rank、GPU 与节点映射不清；
4. **语义连接**：waiting、in-flight、cache hit 在不同组件中定义不同；
5. **因果连接**：把同时发生的相关性误当作原因。

可观测性的最小产物不是一张图，而是可证伪的陈述：
> 在指定请求集合与时间窗内，用户症状由哪一阶段贡献，哪些证据支持，哪些证据可以推翻。

## 2. 统一实验合同 C10

本节所有例子沿用 \(C_{10}\)：
- 服务对象是固定身份的 70B 稠密指令模型 \(M_0\)；
- 模型采用 BF16、TP=4、PP=1，一个逻辑副本占四张 80 GiB GPU；
- 四个 rank 是一个调度、就绪、排空和故障单元；
- 流式长度分布为 60% \((512,128)\)、30% \((2048,256)\)、10% \((8192,512)\)；
- 一半请求带可复用稳定前缀，命中与未命中分层记录；
- 稳态 offered load 为 \(6\) req/s；
- 每 10 分钟出现一次 \(10\) req/s、持续 30 秒的突发；
- 拒绝、超时和客户端取消仍计入 offered load；
- 请求须协议与结果正确，且满足 \(TTFT\le1.5\,s\)、\(TPOT\le60\,ms\)、\(E2E\le45\,s\)；
- 以可信入口到达时间归属逻辑请求 cohort，拒绝、超时和取消均为 bad event，30 天滚动联合达标率 \(A_{10}\ge S_{10}=99\%\)；
- 从扩容决策到副本可路由的冷启动 P99 为 180 秒；
- 任一逻辑副本故障后仍要承接峰值并满足相同 SLO；
- 发布一次最多摘流一个副本，且期间还要容忍另一个副本故障；
- 新版本经正确性、就绪、canary 门禁后放量，旧版本保留至回滚窗口结束。

由长度分布得到两个仅描述 workload 的期望值：
$$
E[N_{\text{in}}]=0.6\times512+0.3\times2048+0.1\times8192=1740.8
$$
$$
E[N_{\text{out}}]=0.6\times128+0.3\times256+0.1\times512=204.8
$$
所以稳态 offered workload 约为 \(10444.8\) input token/s 与 \(1228.8\) target output token/s；突发时分别约为 \(17408\) 和 \(2048\)。
这些是到达侧期望，不是 GPU 吞吐或完成侧实测。
请求可能被拒绝、取消，也可能未生成到目标上限，观测中不能混用。

## 3. 用一条 timeline 定义请求事实

### 3.1 请求事件线

对一次流式请求 \(i\)，定义：
- \(t_0\)：可信入口接收到请求；
- \(t_1\)：鉴权、配额和 admission 给出决定；
- \(t_2\)：Router 选定逻辑副本；
- \(t_3\)：请求进入该副本的 runtime waiting；
- \(t_4\)：Prefill 真正开始；
- \(t_5\)：首 token 离开模型执行边界；
- \(\tau_k\)：第 \(k\) 个输出 token 可见，其中 \(\tau_1=t_5\)；
- \(t_f\)：正常结束、拒绝、取消、超时或失败被最终确认。

由此定义：
$$
T_{\text{admission}}=t_1-t_0,\quad T_{\text{route}}=t_2-t_1,\quad T_{\text{queue}}=t_4-t_3
$$
$$
TTFT=t_5-t_0,\qquad E2E=t_f-t_0
$$
若实际输出 \(m>1\)，请求级平均 token 间隔可记为：
$$
TPOT_i=\frac{\tau_m-\tau_1}{m-1}
$$
生产实现可能对 TPOT 使用更严格的逐 token 或分位定义，但合同必须在所有组件和压测中保持一致。

### 3.2 不要丢掉入口之前和完成之后

只从 \(t_3\) 开始计时，会隐藏 admission 与 Router 排队。
只到模型生成结束计时，又会隐藏网络发送、背压和客户端已经取消的事实。
\(C_{10}\) 的 E2E 从可信入口接受到最终结果结束，边界必须稳定。

入口还要记录 offered load。
如果只统计被接受请求，过载时主动拒绝会让图上 RPS 下降，看起来像需求减少。
正确关系是：
$$
\lambda_{\text{offered}}
=\lambda_{\text{accepted}}+\lambda_{\text{rejected-before-run}}
$$
运行后超时和取消不应从原始到达分母中消失。

### 3.3 把缓存事件放入同一线

稳定前缀存在，不等于本次一定命中。
对每个请求还需记录：
- 路由前估计的前缀身份与长度；
- 目标副本是否已有兼容缓存；
- 实际复用 token 数，而不只是布尔 hit；
- 未命中的原因：冷副本、淘汰、版本不兼容还是路由溢出；
- 缓存查询与物化发生在 \(t_3\) 到 \(t_4\) 的哪个阶段。

Prefix Cache 是性能派生状态。
它可以解释 Prefill 工作变化，但不能改变请求正确性或跨身份复用边界。

### 3.4 把控制动作也变成事件

副本创建、进入 Warming、Ready、权重调整、Draining、终止、故障和回退都要有事件时间。
每个事件至少关联：
- 动作发起时间；
- 控制器观察到的输入状态；
- 目标副本代际与制品身份；
- 动作完成或失败时间；
- 从决定到生效的延迟。

否则 12:03 的 TTFT 上升与 12:02 的发布只能被描述为“同时发生”，无法验证发布是否先于症状。

## 4. 六层观测模型

统一 timeline 上可以叠加六层事实。

### 4.1 请求结果层

这一层回答“用户得到了什么”：协议和结果是否正确，TTFT、TPOT、E2E 是否达标，以及最终是完成、拒绝、超时、取消还是流中断。
同时保留输入、目标输出、实际输出的长度桶，以及稳定前缀和实际缓存命中 cohort。
请求结果是 SLO 的来源，不能由 GPU 指标替代。

### 4.2 入口与 admission 层

这一层回答“系统决定接什么”：offered、accepted、rejected 的关系，拒绝原因，有界队列年龄、剩余 deadline、优先级和重试次数。
入口队列增长是需求超过当前接纳能力的直接信号。
但它不说明瓶颈必然在 GPU，也可能是无 Ready 副本或 Router 状态异常。

### 4.3 Router 与副本队列层

这一层回答“请求为什么去了这里并等了多久”：候选副本、路由理由、waiting/running work、最老等待年龄、热点与新副本权重都落在请求线上。
队列长度必须带工作量语义。
十个 \((8192,512)\) 请求和十个 \((512,128)\) 请求不能视为同等积压。

### 4.4 Runtime 与调度层

这一层回答“模型执行器在做什么”：Prefill/Decode 边界、batch、抢占、重计算、显存分配、rank 同步和 token 完成速率。
四个 rank 必须映射到同一逻辑副本代际，runtime 错误也按这个原子单元归属。
Runtime token/s 是完成侧能力信号。
它必须和 offered token/s、长度分布及 SLO 同看。

### 4.5 KV 与 Cache 层

这一层回答“状态如何改变工作量”：KV 余量、活跃 token、block 分配/回收、抢占/重计算、可复用与实际命中 token、淘汰和缓存温度。
还要证明不同模型身份间没有错误复用。
KV 使用率高可以是健康的高效利用。
只有当它与排队、抢占、分配失败或 SLO 失守同现时，才形成容量压力证据。

### 4.6 GPU 与控制动作层

GPU 层回答物理资源是否支持上层行为：计算、显存容量、内存带宽、互联、功耗、降频和设备错误都要映射到 Pod、rank、副本与节点。
控制动作层回答系统自己改变了什么：扩容原因、180 秒冷启动阶段、Draining、发布/回退身份、路由权重和动作前后的 Ready Capacity。

## 5. RED、USE 与排队信号

### 5.1 RED 从服务边界看结果

RED 分别是 Rate、Errors、Duration。
在推理服务中：
- **Rate** 首先是 offered request rate，同时保留 accepted、completed 与 Goodput rate；
- **Errors** 包含协议失败、结果错误、超时、流中断和按合同计入的拒绝；
- **Duration** 至少拆成 TTFT、TPOT、E2E，而不是只看连接建立时间。

RED 适合从用户边界发现“是否受影响”。
它不直接解释设备为什么忙，也不能单独判断扩容是否会有效。

### 5.2 USE 从资源边界看能力

USE 分别是 Utilization、Saturation、Errors。
对 GPU 推理：
- **Utilization** 表示计算、显存容量、内存带宽或互联被使用的比例；
- **Saturation** 表示等待资源的工作，如 runtime waiting、通信等待、KV 分配压力；
- **Errors** 表示设备、通信、分配和进程层错误。

单个“GPU utilization”覆盖不了 USE。
GPU 核心利用率低但显存带宽饱和时，设备仍可能是瓶颈。
GPU 很忙但队列稳定且 SLO 全部达标时，也不构成故障。

### 5.3 排队连接 RED 与 USE

近似地：
$$
\frac{dQ(t)}{dt}=\lambda_{\text{accepted}}(t)-\mu_{\text{effective}}(t)
$$
队列增长说明接收速率超过有效完成能力。
有效能力会受长度、缓存、批处理、故障和发布影响，因此不能把 \(\mu\) 当常数。

最老请求年龄比队列个数更直接接近 TTFT 风险。
队列斜率是先行信号，TTFT 违反是用户结果；两者在 timeline 上有因果顺序，但仍需排除时间戳和口径错误。

## 6. SLO、Goodput 与 Error Budget

### 6.1 把每个请求判成一个合同结果

对请求 \(i\)，定义：
$$
G_i=\mathbf{1}[\text{correct}_i\land TTFT_i\le1.5\land TPOT_i\le0.060\land E2E_i\le45]
$$
令 \(\mathcal E(W)\) 是以 \(t_0\) 落入窗口 \(W\) 的全部 offered logical requests。
拒绝、超时和取消保留在 \(\mathcal E(W)\) 中且 \(G_i=0\)；窗口只在这些请求达到结果或合同 deadline 后关闭。
窗口内的 Goodput 与联合达标率分别为：
$$
\text{Goodput}(W)=\frac{\sum_{i\in\mathcal E(W)}G_i}{T_W},
\qquad
A_{10}(W)=\frac{\sum_{i\in\mathcal E(W)}G_i}{|\mathcal E(W)|}
$$
其中 \(T_W\) 是窗口秒数，因此 Goodput 表示每秒达标请求数；\(A_{10}\) 才是 Error Budget 使用的比例 SLI。

正确性必须和延迟共同判定。
一个 200 状态但模板错位的响应不是好请求；一个正确但 TTFT 为 5 秒的响应也不计 Goodput。

### 6.2 Error Budget 表示允许失败的份额

对 \(C_{10}\)，SLO 目标为 \(S_{10}=99\%\)。
若窗口内 eligible logical requests 总数为 \(N_{\text{eligible}}\)，则预算事件数为：
$$
B_{\text{allowed}}=(1-S_{10})N_{\text{eligible}}
$$
实际 bad event 包含所有违反正确性或延迟条件的请求。
预算剩余量是：
$$
B_{\text{remaining}}=B_{\text{allowed}}-N_{\text{bad}}
$$

Error Budget 不是错误“配额”。
它用于管理变化速度：预算快速燃烧时，冻结非必要发布、收紧实验并优先恢复服务；admission 和背压仍应继续保护系统。

### 6.3 燃烧率要有窗口语义

设观察窗内实际 bad ratio 为 \(e_W\)，允许 bad ratio 为 \(1-S_{10}\)，则：
$$
\text{burn rate}_W=\frac{e_W}{1-S_{10}}
$$
燃烧率大于 1 表示按当前速度会提前耗尽预算。
短窗口响应快但噪声大，长窗口稳定但滞后；实际决策应结合两者，而不是看到一个瞬时比例就重启副本。

## 7. 指标语义、基数与聚合

### 7.1 先写语义合同

每个指标至少声明对象、单位、数据类型、事件时间、采集时间、reset/缺失/重复语义、维度上限，以及与 \(C_{10}\) 请求边界的关系。
版本升级还要说明如何保持这份语义合同。
“waiting=12”若不知道是入口请求、Router 工作项还是 runtime sequence，就不能用于归因或控制。

### 7.2 低基数维度用于聚合

适合聚合的维度包括区域/服务、模型身份、逻辑副本代际、节点、长度桶、缓存 cohort、结果、优先级、路由原因和控制阶段。
维度的笛卡尔积同样重要。
每个标签单独看都有限，组合后仍可能产生海量时序。
新增维度前应估算：
$$
\text{series upper bound}\approx\prod_k |\mathcal{L}_k|
$$

### 7.3 request_id 不属于指标标签

请求 ID、trace ID、原始前缀哈希、完整 URL、用户文本和账户 ID 通常是高基数字段。
把它们放进指标会让每个请求创建新时序，也增加隐私风险。
请求级关联应进入受控日志或追踪，并通过 exemplar 或时间、版本、Pod 等低基数线索回跳。

### 7.4 分位数不能随意相加或平均

\(P99(T_{\text{queue}})+P99(T_{\text{prefill}})\) 通常不等于 \(P99(TTFT)\)，因为两个 P99 可能来自不同请求。
各副本 P99 的平均也没有清晰的全局分位含义。
正确做法是保留可聚合分布，或在请求级直接计算目标端到端分布。

直方图区间要围绕 1.5 秒、60 毫秒和 45 秒 SLO 提供足够分辨率。
若所有长尾都落入最后一个无穷桶，只能知道“很慢”，无法判断预算偏差。

## 8. 日志、追踪与采样

### 8.1 三类信号各自负责什么

指标低成本回答范围、趋势与预算；日志记录状态迁移、错误上下文和请求结果；追踪串联入口、Router、runtime 与发送阶段。
三者通过内部 request ID、trace ID、逻辑副本代际和制品身份关联。
客户端传入的 ID 不能直接作为可信内部身份，以免冲突或日志注入。

### 8.2 结构化事件保留最小充分信息

请求结束事件表达时间、关联 ID、版本、副本、长度桶、缓存 cohort、阶段耗时、结果和重试；控制事件表达输入状态、动作与延迟；设备错误映射到 GPU、rank、副本和节点。
默认不记录 prompt 和生成文本。
即使为质量调试临时保留内容，也需要授权、脱敏、审计和短保留期。

### 8.3 采样不能破坏分母

请求 Counter 与 SLO 判定通常需要全量或可证明无偏的聚合。
详细 trace 可以采样，但采样决策和概率必须可见。

头部采样成本稳定，却可能漏掉后来才变慢的请求；尾部采样能优先保留错误、取消和 SLO 违反，但需要缓冲完整 trace。
合理策略是让全量指标保留分母，再用分层或尾部采样保存代表性证据。

不能用“采样 trace 中 99% 成功”替代全量 SLI。
异常请求被提高采样率后，样本分布本来就不再代表总体。

### 8.4 时间同步是隐含依赖

若入口、Router 和 GPU 节点时钟偏移 300 毫秒，阶段线可能出现“首 token 早于 Prefill 开始”。
进程内持续时间优先用单调时钟，跨进程关联依赖校准后的墙上时间；原始事件还要保留采集延迟。

## 9. 症状到假设再到证据

### 9.1 先写可证伪假设

排障不是从“重启试试”开始，而是：
$$
\text{症状}\rightarrow\text{候选机制}\rightarrow\text{预期证据}\rightarrow\text{反证}
$$
每个假设都要说明：若它为真，timeline 上还应该看到什么；若看不到，何时放弃。

### 9.2 TTFT 上升、TPOT 稳定

候选假设 A 是入口或 runtime 排队增长。
支持证据包括 \(t_4-t_3\) 增大、最老等待年龄上升、\(dQ/dt>0\)，而执行后的 token 间隔稳定。
反证是请求无排队但 \(t_4\) 到 \(t_5\) 显著变长。

候选假设 B 是输入变长或 Prefix Cache 命中下降。
支持证据是长度 cohort 不变时实际复用 token 减少、Prefill 时间增加，或长输入占比偏离 \(C_{10}\)。
反证是相同长度、相同命中 cohort 的 Prefill 分布不变。

### 9.3 TPOT 上升、TTFT 近似稳定

候选假设是 Decode 阶段资源争用、batch 结构改变、设备降频或 TP 通信等待。
支持证据应出现在 \(t_5\) 之后：逐 token 间隔变长、Decode 吞吐下降、通信或设备 saturation 同步增加。
若 queue 与 Prefill 已先显著恶化，则不能仅凭 TPOT 把原因归到 Decode。

### 9.4 E2E 上升但 TTFT、TPOT 都稳定

先检查实际输出长度是否增加。
由近似关系：
$$
E2E\approx TTFT+(N_{\text{out}}-1)TPOT+T_{\text{send-tail}}
$$
在 TPOT 不变时，更长输出自然拉长 E2E。
若输出长度也稳定，则检查发送背压、客户端读取速度、后处理和结束事件定义。

### 9.5 错误上升但 GPU 正常

候选机制包括 admission 拒绝、版本协议不兼容、Tokenizer/模板身份错误、Router 无候选副本或客户端 deadline 先到。
支持证据来自结果分类和控制事件，而不是继续寻找 GPU 峰值。
这说明 RED 能先发现影响，USE 再帮助判断是否与资源有关。

### 9.6 单副本异常与全池异常

若长尾集中在一个逻辑副本代际，优先检查该副本四个 rank、GPU 拓扑、缓存状态和启动阶段。
若所有副本同时变化，优先检查 workload、入口、共享依赖和控制动作。
按版本与副本拆分是定位范围，不是证明因果；最终仍要回到事件先后与机制证据。

## 10. 统一算例：一次突发中的归因

下面是符合 \(C_{10}\) 的教学观测，不代表真实硬件数据：12:00:00，offered load 从 \(6\) 升到 \(10\) req/s，持续 30 秒；入口同时保留 accepted、rejected、cancelled。

### 10.1 第一阶段：发现用户症状

12:00:06，\((8192,512)\) 且 cache miss cohort 的 TTFT 首先接近 1.5 秒；短请求与 hit cohort 仍达标，TPOT 低于 60 毫秒。
准确症状是“突发开始后，长输入 cache miss cohort 的 TTFT 先失守，Decode 仍稳定”。
这比“服务变慢”更可验证。

### 10.2 第二阶段：形成两个假设

假设 A 是突发让 runtime queue 增长；预期证据为 accepted workload 增长、queue work 斜率为正、\(t_4-t_3\) 增大。
假设 B 是路由权重变更打散前缀局部性；预期证据为稳定前缀占比仍为一半，但实际命中 token 下降，Prefill 工作先于队列上升。

### 10.3 第三阶段：沿 timeline 取证

控制事件显示 11:59:50 一个同身份、正确性已过门禁但缓存仍冷的新副本 Ready 并开始加权。
稳定前缀占比没有变化，实际 hit 却下降；miss cohort 的 Prefill work 增加，waiting 在 11:59:54 后转为正斜率，TTFT 在 12:00:06 越界。
同期 TPOT 未系统性变化，GPU 无设备错误，四个 TP rank 均健康。
顺序是“新副本入池 → 命中下降 → Prefill 工作增加 → 排队增长 → TTFT 失守”。
这些证据支持假设 B 是放大因素，也支持突发是必要扰动；两者共同作用，而不是二选一。

### 10.4 第四阶段：验证动作而非只看相关性

控制器降低冷副本初始权重，并在不突破排队预算时优先保留前缀局部性；随后 hit 恢复、queue slope 转负，TTFT 回到边界内。
动作时间与 cohort 对照比单纯看到“后来恢复”提供了更强证据。
180 秒冷启动意味着临时再创建副本无法挽救这次 30 秒突发。
观测系统应把扩容动作记录为“恢复未来容量”，而不能在新副本仍 Warming 时把 desired count 当作已生效容量。

### 10.5 第五阶段：检查合同完整性

复盘确认 offered 分母不因拒绝下降，三档长度仍符合合同，稳定前缀与实际命中分开，三项延迟由请求事件计算。
同时确认 Ready、路由加权和缓存变冷在同一 timeline，没有相加阶段 P99，Error Budget 包含所有 bad request。

## 11. 观测系统自己的失败模式

### 11.1 缺数据不等于零

采集器中断时，GPU 错误、队列和请求率都可能消失；填成零会制造“突然空闲且无错误”的假象。
数据新鲜度必须可观测，并与业务事件时间分开。

### 11.2 遥测背压会选择性丢失

故障时日志量增加，遥测管道容易在最重要时刻过载；选择性丢掉错误或长 trace 会让样本偏向健康请求。
应记录丢弃量、缓冲年龄和采样变化，并保证 SLO 聚合不依赖易丢详细事件。

### 11.3 协调遗漏会美化延迟

响应变慢时自动降低发送速率的负载源会漏掉本应到达的请求；只统计 accepted request 也会产生类似 coordinated omission。
\(C_{10}\) 要求从可信入口保留 offered load，正是为了避免这种自我美化。

### 11.4 重试会重复计数

一个用户意图可能产生多个后端 attempt：容量分析需要 attempt 视角，用户 SLO 需要 logical request 视角。
若两者混在同一 Rate 和 Error denominator 中，重试风暴会既放大流量又扭曲成功率。

### 11.5 版本升级会改变语义

运行时升级可能重命名指标、改变 waiting 定义或分布区间；观测合同要稳定组织语义，并在 canary 中比较版本。
“还能采到一个同名数”不代表统计含义没有变化。

## 12. 代价、边界与设计取舍

更细的请求事件提升归因能力，也增加 CPU、网络、存储和隐私风险。
更短的采样周期能看见尖峰，也会增加遥测开销与噪声。
更多标签方便切片，却会放大时序基数。
更高 trace 保留率能复现长尾，但尾部采样需要额外缓冲。

观测应遵循最小充分原则：
1. 全量保留 SLO 分母与低基数结果聚合；
2. 请求级日志保留可关联的阶段事实，不默认保留内容；
3. 追踪按风险分层采样；
4. 控制动作与身份变化作为一等事件；
5. 设备信号必须映射回逻辑副本；
6. 每项新增遥测都说明它能推翻哪个假设。

本节没有规定具体指标名称、存储系统、采样百分比或告警阈值。
RED、USE 与 Error Budget 是推理框架，不是某种监控产品的功能清单。
相关性不能单独证明因果，最终结论需要 timeline、对照 cohort 与可重复实验。
观测也不能替代 admission、路由、扩缩容和容量余量；它只为这些动作提供可信 feedback。

## 总结

推理可观测性的主线是一条请求级 timeline。
它从 offered arrival 开始，经过 admission、Router、runtime queue、KV/Cache、Prefill、Decode 和发送结束，并叠加 GPU 状态与控制动作。

RED 判断用户是否受影响，USE 检查资源利用、饱和与错误，排队把需求和有效能力连接起来。
SLO 把正确性、TTFT、TPOT、E2E 合成请求结果，Error Budget 再把结果转成变化速度约束。

低基数指标用于总体，日志与追踪用于请求证据。
可靠排障始终遵循“症状 → 可证伪假设 → 预期证据 → 反证”，而不是看到一个高利用率就宣布根因。
